# 4  **V5-DD-1**  **同态加密模块**

在传统全密态数据库中，加密列仅支持等值查询（DET）、范围查询（OPE）和模糊匹配（SEARCH）等"查询型"能力，无法对密文直接进行算术运算。本模块为整型密态类型（int2_enc / int4_enc / int8_enc）提供密文域直接计算能力：加法同态（he-add）支持密文加（+）、减（-）与 SUM 聚合及标量运算，乘法同态（he-mul）支持密文乘（*）、幂（^、power）与标量乘法，并支持跨类型运算与对称算法并存（一列多 DEK）。模块设计遵循"服务端密文运算、客户端解密校验"的分工：服务端持同态公钥在密文域完成运算，不感知明文；客户端解密后按结果类型做范围校验。

## 4.1  **V5-DD-1-1**  **EC-ElGamal（加法同态）算法设计**

### 4.1.1  **程序描述**

本子模块设计 EC-ElGamal 加法同态算法的完整实现方案，覆盖算法原理、CRT 拆分、BSGS 离散对数求解、并行解密、负数处理与溢出校验，为 he-add 密文的加/减/SUM/标量运算提供客户端加解密与服务端运算的算法基础。算法基于公开密码学文献（T. ElGamal 1985、N. Koblitz 1987），不依赖第三方商用加密组件。

### 4.1.2  **功能**

- 密钥对生成：基于 P-256 椭圆曲线生成 EC-ElGamal 密钥对（私钥 x、公钥 Q = x·G），可切换 SM2 曲线以符合国密要求；
- 加密：将明文 m 编码为曲线标量倍点后概率性加密为 (C1, C2)，同一明文每次密文不同；
- 解密：由私钥恢复 m·G 后经 BSGS 求解离散对数得到明文 m；
- 同态运算：密文加（E(a)+E(b)）、密文减（E(a)−E(b)）、标量倍点（k·E(a)）；
- CRT 拆分：将明文按 8 个 12-bit 素数拆分为同余组分别加密，解密时逐分量解 DLP 后 CRT 重组，支撑 int8 全值域与高效解密；
- 并行解密：8 个 CRT 分量的 DLP 求解相互独立，多线程并行加速；
- 负数支持：按符号约定（还原值 > N/2 视为负数）支持负数明文的同态运算；
- 跨类型运算支持：EG_ADD 密文段格式与类型无关，支撑 int2/int4/int8 两两组合运算（见 4.4）。

### 4.1.3  **性能**

- 解密性能：BSGS 表（2^14 条目）覆盖 12-bit 值域，0 步命中；8 分量并行求解，线程数上限 16；
- 客户端 HE 查询启动：BSGS 表静态数据化（编译进 libpq，参数指纹校验兜底）+ PBKDF2 HMAC_CTX 复用，HE 查询启动由约 0.6s 降至约 0.18s；
- 单次加解密：算法内部并行（固定小线程数）提速约 1.4~1.5 倍；
- 批量解密：按行分片并行，约 3.7~5.7 倍（行数较少时自动退化为串行）；
- 同态加法性能指标（需求 4.8.1）：返回 10000 行（纯解密返回）平均耗时 ≤ 50000ms；SUM 1 万行（服务端聚合）平均耗时 ≤ 20000ms。

### 4.1.4  **输入项**

| 输入项 | 类型/格式 | 说明 |
|---|---|---|
| 明文 m | int2/int4/int8 整型 | 待加密明文，绝对值范围 ≤ 2^63−1（int8 全值域）|
| 公钥 Q | 椭圆曲线点（压缩形式 33B）| 加密侧使用，存于服务端 hg_dek_args（he_ec_pubkey）|
| 私钥 x | 曲线标量 | 解密侧使用，经 KEK(sm2) 信封保护存于 hg_dek_args（he_ec_privkey）|
| 曲线参数 | P-256（或 SM2）| 基点 G、阶 n、素数 p |
| CRT 参数 | 8 个 12-bit 素数 | 每分量值域 0~4095 |
| 参与运算密文 | CipherDataType v2.0 的 EG_ADD 段 | 两个操作数段内 DEK 分布式身份标识必须一致 |

### 4.1.5  **输出项**

| 输出项 | 类型/格式 | 说明 |
|---|---|---|
| 密文 | EG_ADD 段（dek_id:4B + 密文体）| 密文体 = 1B 分区数 + 8×(C1+C2 各 33B)；8 分区时密文体 529B，含段首共 533B |
| 解密明文 | int2/int4/int8 | 按结果列类型返回；超范围时报错 |
| 同态运算结果 | EG_ADD 段密文 | 加/减/标量运算结果仍为 EC-CRT 密文，仅含 EG_ADD 段 |

### 4.1.6  **算法**

| 环节 | 数学表达 | 说明 |
|---|---|---|
| 密钥生成 | 私钥 x ← 随机(0,n)；公钥 Q = x·G | 一次性生成，公钥明文入库 |
| 加密 | E(m) = (C1, C2) = (r·G, m·G + r·Q)，r 为随机数 | 概率性加密 |
| 解密 | M = C2 − x·C1 = m·G，求解离散对数得 m | BSGS 加速 |
| 同态加 | E(a)+E(b) = (C1a+C1b, C2a+C2b) = E(a+b) | 点群加法 |
| 同态减 | E(a)−E(b) = (C1a−C1b, C2a−C2b) = E(a−b) | 点群减法 |
| 标量乘 | k·E(a) = (k·C1, k·C2) = E(k·a) | 标量倍点 |

CRT 拆分与重组：明文 m 按 8 个 12-bit 素数 p1..p8 拆为同余组 mi = m mod pi，各分量独立加密；解密时每分量在 12-bit 值域内解 DLP（BSGS 2^14 表一步命中），再按 CRT 公式重组恢复 m。总明文位宽 96 bit（2^96 ≈ 7.9×10^28），覆盖 int8 全范围。

BSGS（Baby-Step Giant-Step）：预计算 i·G（i=0..16383）按键值排序建表（一次构建、多次复用，支持并行构建与静态数据化）；在线求解时对目标点 M 逐次减去 m·G 并二分查表，命中即得明文值。双向 BSGS 支持负数解密（与正数对称）。

负数处理：明文经 CRT 还原后取值在 [0, N) 区间，当还原值 m > N/2 时实际整数为 m − N；加密侧对负数取模后加密。

溢出处理：8 分区 CRT 总模数 P ≈ 2^96，按符号约定后有效明文范围约 ±2^95，远大于 int8 范围；服务端不判溢出，客户端解密后按结果列类型（int2/int4/int8）范围校验，超范围报错，与原生整型运算行为一致。

### 4.1.7  **流程逻辑**

```
加密路径（写入/常量）：
明文 m ─► CRT 拆分（8×12-bit 分量）─► 逐分量 EC 加密（随机 r）─► 组装 EG_ADD 段
        （段首嵌入 he-add DEK 分布式身份标识）─► 填入 CipherDataType v2.0 EG_ADD 槽位 ─► hex 传输服务端

同态运算路径（服务端）：
EG_ADD(a) + EG_ADD(b) ─► 校验段内 DEK 身份一致 ─► 逐分量点加/点减/标量倍点 ─► 结果 EG_ADD 段

解密路径（查询结果）：
EG_ADD 段 ─► 解析段内 DEK 身份 ─► 加载 he-add DEK 私钥（KEK(sm2) 解信封）─► 8 分量并行 BSGS 解 DLP
        ─► CRT 重组 ─► 符号还原 ─► 按结果类型范围校验 ─► 返回明文
```

### 4.1.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 4 章对应（V5-AD-1-1）。

2）方法：加密调度器算法接口（tecc_crypto_scheduler 按列元数据 enable_he_add 选择）；服务端操作符（+、-、标量运算）与聚合过渡函数内部调用同态运算核心；客户端解密经密钥管理器加载 HE 私钥后调用。

3）接口说明：算法层接口由 src/common/tecc_algorithm/ 提供；服务端同态运算核心位于 src/backend/utils/tecc/he_operators.c；前端透传与结果类型标记位于 tecc_processor。

4）接口参数：明文/密文 Datum、DEK 分布式身份标识、曲线参数、BSGS 表上下文、线程数（环境变量控制）。

### 4.1.9  **存储分配**

- 密文存储：EG_ADD 段 533B（8 分区），随行内 varlena 存储（CipherDataType v2.0）；
- BSGS 表：静态数据约 3MB 编译进 libpq（页缓存跨进程共享，物理内存增量小）；运行时构建路径作为参数指纹不匹配时的兜底；
- 公钥缓存：服务端按 DEK 分布式身份缓存同态公钥（进程级多键哈希表，relcache 失效时整表失效）；
- 线程上下文：并行解密各工作线程持有独立运算上下文，避免 OpenSSL 上下文竞争。

### 4.1.10  **注释设计**

按《瀚高数据库内核编码规范》执行：新增代码以 `/* ReqID:TECC4.0 */` 标注；算法关键步骤（CRT 拆分、BSGS 建表/求解、符号约定、范围校验）以块注释说明数学依据；线程安全约束（连接特定状态存于 TeccState、禁止全局变量）在相关函数头注释说明。

### 4.1.11  **限制条件**

- 仅支持 int2_enc / int4_enc / int8_enc 三种密态整数类型，不支持 numeric_enc、float4_enc、float8_enc；
- 仅支持在 PG 兼容端口使用；
- 依赖非对称密钥体系：he-add DEK 必须绑定非对称 KEK（key_algo='sm2'）；
- 跨类型运算要求参与列使用同一 DEK（段内 DEK 身份校验）；
- 明文范围上限：单值读写与单次加法不受限（覆盖 int8 全范围）；多明文持续累加（SUM、链式加法、连续 UPDATE 赋值）时累计明文总和不能超过约 42.9 亿，超出则解密失败；
- 服务端不做溢出判断，超范围由客户端解密后校验报错。

### 4.1.12  **测试计划**

- 单元测试：CRT 拆分/重组正确性（边界值 0、±1、int2/int4/int8 上下限）、BSGS 求解（0~4095 全值域）、负数符号还原、随机性（同明文不同密文）；
- 功能测试：密文加/减（列×列、列×常量、常量在左）、同列相减为 0、SUM 聚合（含 NULL 行）、标量乘、跨类型组合 6 方向、结果类型断言；
- 溢出测试：单次加法超 int8 范围、SUM 累计超 42.9 亿上限，均报错；
- 边界测试：DEK 不匹配报错、操作数缺 EG_ADD 段报错、私钥缺失返回密文；
- 回归：make check-tecc-libpq 全量 + 同态专项用例（shared/sql 与 libpq/sql）。

### 4.1.13  **尚未解决的问题**

- SUM 聚合明文上限（约 42.9 亿）为算法解密上限，超出报错；更高上限方案（增大 CRT 分区数/位宽）待评估。

## 4.2  **V5-DD-1-2**  **有限域 ElGamal（乘法同态）算法设计**

### 4.2.1  **程序描述**

本子模块设计有限域 ElGamal（FF-ElGamal）乘法同态算法的完整实现方案，为 he-mul 密文的乘（*）、幂（^、power）与标量乘法提供算法基础。与 EC-ElGamal 的关键区别：解密通过模逆直接恢复明文，不依赖 DLP 求解，无需 CRT 拆分也能处理大数；CRT 双素数模式仅用于性能优化。

### 4.2.2  **功能**

- 密钥对生成：基于 RFC 5114 IKE/2048 安全素数群生成密钥对（私钥 x、公钥 h = g^x mod p）；
- 加密：E(m) = (c1, c2) = (g^r, m·h^r) mod p，概率性加密；
- 解密：m = c2 · (c1^x)^(−1) mod p，直接模算术，无需解 DLP；
- 同态乘法：E(a)·E(b) = (c1a·c1b, c2a·c2b) = E(a·b mod p)；
- 幂运算：密文连续自乘 n−1 次（a^n = a×a×…×a），指数为正整数、上限 10000；
- 标量乘法：服务端持公钥现场加密常量 k 得 E(k)，再做同态乘法；
- CRT 双素数优化：按 p1、p2（各 1024-bit）双模运算，净加速约 4 倍；
- 跨类型运算支持：EG_MUL 密文段格式与类型无关（见 4.4）。

### 4.2.3  **性能**

- 同态乘法性能指标（需求 4.8.1）：返回 10000 行（纯解密返回）平均耗时 ≤ 30000ms；幂运算 a^10000 返回 1 行平均耗时 ≤ 300ms；
- CRT 双素数模式：1024-bit 模幂约比 2048-bit 快 8 倍，双素数开销抵消后净加速约 4 倍；
- 解密直接模算术（一次模幂 + 一次模逆），无 DLP 求解开销，整体性能优于 EC-ElGamal。

### 4.2.4  **输入项**

| 输入项 | 类型/格式 | 说明 |
|---|---|---|
| 明文 m | int2/int4/int8 整型 | 待加密明文 |
| 公钥 h | 2048-bit 大数 | 加密侧使用，存于 hg_dek_args（he_eg_pubkey）|
| 私钥 x | 2048-bit 大数 | 解密侧使用，信封保护存于 hg_dek_args（he_eg_privkey）|
| 群参数 | RFC 5114 IKE/2048（或 CRT 双素数 p1/p2）| 安全素数 p、生成元 g |
| 幂指数 n | 正整数（常量或非密态整数列）| 上限 10000，不支持密态列 |
| 参与运算密文 | CipherDataType v2.0 的 EG_MUL 段 | 两操作数段内 DEK 身份一致 |

### 4.2.5  **输出项**

| 输出项 | 类型/格式 | 说明 |
|---|---|---|
| 密文 | EG_MUL 段（dek_id:4B + 密文体）| 标准模式 c1、c2 各 256B（定长填充）共 512B，含段首 516B；CRT 模式按 p1/p2 顺序 4×128B，总长相同 |
| 同态乘法结果 | EG_MUL 段密文 | 仅含 EG_MUL 段 |
| 幂运算结果 | EG_MUL 段密文 | 解密得 a^n，按结果类型范围校验（类型提升见 4.4）|
| 解密明文 | int2/int4/int8 | 按结果列类型返回，超范围报错 |

### 4.2.6  **算法**

| 环节 | 数学表达 | 说明 |
|---|---|---|
| 密钥生成 | 私钥 x ← 随机；公钥 h = g^x mod p | RFC 5114 群参数 |
| 加密 | E(m) = (c1, c2) = (g^r, m·h^r) mod p | 概率性加密 |
| 解密 | m = c2 · (c1^x)^(−1) mod p | 直接模算术，无需解 DLP |
| 同态乘 | E(a)·E(b) = (c1a·c1b, c2a·c2b) = E(a·b mod p) | 分量模乘 |
| 标量乘 | E(k) 现场加密后同态乘 | 服务端持公钥加密常量 |
| 幂 | E(a)^n = 连续自乘 n−1 次 | 服务端密文域叠加 |

CRT 双素数模式：明文 m 分别在 p1、p2 两个子群加密为 (c1_i, c2_i)，解密时各自恢复 m_i 后按 CRT 公式 m = m1 + p1 · ((m2 − m1) · p1⁻¹ mod p2) (mod N) 重组，N = p1·p2 ≈ 2048 bit，与标准模式安全强度相当。

幂运算入口：`^` 运算符与 power 函数双入口等价；指数 n 必须为正整数，支持整型常量或非密态整数列，不支持密态列；负指数、零指数按语法错误处理；指数上限 10000（DoS 防护）。

标量乘法：常量 k 由服务端持 he-mul 公钥现场加密为 E(k) 后做同态乘法；双向支持（a×k 与 k×a）；若列同时开启 he-add 可优先复用 EC-ElGamal 标量倍点（性能更优）；负标量按符号约定取模加密、解密侧还原。

### 4.2.7  **流程逻辑**

```
加密路径：明文 m ─► (c1, c2) = (g^r, m·h^r) ─► 组装 EG_MUL 段（段首 he-mul DEK 身份）─► 填入 v2.0 EG_MUL 槽位

同态乘法路径（服务端）：EG_MUL(a) × EG_MUL(b) ─► DEK 身份一致校验 ─► 分量模乘 ─► 结果 EG_MUL 段
幂运算路径（服务端）：E(a) 连续自乘 n−1 次（n ≤ 10000）─► 结果 EG_MUL 段

解密路径：EG_MUL 段 ─► 解析段内 DEK 身份 ─► 加载 he-mul DEK 私钥 ─► m = c2·(c1^x)^(−1) mod p
        ─► 按结果类型范围校验 ─► 返回明文
```

### 4.2.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 4 章对应（V5-AD-1-2）。

2）方法：服务端操作符（*、^、power、标量乘法）与前端透传链路；客户端加解密经加密调度器按 enable_he_mul 选择算法。

3）接口说明：服务端同态乘法/幂运算核心位于 src/backend/utils/tecc/he_operators.c（he_mul_pow_core 等）；系统目录注册见 4.5。

4）接口参数：明文/密文 Datum、DEK 分布式身份标识、群参数、指数（幂运算）。

### 4.2.9  **存储分配**

- 密文存储：EG_MUL 段 516B（标准/CRT 模式总长一致），随行内 varlena 存储；
- 公钥缓存：服务端按 DEK 分布式身份缓存 he-mul 公钥（与 EC 公钥共用多键缓存，见 4.1.9）。

### 4.2.10  **注释设计**

按编码规范以 `/* ReqID:TECC4.0 */` 标注新增代码；群参数来源（RFC 5114）、CRT 重组公式、符号约定、指数上限校验等关键逻辑加注释说明。

### 4.2.11  **限制条件**

- 仅支持 int2_enc / int4_enc / int8_enc；
- he-mul DEK 必须绑定非对称 KEK（key_algo='sm2'）；
- 幂运算指数须为正整数且 ≤ 10000；负/零指数按语法错误处理；指数不支持密态列；
- 跨类型乘法要求参与列使用同一 he-mul DEK；
- 乘法/幂运算结果仅含 EG_MUL 段，只能赋值给纯 he-mul 列（或纯 he-add 列，见 4.4 赋值校验）；
- 结果解密后按类型范围校验，超范围报错。

### 4.2.12  **测试计划**

- 单元测试：加解密 roundtrip（0、±1、边界值）、CRT 双素数与标准模式结果一致性、随机性；
- 功能测试：密文乘（列×列、列×常量、双向）、幂运算（^ 与 power 等价）、标量乘法、跨类型乘法；
- 边界测试：指数 0/负/超 10000 报错、DEK 不匹配报错、缺 EG_MUL 段报错、结果超类型范围报错；
- 回归：make check-tecc-libpq 全量 + 同态专项用例。

### 4.2.13  **尚未解决的问题**

- 超大指数（接近 10000）的服务端耗时与超时策略待实际环境验证。

## 4.3  **V5-DD-1-3**  **密文数据结构设计**

### 4.3.1  **程序描述**

同态加密要求单个加密值可同时携带多种算法的密文，因此将密文格式升级为 CipherDataType v2.0：在 v1.0（Header + RND/DET/OPE/SEARCH 四对称槽位）基础上新增 EG_ADD、EG_MUL 两个同态槽位，各同态槽位内嵌所属 DEK 的分布式身份标识（4B 定长），支撑同一密态列同时绑定对称 DEK 与多个同态 DEK（一列多 DEK）的独立解密与运算。

### 4.3.2  **功能**

- v2.0 头部：版本号 + 各槽位长度（含 eg_add_length、eg_mul_length）+ 全局 DEK 分布式身份标识；
- 同态槽位：EG_ADD 段（EC-CRT 密文）、EG_MUL 段（FF-ElGamal 密文），各段独立携带 DEK 身份；
- 槽位独立为空：未启用对应算法的列不填充该槽位（长度为 0）；
- 槽位填充规则：纯 HE 列不生成 RND 密文；混合列同时填充对称槽位与同态槽位；同态运算结果密文仅携带参与运算的同态段；
- 密文解析/组装：客户端写入加密时组装，服务端运算时按段提取，客户端解密时按段解析（维修性工具函数 tecc_enc_info 亦基于该结构，见第 11 章）。

### 4.3.3  **性能**

- 密文长度：EG_ADD 段 533B（8 分区）、EG_MUL 段 516B（标准/CRT 一致）；纯 HE 列不生成 RND 密文，减少存储体积与解密负担；
- 槽位解析开销：按长度头定位槽位边界，O(1) 定位，不扫描全密文。

### 4.3.4  **输入项**

| 输入项 | 说明 |
|---|---|
| 列算法配置 | SUPPORT_ALGO（det/ope/search/he-add/he-mul + 默认 rnd）|
| 各 DEK | 对称 DEK（column_key_id）、he-add DEK（he_add_dek）、he-mul DEK（he_mul_dek），各带分布式身份标识 |
| 各算法密文 | RND/DET/OPE/SEARCH 段密文、EG_ADD 段密文、EG_MUL 段密文 |

### 4.3.5  **输出项**

| 输出项 | 说明 |
|---|---|
| CipherDataType v2.0 密文 | Header(36B) + 各槽位（按配置填充，可空），以 hex 形式传输与存储 |
| 槽位提取结果 | 单算法段密文载荷（供 tecc_decrypt_raw 客户端解密、同态运算或段比较使用）|

### 4.3.6  **算法**

v2.0 存储格式：

```
┌──────────┬──────┬──────┬──────┬────────┬──────────────────┬──────────────────┐
│ Header   │ RND  │ DET  │ OPE  │ SEARCH │ EG_ADD           │ EG_MUL           │
│ (36 B)   │ ...  │ ...  │ ...  │ ...    │ [dek_id][HE加]   │ [dek_id][HE乘]   │
└──────────┴──────┴──────┴──────┴────────┴──────────────────┴──────────────────┘
```

| 字段 | 位置 | 长度 | 说明 |
|---|---|---|---|
| header | 开头 | 36 B | 版本号 + 各槽位长度（含 eg_add_length、eg_mul_length）+ DEK 分布式ID |
| eg_add_length | header | 4 B | EG_ADD 段总长度（含内嵌 4B DEK 分布式ID）|
| eg_mul_length | header | 4 B | EG_MUL 段总长度（含内嵌 4B DEK 分布式ID）|
| EG_ADD 段 | 槽位 5 | 动态 | [dek_id:4] + EC-CRT 密文（1 + 66×n 字节）|
| EG_MUL 段 | 槽位 6 | 动态 | [dek_id:4] + ElGamal 密文（512 字节）|

DEK 身份标识规则：密文中所有 DEK 身份一律使用分布式身份标识（对 schema.dek_name 的确定性 hash，即 hg_dek 表的 column_key_distributed_id），不使用实例内 Oid；header 全局 DEK 分布式ID 用于对称槽位，EG_ADD/EG_MUL 段内嵌各自 DEK 的分布式ID，各段独立解析密钥、互不干扰。

EG_ADD 段内部格式：`[dek_id:4][num:1][C1_1:33][C2_1:33]...[C1_n][C2_n]`，8 分区时密文体 529B（含段首 533B），分区数可配置、长度随 n 线性变化。

EG_MUL 段内部格式：`[dek_id:4][c1:256][c2:256]`（标准模式）；CRT 模式按 p1/p2 顺序 `[c1_1:128][c2_1:128][c1_2:128][c2_2:128]`，总长均为 512B。

槽位填充规则：

| 列配置（SUPPORT_ALGO） | RND | DET/OPE/SEARCH | EG_ADD | EG_MUL |
|---|---|---|---|---|
| 仅 he-add | 不填充 | 不填充 | 填充 | 不填充 |
| 仅 he-mul | 不填充 | 不填充 | 不填充 | 填充 |
| 对称算法（默认含 RND） | 填充 | 按需填充 | 不填充 | 不填充 |
| he-add + he-mul | 不填充 | 不填充 | 填充 | 填充 |
| 对称 + he-add / he-mul（并存） | 填充 | 按需填充 | 按配置填充 | 按配置填充 |

规则要点：纯 HE 列（仅配置 he-add/he-mul）不生成 RND 密文，保证 HE 解密路径不被对称槽位干扰；同态运算结果密文仅携带参与运算的同态段（EG_ADD 或 EG_MUL），对称段不被携带——这是并存模式下赋值约束的根源（见 4.4.5）；同态操作符执行前先校验所需槽位是否存在。

### 4.3.7  **流程逻辑**

```
写入路径：明文 ─► 按列算法配置逐算法加密（对称 + 同态）─► 组装各槽位 ─► 填 header 长度 ─► v2.0 密文 hex 发送
运算路径：提取 EG_ADD/EG_MUL 段（按长度头定位）─► 校验段内 DEK 身份 ─► 同态运算 ─► 结果仅含参与段
解析路径：header 解析 ─► 按槽位长度定位各段 ─► 段内 DEK 身份反查 DEK ─► 加载密钥解密
```

### 4.3.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 4 章对应（V5-AD-1-3）。

2）方法：密文组装/解析由客户端数据格式化模块（tecc_formatter）与后端类型 I/O 提供；服务端同态运算与 tecc_enc_info 工具函数按段读取。

3）接口说明：v2.0 结构向后兼容 v1.0 对称槽位布局；V4.0.0 密文（无同态槽位）可继续解析解密。

4）接口参数：算法配置位掩码、各算法密文段、DEK 分布式身份标识、输出 v2.0 密文。

### 4.3.9  **存储分配**

- 单值密文：v2.0 结构按列配置动态增长（对称列约 132B，纯 HE 列 533B 或 516B，全开列约 1.2KB）；
- 无新增服务端持久化结构，密文随行存储（varlena）。

### 4.3.10  **注释设计**

密文头部布局、槽位偏移、DEK 身份内嵌规则、槽位填充规则等以 `/* ReqID:TECC4.0 */` 注释说明，并在格式化模块头文件标注 v1.0/v2.0 兼容关系。

### 4.3.11  **限制条件**

- 各槽位独立为空（长度为 0），未启用算法的列不填充；
- 同态运算结果密文仅携带参与段，赋值目标列必须兼容（见 4.4.5）；
- 密文段内 DEK 身份必须与绑定元数据一致，否则解密/运算报错。

### 4.3.12  **测试计划**

- 结构测试：各配置组合（纯对称/纯 HE/并存/全开）的槽位填充与长度断言；
- 兼容测试：V4.0.0 格式密文（v1.0）在 v2.0 解析器下正常解密；
- roundtrip：写入→导出→导入→解密数据一致；
- 工具函数验证：tecc_enc_info 输出各段长度与内容与预期一致。

### 4.3.13  **尚未解决的问题**

## 4.4  **V5-DD-1-4**  **前端处理设计**

### 4.4.1  **程序描述**

前端处理设计覆盖建表语法解析与校验、HE 表达式透传、结果列类型提升、数据写入加密路径、UPDATE 赋值校验与查询语法增强六部分，由 libpq 客户端 tecc_processor（create_stmt_processor / stmt_processor / where_clause_processor / expr_processor）实现，保证同态加密与对称加密在 SQL 层面透明协同。

### 4.4.2  **功能**

- 建表语法解析：解析 ENCRYPTED WITH 子句中的 DEK / SUPPORT_ALGO / HE_ADD_DEK / HE_MUL_DEK 选项并执行第一层校验（SUPPORT_ALGO 与 DEK 参数匹配、DEK 的 key_algo 与算法一致）；
- HE 表达式透传：涉及加密列的 +、-、*、^ 运算识别为 HE 运算，不做客户端常量加密，密文直接发送服务端执行同态运算；与 DET/OPE/SEARCH 查询改写互斥；
- 结果列类型提升：按原生整数提升惯例标记 HE 表达式结果类型（跨类型取较大者、SUM 提升 int8_enc、幂提升 int8_enc）；
- 数据写入加密路径：INSERT/UPDATE 按列算法配置逐槽位加密组装 v2.0 密文；
- UPDATE 赋值校验：HE 运算结果仅含同态段，赋值目标列必须兼容；
- 查询语法增强：JOIN 等值/范围、UNION 系列、子查询、WITH、GROUP BY、ORDER BY、DISTINCT、COUNT(DISTINCT)、精度/长度指定等语法场景的处理规则（见 4.4.6）；
- DET 等值 JOIN 规划期分流：优化器将无 OPE 加密列的等值子句排除 Merge Join 候选、落到 Hash Join（见 4.4.6）。

### 4.4.3  **性能**

- 建表元数据检测走索引（复用现有索引，消除 hg_encrypted_columns 全表扫描）；
- HE 表达式透传不产生客户端常量加密开销；DET 等值 JOIN 稳定走 Hash Join，避免误选 Merge Join 运行期报错；
- 前端校验零误报：元数据缺失时防御性放行，不触发假阳性错误。

### 4.4.4  **输入项**

| 输入项 | 说明 |
|---|---|
| 建表语句 | CREATE TABLE ... 列类型 ENCRYPTED WITH (DEK, HE_ADD_DEK, HE_MUL_DEK, SUPPORT_ALGO) |
| 查询语句 | SELECT/INSERT/UPDATE/DELETE 含 HE 表达式或复杂语法 |
| 列元数据 | hg_encrypted_columns（encryption_type 位掩码）+ hg_encrypted_column_args（he_add_dek/he_mul_dek）+ DEK 元数据 |
| UPDATE SET 赋值 | 目标列与结果表达式（含 DEK 与算法配置）|

### 4.4.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 改写后 SQL | 常量按列算法加密后原位替换（HE 表达式透传不改写）|
| 结果列类型标记 | HE 表达式结果类型（同类型原类型、跨类型较大者、sum/power → int8_enc）|
| 校验结果 | 语法/算法/DEK 匹配校验通过或固定格式错误 |
| 密文写入值 | v2.0 密文 hex（按列算法配置逐槽位填充）|

### 4.4.6  **算法**

（1）建表语法解析与校验（双层）：前端语法校验（SUPPORT_ALGO 与 DEK 参数匹配、key_algo 与算法一致，语法错误立即报错、不访问数据库）→ 后端权威校验（DEK 存在性、key_algo 与 SUPPORT_ALGO 匹配、USAGE 权限）→ 写入列 DEK 绑定元数据（hg_encrypted_column_args）。

| 选项 | 含义 | 必选条件 |
|---|---|---|
| DEK | 对称 DEK（供 DET/OPE/SEARCH/RND）| 列启用任一对称算法时必选 |
| SUPPORT_ALGO | 列启用算法列表（det/ope/search/he-add/he-mul）| 不配置或仅配置对称算法时默认同时启用 rnd |
| HE_ADD_DEK | he-add 算法使用的同态 DEK | 列启用 he-add 时必选 |
| HE_MUL_DEK | he-mul 算法使用的同态 DEK | 列启用 he-mul 时必选 |

（2）HE 表达式透传规则：+、-、*、^ 涉及加密列时识别为 HE 运算，不做客户端常量加密（含常量在内直接发送服务端）；幂运算指数作为普通整型参数透传（常量或非密态整数列）；跨类型 HE 表达式同样透传，结果列类型按提升规则标记。

（3）结果列类型提升规则：

| 表达式 | 结果类型 |
|---|---|
| int2_enc + int4_enc / int4_enc + int2_enc | int4_enc |
| int2_enc + int8_enc / int8_enc + int2_enc | int8_enc |
| int4_enc + int8_enc / int8_enc + int4_enc | int8_enc |
| 同类型运算 | 原类型 |
| sum(int2_enc) / sum(int4_enc) / sum(int8_enc) | int8_enc |
| 幂运算 intX_enc ^ n | int8_enc（提升到最宽密态整型，与原生幂运算结果取更宽类型惯例一致，避免解密明文超出原类型范围）|

（4）数据写入加密路径：对称算法（按需 DET/OPE/SEARCH，默认含 RND）→ 对称 DEK 加密填充对应槽位；he-add → he-add DEK 公钥 EC-CRT 加密填充 EG_ADD 槽位；he-mul → he-mul DEK 公钥 FF 加密填充 EG_MUL 槽位；纯 HE 列仅填同态槽位、混合列同时填充；组装 v2.0 密文后以 hex 传输。

（5）UPDATE 赋值校验：

| 赋值场景 | 结果 |
|---|---|
| HE 结果 → 纯 he-add / he-mul 列 | 成功 |
| HE 结果 → 含对称算法配置的列（仅对称、或对称+同态并存）| 报错（结果密文缺少对称密文段）|
| 跨 DEK 赋值（结果 DEK 与目标列 DEK 不一致）| 报错（DEK 不匹配）|

校验由前端处理器在 UPDATE SET 赋值时执行（基于列缓存元数据），错误提示明确指明结果 DEK 与目标列 DEK 的差异。

（6）查询语法增强（对应需求 V4.0.1-20-3-8）：前端对查询统一走"子句遍历 → 加密列提取 → 列元数据获取 → 条件常量按列算法加密 → 密文比较"处理链路，各语法场景规则：

| 语法场景 | 前端处理 | 算法要求 |
|---|---|---|
| JOIN 等值（a.enc_col = b.enc_col）| 两端为密态列时不做常量加密，直接比较密文（DET 段 memcmp 或 OPE 段等值比较）；递归遍历 JOIN 左右子树提取两侧加密列；不同 DEK 的 JOIN 严格拒绝 | DET 或 OPE |
| JOIN 范围（a.enc_col > b.enc_col）| 范围比较走 OPE 保序密文比较 | OPE |
| UNION ALL | 透传，仅追加结果 | 无条件 |
| UNION / INTERSECT / EXCEPT | 透传；去重依赖服务端对密文的哈希与等值比较 | DET 或 OPE |
| WHERE enc_col IN (子查询) | 子查询（SubLink）递归提取列并处理，返回密文列可直接比较 | DET 或 OPE |
| WHERE enc_col = ANY / ALL (子查询) | ANY 依赖等值比较；ALL 依赖范围比较 | ANY：DET 或 OPE；ALL：OPE |
| EXISTS 子查询 | 透传，不涉及密文直接比较 | 无条件 |
| WITH / WITH RECURSIVE | 透传，不影响 CTE 执行 | 无条件 |
| GROUP BY enc_col | 透传；分组依赖密文哈希。DET-only 列需走 HashAggregate 路径（默认可能走 Sort 路径导致报错，可 SET enable_sort=off 切换）| DET 或 OPE |
| ORDER BY enc_col | 透传；排序依赖 OPE 保序密文 | OPE |
| DISTINCT enc_col | 透传；去重依赖密文等值比较 | DET 或 OPE |
| COUNT(DISTINCT enc_col) | 透传；去重计数依赖密文哈希 | DET 或 OPE |
| 精度/长度指定（varchar_enc(n)、bpchar_enc(n)、numeric_enc(p,s)）| 建表时通过 typenameTypeIdAndMod 解析 typmod 存入列元数据 data_type_original_mod；解密输出按 typmod 格式化；text 原生类型不支持指定长度（text(n) 报错）| 无条件 |

算法缺失处理：where_clause_processor 对操作符与列算法不匹配返回特定错误码（MISSING_DET / MISSING_OPE / MISSING_SEARCH / MISSING_DET_OPE / INCOMPATIBLE_TYPES），前端转换为固定格式错误信息。

子查询与 CTE：FROM 子句子查询（RangeSubselect）、WHERE 子链接（SubLink）均递归调用同一列提取与元数据处理链路；JOIN 嵌套递归遍历左右子树；WITH 透传。

（7）DET 等值 JOIN 规划期分流：DET 加密列的等值 JOIN 语义由 Hash Join 承载（cipherdata_eq 用 DET 段 memcmp、cipherdata_hash_func 用 DET 段确定性哈希，语义正确）；但密态类型注册了 btree 操作符族，优化器静态判定"可排序"可能选 Merge Join，而排序比较 cipherdata_cmp 仅实现 OPE 段路径，DET 列运行期报错。在 Merge Join 候选判定的唯一入口 check_mergejoinable（initsplan.c）处，对"引用无 OPE 加密列（DET-only/RND-only）的等值子句"不设置 mergeopfamilies，排除 Merge Join 候选、自动落 Hash Join。设计要点：保持比较语义不变（cipherdata_cmp 仍仅支持 OPE 段，DET 列 ORDER BY/范围查询/范围 JOIN 继续明确报错）；仅干预 JOIN 路径生成；一侧 DET、一侧 OPE 同样拦截。

### 4.4.7  **流程逻辑**

```
建表：CREATE TABLE ... ENCRYPTED WITH ─► 前端语法校验（SUPPORT_ALGO↔DEK 匹配）─► 后端权威校验（存在性/key_algo/USAGE）
      ─► 写入 hg_encrypted_columns + hg_encrypted_column_args
查询：SQL ─► 语句识别 ─► 子句遍历提取加密列 ─► 数据获取器查列元数据 ─► HE 表达式透传 / 条件常量按列算法加密
      ─► 原位改写 ─► 发送服务端
UPDATE：SET 赋值 ─► 校验结果段类型与目标列配置兼容、DEK 一致 ─► 放行或报错
```

### 4.5.2  **功能**

|---|---|---|

性能测试方法：使用 100 万条测试数据，同态场景使用独立同态表（两列分别开启 he-add 和 he-mul），与对称加密场景分开测试，避免同态段干扰对称加密扫描与查询性能；每个查询场景执行至少 5 次，丢弃第一次结果取平均。

### 4.6.6  **算法**

优化方案汇总：

| 优化层次 | 优化方案 | 大致收益 | 主要影响与风险 |
|---|---|---|---|
| 算法层 | 国密算法预计算表与循环展开 | SM3 吞吐提升约 25%，SM4 反超 OpenSSL | 结果与 OpenSSL 逐字节一致，一致性测试兜底 |
| 算法层 | EC 运算 BN_CTX 复用 | 减少每行 BN_CTX 创建销毁开销 | 仅内存管理优化 |
| 算法层 | BSGS 表并行构建 | 建表约 1s → 约 0.1s | 8 表独立并行，无共享写 |
| 算法层 | BSGS 表静态数据化 | 建表 0.5s 完全消除，HE 查询启动 0.6s → 0.22s | 表数据约 3MB 编译进 libpq；参数指纹不匹配自动回退运行时构建 |
| 算法层 | 双向 BSGS 求解 | 负值解密与正数对称，回归由超时降至 13s | 正数聚合解密慢约 2~3 倍，聚合场景占比小 |
| 算法层 | 离散对数求解上限提升 | 聚合明文上限 2.68 亿 → 42.9 亿 | 正确性提升 |
| 算法层 | PBKDF2 HMAC_CTX 复用 | PBKDF2 单次 49ms → 6ms，HE 查询启动 0.22s → 约 0.18s | HMAC_CTX 为 OpenSSL 3.0 废弃 API（仅编译警告）；输出逐字节一致 |
| 客户端加解密层 | 算法内部并行 | 约 1.4~1.5 倍 | 固定小线程数避免超订阅 |
| 客户端加解密层 | HEX 编解码查找表 | 扫描类场景约 2.86 倍 | 仅文本协议有效 |
| 客户端加解密层 | 字段级并行（批量 INSERT）| 约 5.7 倍 | worker 需独立元数据缓存与运算上下文 |
| 客户端加解密层 | 批量解密并行 | 约 3.7~5.7 倍 | 线程数环境变量控制，行少退化为串行 |
| 服务端聚合层 | SUM 并行聚合 | 约 4.6 倍 | 依赖 PG 原生并行，带 LIMIT 无收益 |
| 服务端缓存与元数据层 | HE 公钥多键缓存 | 消除多 DEK 交替访问缓存抖动 | relcache 失效仍整表失效，粒度安全 |
| 服务端缓存与元数据层 | 建表元数据检测走索引 | 消除 hg_encrypted_columns 全表扫描 | 复用现有索引 |
| 查询优化器层 | DET 等值 JOIN 分流 Hash Join | 稳定走 Hash Join，避免误选 Merge Join 报错 | 仅干预 JOIN 路径生成 |

共同原则：仅在计算单元相互独立、可安全并行时启用并发；并行路径保证共享资源只读或线程隔离；算法类优化通过与 OpenSSL 结果一致性测试兜底。

### 4.6.7  **流程逻辑**

```
性能测试流程：temp-install → 启动 PG → 建加密表（对称表 + 独立同态表）→ seed 100 万行
    → 每用例预热 1 次 + 测量 PERF_RUNS 次（默认 5）→ 对照阈值判定
优化实施流程：热点分析（profiling）→ 方案设计（并行/缓存/预计算）→ 实现 → 一致性/回归验证
```

### 4.6.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 4 章对应（V5-AD-1-6）。

2）方法：性能测试框架（src/test/modules/tecc_tests/perf/，perf/sql + thresholds.json）；环境变量控制并发度。

### 4.6.9  **存储分配**

- BSGS 静态表约 3MB（编译进 libpq，跨进程页缓存共享）；
- 批量加解密 worker 线程各自独立上下文（元数据缓存与运算上下文隔离）。

### 4.6.11  **限制条件**

- 同态乘法（FF-ElGamal）性能优于同态加法（EC-ElGamal），为算法特性（椭圆曲线点运算含多次有限域模运算）；

- 优化正确性：算法优化项与 OpenSSL 一致性测试、密文语义不变断言；
- 并发正确性：并行加解密结果与串行一致。

### 4.6.13  **尚未解决的问题**

- 幂运算 a^10000 指标（≤300ms）依赖服务端重复同态乘法 9999 次的实测性能，实际环境待验证。

## 4.7  **V5-DD-1-7**  **密钥管理依赖说明**

### 4.7.1  **程序描述**

同态加密功能依赖两级密钥体系（KEK/DEK）与非对称密钥（SM2），本子模块说明同态加密对密钥管理的依赖关系，具体设计见第 7 章。

### 4.7.2  **功能**

- 依赖 key_algo 参数设计：同态 DEK（he-add/he-mul）必须绑定非对称 KEK（key_algo='sm2'）；
- 依赖 HE 密钥对生成与存储：he-add 生成 EC-ElGamal 密钥对（P-256）、he-mul 生成 FF-ElGamal 密钥对（RFC 5114 2048-bit），按算法独立生成、互不混用；公钥明文入库 hg_dek_args，私钥经 KEK(sm2) 公钥信封加密后入库；
- 依赖一列多 DEK 绑定（hg_encrypted_column_args）：同一密态列可同时绑定对称 DEK 与 he-add/he-mul DEK；
- 依赖分布式身份标识：密文段内嵌 DEK 分布式身份，服务端运算与客户端解密按段解析密钥；
- 依赖 KEK 密钥轮换（ALTER KEK）：轮换时对关联 HE DEK 私钥信封重加密。

### 4.7.3  **性能**

- 客户端 HE 解密需加载 KEK(sm2) 私钥解信封（PBKDF2 HMAC_CTX 复用优化后，KEK 加载约 6ms/次，见 4.6.6）。

### 4.7.4  **输入项**

| 输入项 | 说明 |
|---|---|
| 同态 DEK | he-add / he-mul DEK（key_algo、绑定的非对称 KEK）|
| KEK(sm2) | 公钥（入库 hg_kek_args.PUBLIC_KEY）+ 私钥（软加密 .priv 文件 / 硬加密密码机）|
| 绑定元数据 | hg_encrypted_column_args（he_add_dek / he_mul_dek）|

### 4.7.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 信封密文 | HE 私钥经 SM2 公钥信封加密后的 hex（he_ec_privkey / he_eg_privkey）|
| 解密依赖 | 客户端持 KEK(sm2) 私钥解信封获 HE 私钥 |

### 4.7.6  **算法**

信封加密：HE 私钥用 KEK(sm2) 公钥做 SM2 非对称加密（公钥加密、私钥解密分工，见 7.3）；解密侧软加密本地 .priv 文件、硬加密密码机内私钥（私钥永不出设备）。

### 4.7.7  **流程逻辑**

见第 7 章密钥管理模块详细设计。

### 4.7.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 4 章对应（V5-AD-1-7）。

2）方法：客户端密钥管理器加载 HE 私钥（解信封）；服务端运算加载 HE 公钥（缓存）。

3）接口说明：依赖密钥管理模块（V5-DD-4）的接口，详见第 7 章。

4）接口参数：DEK 分布式身份标识、KEK(sm2) 私钥/公钥、HE 密钥对材料。

### 4.7.9  **存储分配**

无独立存储分配，依赖 hg_dek_args（HE 密钥对材料）与 hg_kek_args（SM2 公钥）。

### 4.7.10  **注释设计**

依赖关系与调用链在密钥管理模块注释中说明。

### 4.7.11  **限制条件**

- 同态 DEK 必须绑定非对称 KEK（key_algo='sm2'），对称 KEK 无公钥无法做信封加密，创建时校验报错；
- HE 解密依赖客户端持有 KEK(sm2) 私钥，私钥缺失时返回密文（不报错）。

## 6.1  **V5-DD-3-1**  **\copy 子查询导出与 BINARY 格式**

### 6.1.1  **程序描述**

\copy 是 psql 客户端元命令，数据在客户端本地处理：导出时密态列输出明文，导入时明文经客户端加密后发送服务端。V4.0.0 已交付 \copy 的 TEXT、CSV 格式，本子模块在既有能力之上新增 **BINARY 格式**与**子查询导出**两项能力，加解密挂在 libpq 协议层（COPY IN 在 PQputCopyData 出口加密、COPY OUT 在 pqGetCopyData3 出口解密），psql 无需额外处理密态数据。

### 6.1.2  **功能**

| 能力 | V4.0.0（已交付） | V4.0.1（本模块） |
|---|---|---|
| \copy 表导出/导入（TEXT 格式）| 支持（加密列明文输出）| 保持 |
| \copy 表导出/导入（CSV 格式）| 支持 | 保持 |
| \copy 表导出/导入（BINARY 格式）| 不支持 | 新增 |
| \copy (SELECT ...) TO 子查询导出 | 不支持 | 新增 |

- 客户端 \copy 与服务端 COPY 相互独立：客户端 \copy 导出时加密列输出明文，服务端 COPY 导出时输出密文；
- BINARY 格式遵循 PG 原生二进制 COPY 协议（PGCOPY 签名 + 标志区 + 扩展区 + 字段长度头 + NULL 标记）；
- 子查询导出复用前端 SELECT 处理链路识别加密列，导出时对查询结果按列解密。

### 6.1.3  **性能**

- BINARY 模式按字段长度头定位边界，免去 TEXT/CSV 的行文本解析，批量导入导出性能与原生接近；
- 子查询导出对结果集内所有加密列解密（多表 JOIN 场景亦然），无额外解密开销。

### 6.1.4  **输入项**

| 输入项 | 说明 |
|---|---|
| \copy 命令 | \copy 表 TO/FROM 'file' [WITH (FORMAT BINARY)]、\copy (SELECT ...) TO 'file' |
| COPY 数据流 | 二进制字段流（PGCOPY 头 19 字节 + 字段长度头 + 数据）或文本行 |
| 列元数据 | 目标表/子查询结果列的加密列映射（copy_column_mapping）|

### 6.1.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 导出文件 | 密态列明文（客户端 \copy）或密文（服务端 COPY），BINARY/TEXT/CSV 格式 |
| 导入结果 | 明文经客户端加密后写入服务端密文 |

### 6.1.6  **算法**

**BINARY 格式设计（协议遵循）**：\copy 的 BINARY 格式遵循 PG 原生二进制 COPY 协议（PGCOPY 签名 + 标志区 + 扩展区 + 字段长度头 + NULL 标记）。与 TEXT/CSV 的按行文本解析不同，BINARY 模式按字段长度头定位边界，密态列密文以二进制形态随流传输，客户端按列元数据完成解密/加密。

| 场景 | 说明 |
|---|---|
| 类型覆盖 | 全 9 种密态类型（int2/int4/int8/float4/float8/numeric/varchar/bpchar/text 的 _enc 变体）|
| 混合列 | 加密列与非加密列混合的表 |
| 边界值 | INT2/INT4/INT8 上下限、浮点精度边界、Numeric 精度、特殊字符 |
| NULL 值 | 全 NULL、部分 NULL、首列 NULL、末列 NULL 等组合 |
| 数据一致性 | BINARY 导出后再导入（roundtrip）数据保持一致 |

处理要点：导出（TO）密态列密文解析为明文后按目标类型序列化为二进制字段；导入（FROM）明文按源列类型解析、加密后编码为二进制字段；NULL 值按二进制协议 NULL 标记处理，不参与加解密；密文在二进制流内部以明文长度头界定，客户端按列映射定位密态列槽位。

**子查询导出设计**：\copy (SELECT ...) TO 'filename' 复用前端 SELECT 处理链路识别加密列（前端解析器将 COPY 解析为 CopyStmt，从子查询 FROM 提取表名并建立"结果列→原表列"映射）：

| 子查询场景 | 行为 |
|---|---|
| 单表 SELECT * | 全部加密列解密导出 |
| 单表显式列 / 单列 | 对应加密列解密导出 |
| 单表非加密列 | 原样导出 |
| 多表 JOIN | 结果集内加密列全部解密导出 |
| 聚合函数（COUNT(*) 等）| 聚合结果为非密文值，原样导出 |
| GROUP BY 加密列 | 分组键加密列解密导出，聚合值原样导出 |

### 6.1.7  **流程逻辑**

```
\copy (SELECT ...) TO 'file' [BINARY]
    │
    ▼
psql parse_slash_copy：解析子查询/表名、BINARY 关键字、选项
    │
    ▼
tecc_preprocess_copy：前端解析器解析 CopyStmt → 提取 FROM 表名 → 建立列映射
    │
    ▼
服务端 COPY 执行（BINARY 按 PGCOPY 协议传输）
    │
    ▼
COPY OUT：pqGetCopyData3 → tecc_process_copy_result（按列映射解密加密列）→ 输出明文到文件
COPY IN ：PQputCopyData → tecc_process_copy_data（按列映射加密明文列）→ 密文写入服务端
```

### 6.1.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 6 章对应（V5-AD-3-1）。

2）方法：psql copy.c（parse_slash_copy、tecc_preprocess_copy）；libpq fe-tecc-copy.c（tecc_preprocess_copy、tecc_process_copy_data、tecc_process_copy_result、tecc_copy_parse_binary_row、tecc_copy_format_binary_row）；fe-exec.c（PQputCopyData 出口加密）、fe-protocol3.c（pqGetCopyData3 出口解密）。

3）接口说明：加解密挂在 libpq 协议层，覆盖 COPY 协议；psql 无需额外处理密态数据。

4）接口参数：COPY 数据流、列映射（copy_column_mapping）、列元数据。

### 6.1.9  **存储分配**

- 行缓冲区：BINARY 模式按行解析/重组，字段长度头定位，无整文件缓存；
- 列映射内存：按结果列数分配（子查询场景）。

### 6.1.10  **注释设计**

COPY 协议加解密挂接点、BINARY 行解析/格式化（PGCOPY 头、网络序转换）以 `/* ReqID:TECC4.0 */` 注释标注。

### 6.1.11  **限制条件**

- 子查询中加密列仅支持解密输出，不支持在子查询内对密文做运算（与直接查询行为一致）；
- 多表 JOIN 场景结果集内加密列全部解密导出（与需求约定一致）；
- BINARY 模式按列类型严格解析，类型不匹配时报错；
- 客户端 \copy 与服务端 COPY 行为相互独立，互不影响。

### 6.1.12  **测试计划**

- BINARY roundtrip：全 9 种密态类型 + 混合列 + 边界值 + NULL 组合（全 NULL、部分 NULL、首/末列 NULL），导出再导入数据一致；

- 客户端/服务端独立性：\copy 导出明文 vs COPY 导出密文对比；
- 异常：BINARY 流解析失败（签名错误、字段长度越界）报错终止、解密失败按行报错可回滚。

## 6.2  **V5-DD-3-2**  **pg_dump 导出 KEK/DEK 与跨平台恢复**

### 6.2.1  **程序描述**

pg_dump 将 KEK/DEK 创建语句导出到备份文件，pg_restore 还原时可重建密钥元数据，并支持跨平台恢复（V4.0.1-20-3-10 / V4.0.1-20-3-23）。导出能力已实现（dumpKek/dumpDek），**一列多 DEK 绑定元数据（hg_encrypted_column_args）当前未纳入导出**，需补充（见 6.2.13 与 14.1）。

### 6.2.2  **功能**

- 导出范围：KEK（key_store、key_algo、key_path、public_key）；对称 DEK（kek 引用、key_algo、encrypted_value、key_length）；同态 DEK（kek 引用、key_algo、HE 密钥对材料 he_ec_pubkey/he_ec_privkey/he_eg_pubkey/he_eg_privkey）；
- 导出语句结构：每个 KEK/DEK 对象导出 DROP + CREATE 语句对，pg_restore 按对象依赖顺序执行重建（PRE_DATA section，先 KEK 后 DEK）；
- 语句均带 `_tecc_processed = 'on'` 标记，还原时前端处理器跳过重复加密/改写；
- 密态列定义导出：CREATE TABLE 语句含 ENCRYPTED WITH (DEK=..., SUPPORT_ALGO=...)（getTableAttrs 联接 hg_encrypted_columns/hg_dek，dumpTableSchema 输出）；
- 跨平台恢复：还原时经 libpq TECC 处理器用 TECC_KEK_PATH 重定向密钥文件目录（create_kek_processor.c），屏蔽平台路径差异；
- 密钥文件不在备份范围内，仅导出元数据，需单独备份。

### 6.2.3  **性能**

导出/还原为离线操作，无性能指标要求；还原按依赖顺序批量执行。

### 6.2.4  **输入项**

| 输入项 | 说明 |
|---|---|
| 系统表 | hg_kek、hg_dek、hg_kek_args、hg_dek_args（+ 待补充的 hg_encrypted_column_args）|
| 密钥文件 | .key（对称 KEK）、.priv+.pub（非对称 KEK），还原前需在目标机器放置 |
| TECC_KEK_PATH | 目标机器环境变量，跨平台还原时替代 key_path 目录部分 |

### 6.2.5  **输出项**

| 输出项 | 说明 |
|---|---|
| dump 文件 | CREATE KEK / CREATE DEK 语句（DROP + CREATE 对，PRE_DATA section，含 _tecc_processed 标记）|
| 还原结果 | pg_restore 重建 KEK/DEK 元数据（含 HE 密钥对材料），密态列定义 |

### 6.2.6  **算法**

**导出结构**：

- CREATE KEK：输出 key_store / key_algo / key_path / public_key 参数，还原时前端解析后重新校验并入库；
- CREATE DEK WITH VALUES：输出 kek / key_algo / key_length / encrypted_value（对称）/ HE 密钥对材料（同态），还原时生成/重建元数据记录。

**还原流程**：pg_restore 按依赖顺序重建 DEK/KEK 元数据；还原前需在目标机器放置对应 .key 文件（对称 KEK）或 .priv 文件（非对称 KEK，且需同时存在同名 .pub 公钥文件——CREATE KEK 还原时从 .priv 同目录加载 .pub 入库）；密钥文件缺失或校验失败时还原报错，事务内可回滚。

**跨平台恢复**：导出的 key_path 仅用于运行时定位密钥文件名；跨平台还原时在目标机器设置 TECC_KEK_PATH 环境变量指向密钥文件所在目录，由 TECC_KEK_PATH 替代 key_path 中的目录部分定位密钥文件，屏蔽不同平台路径格式差异（如 Windows 盘符与 Linux 挂载点）；未设置 TECC_KEK_PATH 时按 key_path 原始路径查找，失败报错。

### 6.2.7  **流程逻辑**

```
pg_dump：getKekInfo/getDekInfo 读取系统表 → dumpKek/dumpDek 生成 DROP+CREATE 语句
    → PRE_DATA section（先 KEK 后 DEK）→ dump 文件
pg_restore：按依赖顺序执行 → CREATE KEK（前端处理器经 TECC_KEK_PATH 定位密钥文件、加载 .pub 入库）
    → CREATE DEK（重建对称/同态 DEK 元数据）→ 密态列定义
```

### 6.2.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 6 章对应（V5-AD-3-2）。

2）方法：pg_dump.c（getKekInfo:5728、getDekInfo:5856、dumpKek:14654、dumpDek:14738、DO_KEK/DO_DEK 对象类型、PRE_DATA section）；libpq create_kek_processor.c（TECC_KEK_PATH 重定向：302-318、567-601）。

3）接口说明：导出语句带 `_tecc_processed='on'` 标记，pg_restore 还原时前端处理器跳过重复加密/改写。

4）接口参数：KEK/DEK 元数据字段、密钥文件路径、_tecc_processed 标记。

### 6.2.9  **存储分配**

导出语句文本按对象数分配（dump 文件）；无运行期持久化结构。

### 6.2.10  **注释设计**

dumpKek/dumpDek 生成语句结构、PRE_DATA 排序、_tecc_processed 标记以 `/* ReqID:TECC4.0 */` 注释标注。

### 6.2.11  **限制条件**

- 密文数据随普通 pg_dump 数据导出（密态列在库内为密文存储，导出/导入不改变其形态）；

# 7  **V5-DD-4**  **密钥管理模块**

对应需求 4.5.1"安全性-密钥管理"：在 V4.0.0 两级密钥（KEK/DEK）体系上引入非对称密钥体系，覆盖密钥算法参数、一列多 DEK 绑定、HE 密钥对生成与存储、分布式身份标识、KEK 密钥轮换与 tecc_ktool 工具设计，支撑同态加密与密钥生命周期管理（V4.0.1-20-3-16 / 17 / 18）。

## 7.1  **V5-DD-4-1**  **密钥算法参数（key_algo）设计**

### 7.1.1  **程序描述**

KEK 与 DEK 统一使用 key_algo 参数指定密钥算法，以"对称/非对称、用途"为语义划分，便于后续扩展新算法（如 rsa、aes、paillier 等）。本子模块定义 key_algo 取值、密钥材料与保护对象，支撑对称加密与同态加密的密钥体系。

### 7.1.2  **功能**

- KEK 的 key_algo：sm4（默认，对称）、sm2（非对称 SM2 密钥对）；
- DEK 的 key_algo：sm4（默认，对称）、he-add（EC-ElGamal 密钥对）、he-mul（有限域 ElGamal 密钥对）；
- 同态 DEK 按算法独立生成密钥对，he-add 与 he-mul 各是各的、互不混用；
- 绑定约束校验：传统 DEK（sm4）绑定对称 KEK（sm4）；同态 DEK（he-add/he-mul）绑定非对称 KEK（sm2，信封加密需要公钥），创建时校验。

### 7.1.3  **性能**

无独立性能要求；密钥材料加载性能见 4.6（PBKDF2 HMAC_CTX 复用优化）。

### 7.1.4  **输入项**

| 输入项 | 说明 |
|---|---|
| CREATE KEK 选项 | KEY_STORE、KEY_ALGO（sm4|sm2）、KEY_PATH |
| CREATE DEK 选项 | KEK 引用、KEY_ALGO（sm4|he-add|he-mul）|

### 7.1.5  **输出项**

| 输出项 | 说明 |
|---|---|
| KEK 元数据 | hg_kek + hg_kek_args（key_path、key_algo、public_key 等）|
| DEK 元数据 | hg_dek + hg_dek_args（encrypted_value、HE 密钥对材料等）|

### 7.1.6  **算法**

**KEK（密钥加密密钥，仅用于信封加密保护 DEK）：**

| key_algo | 算法 | 密钥材料 | 保护对象 |
|---|---|---|---|
| sm4（默认）| SM4 对称 | 32B 随机密钥（MEK 加密存 .key 文件）| 传统 DEK 密文（encrypted_value）|
| sm2 | SM2 非对称密钥对 | SM2 密钥对（localkms：私钥 MEK 加密存 .priv、公钥入库；swxakms/tzwykms：密钥对托管密码机、公钥导出后入库）| HE DEK 私钥（SM2 公钥信封加密）|

**DEK（数据加密密钥）：**

| key_algo | 算法 | 密钥材料 | 服务算法 |
|---|---|---|---|
| sm4（默认）| SM4 对称 | 32B 随机密钥（KEK 加密存 encrypted_value）| DET/OPE/SEARCH/RND |
| he-add | EC-ElGamal | EC-ElGamal 密钥对（P-256）| he-add（加减法、SUM、标量）|
| he-mul | ElGamal | 有限域 ElGamal 密钥对（RFC 5114 2048-bit）| he-mul（乘法、幂）|

### 7.1.7  **流程逻辑**


## 7.2  **V5-DD-4-2**  **一列多 DEK 绑定**

### 7.2.1  **程序描述**

同一密态列可同时绑定对称 DEK 与同态 DEK（he-add/he-mul），绑定关系独立存储、独立管理。绑定关系采用 args 扩展表模式存储，新增系统表 hg_encrypted_column_args（V4.0.1 仅新增此表，V4.0.0 无此表数据，pg_upgrade 无历史数据冲突）。

### 7.2.2  **功能**

- 建表语法：ENCRYPTED WITH (DEK=对称DEK, HE_ADD_DEK=he-add DEK, HE_MUL_DEK=he-mul DEK, SUPPORT_ALGO='...')；
- 多 DEK 校验（双层）：前端校验 SUPPORT_ALGO 与 DEK 参数匹配、DEK 的 key_algo 与算法一致；后端权威校验 DEK 存在性、key_algo 匹配、USAGE 权限；
- 绑定元数据存储：hg_encrypted_column_args（column_id + key + value，value 为 DEK 分布式身份标识）；
- 生命周期管理：建列同一事务写入 args；删列/删表/删 DEK 经依赖机制级联清理；
- 元数据视图：hg_encrypted_columns_info 扩展 he_add_dek、he_mul_dek 列（关联 args → hg_dek 解析 DEK 名称与分布式 ID）；
- 单 DEK 兼容模式：列仅配置一个 DEK 时不写 args，DEK 由 hg_encrypted_columns.column_key_id 承载（V4.0.0 兼容）。

### 7.2.3  **性能**

客户端列缓存一次查询获取全部 DEK 绑定（hg_encrypted_columns_info），无需额外表访问。

### 7.2.4  **输入项**

| 输入项 | 说明 |
|---|---|
| 建表语句 | ENCRYPTED WITH（DEK/HE_ADD_DEK/HE_MUL_DEK/SUPPORT_ALGO）|
| DEK 元数据 | 各 DEK 的 key_algo、分布式身份标识、USAGE 权限 |

### 7.2.5  **输出项**

| 输出项 | 说明 |
|---|---|
| hg_encrypted_column_args 记录 | column_id + key（he_add_dek/he_mul_dek）+ value（DEK 分布式身份标识）|
| 客户端列缓存 | he_add_dek / he_mul_dek 分布式 ID |

### 7.2.6  **算法**

建表校验规则汇总（对应需求 V4.0.1-20-3-3）：

| SUPPORT_ALGO 配置 | 必选 DEK 参数 | key_algo 要求 |
|---|---|---|
| 含 DET/OPE/SEARCH/RND 任一对称算法 | DEK | 'sm4' |
| 含 he-add | HE_ADD_DEK | 'he-add' |
| 含 he-mul | HE_MUL_DEK | 'he-mul' |
| 未配置的算法 | 对应 DEK 参数可省略 | — |

- 所有指定 DEK 必须存在且当前用户对其具有 USAGE 权限，否则报错；
- 同态 DEK（he-add/he-mul）必须绑定非对称 KEK（key_algo='sm2'），对称 DEK 绑定对称 KEK 或非对称 KEK 均可。

多 DEK 绑定元数据存储（hg_encrypted_column_args）：

| 字段 | 说明 |
|---|---|
| oid | 记录 OID |
| column_id | 引用 hg_encrypted_columns.oid |
| function_name | 算法类型标识 |
| key | 'he_add_dek' / 'he_mul_dek' |
| value | DEK 分布式身份标识（4B int4）|

唯一索引：column_id + key；辅助索引：oid；挂 toast 与依赖清理机制。

采用 args 扩展表而非直接给 hg_encrypted_columns 加字段的原因：hg_encrypted_columns 为系统表，加字段需变更 bki 表结构，影响 V4.0.0→V4.0.1 的 pg_upgrade（文件级拷贝系统表时新旧结构不匹配，且系统表 ALTER TABLE 受 PG 限制）；新增 args 表在新库初始化时建空表，pg_upgrade 无历史数据与结构冲突；未来扩展只需新增 key 条目，不动表结构。

关联与取值规则：column_id 引用 hg_encrypted_columns.oid（与 hg_dek_args.dek_id 引用 hg_dek.oid 的关联模式一致）；value 存储 DEK 的 column_key_distributed_id（跨实例确定性一致，与密文段内嵌 DEK 身份标识同一体系，见 7.4），不使用实例内 hg_dek.oid；单 DEK 模式不写 args，DEK 由 column_key_id 承载。

## 7.3  **V5-DD-4-3**  **密钥存储与保护**

### 7.3.1  **程序描述**

本子模块设计 HE 密钥对的存储与保护、KEK(sm2) 公钥入库路径与 HE 私钥信封的加解密路径，遵循"服务端零信任"安全模型：服务端仅存储 HE 公钥明文与信封密文，不接触私钥明文。

### 7.3.2  **功能**

- HE 密钥对存储（hg_dek_args）：he_ec_pubkey/he_eg_pubkey 公钥明文（可公开）；he_ec_privkey/he_eg_privkey 私钥信封密文（KEK(sm2) 公钥 SM2 信封加密）；
- KEK(sm2) 公钥入库（前端传递，后端不读文件）：软加密从 key_path 同目录 .pub 文件读取 65 字节未压缩点（04‖x‖y）；硬加密调用密码机导出公钥接口，统一为 65 字节未压缩点；前端将公钥 hex 注入 CREATE KEK 语句 public_key 参数，服务端解析后以 65 字节二进制存入 hg_kek_args.PUBLIC_KEY；
- HE 私钥信封加解密：公钥加密（CREATE DEK / ALTER KEK 重信封，客户端本地）、私钥解密（查询时解 HE 私钥，localkms 本地 .priv 文件 / 硬加密密码机内私钥，私钥永不出设备）；
- 公钥入库的收益：任何持有该 KEK USAGE 权限的客户端均可从服务端读取 PUBLIC_KEY 创建 HE DEK，无需本地持有 KEK 私钥文件或访问密码机（多客户端协同创建 HE DEK 的基础）。

### 7.3.3  **性能**

信封加解密为创建/轮换/查询路径开销：软加密本地 SM2 运算；硬加密由密码机 SDF 接口完成（SDF_ExternalEncrypt_ECC / SDF_InternalDecrypt_ECC）。

### 7.3.4  **输入项**

| 输入项 | 说明 |
|---|---|
| HE 密钥对 | EC-ElGamal / FF-ElGamal 公钥与私钥 |
| KEK(sm2) 公钥 | 65 字节未压缩点（入库 hg_kek_args.PUBLIC_KEY）|
| KEK(sm2) 私钥 | 软加密 .priv 文件 / 硬加密密码机内 |

### 7.3.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 信封密文 | HE 私钥 SM2 信封加密 hex（he_ec_privkey / he_eg_privkey）|
| HE 私钥明文 | 客户端查询时解信封获得，仅前端内存使用 |

### 7.3.6  **算法**

**HE 密钥对存储（hg_dek_args）：**

| 键 | 内容 | 保护 |
|---|---|---|
| he_ec_pubkey / he_eg_pubkey | HE 公钥（明文 hex）| 可公开 |
| he_ec_privkey / he_eg_privkey | HE 私钥（信封加密 hex）| KEK(sm2) 公钥 SM2 信封加密 |

**KEK(sm2) 公钥的入库路径（前端传递，后端不读文件）：** HE DEK 创建（信封加密）与查询解密（信封解密）分别依赖 KEK(sm2) 公钥与私钥，公钥在 CREATE KEK 时入库 hg_kek_args.PUBLIC_KEY。key_path 是客户端密钥文件路径，服务端无法读取（客户端与服务端分离部署时更是如此），故公钥由前端 libpq 处理器在 CREATE KEK 时获取并经 SQL 改写传递，服务端不读文件：
- 软加密（localkms）：前端从 key_path 同目录的 .pub 文件读取 65 字节未压缩点（04‖x‖y）；
- 硬加密（tzwykms/swxakms）：前端调用密码机导出公钥接口，返回原始点（bits‖x‖y），剥离长度前缀并补 04 前缀，统一为 65 字节未压缩点；
- 前端将公钥 hex 注入 CREATE KEK 语句的 public_key 参数（与 _tecc_processed 标记一并注入），服务端解析 public_key 参数后以 65 字节二进制存入 PUBLIC_KEY；后端不再读 key_path 文件，消除"客户端服务端同机"的隐含依赖。

**HE 私钥信封的加解密路径：**

| 操作 | 使用的密钥 | 执行位置 |
|---|---|---|
| 信封加密（CREATE DEK / ALTER KEK 重信封）| SM2 公钥 | 客户端本地（公钥已入库，公开无害）|
| 信封解密（查询时解 HE 私钥）| SM2 私钥 | localkms：本地 .priv 文件；swxakms/tzwykms：密码机内（私钥永不出设备）|

"公钥本地加密、私钥设备内解密"是非对称密码学在硬加密（HSM）场景下的标准通行做法——国密 SDF 接口的 SDF_ExternalEncrypt_ECC（外部公钥加密）与 SDF_InternalDecrypt_ECC（内部私钥解密）、PKCS#11 的 C_Encrypt/C_Decrypt 均按此分工设计，TLS、云 KMS 信封加密等业界实践与之同构；公钥本身设计为公开材料，导出到客户端加密不引入安全损失；私钥始终不出密码机（硬加密的核心安全模型），故解密必须由密码机完成；该分工使 HE 加密侧摆脱设备在线依赖（CREATE DEK 无需设备即可信封加密），仅解密侧依赖密码机。

### 7.3.7  **流程逻辑**

```
CREATE KEK(sm2)：tecc_ktool 生成 .priv/.pub → 前端读 .pub（或密码机导出公钥）→ 公钥 hex 注入 public_key 参数
    → 服务端解析存入 hg_kek_args.PUBLIC_KEY
CREATE DEK(he-add/he-mul)：生成 HE 密钥对 → 公钥明文入库 → 私钥用 KEK(sm2) 公钥信封加密入库
查询解密：客户端读密文段内 DEK 身份 → 加载 KEK(sm2) 私钥（本地 .priv 或密码机）→ 解 HE 私钥信封 → HE 私钥解密
```

### 7.3.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 7 章对应（V5-AD-4-3）。

2）方法：前端 create_kek_processor（公钥加载注入）、create_dek_processor（信封加密）、密钥管理器（信封解密）；软加密 tecc_sm2_envelope_decrypt、硬加密密码机 SDF 接口。

## 7.5  **V5-DD-4-5**  **KEK 密钥轮换（ALTER KEK）**

### 7.5.1  **程序描述**

ALTER KEK 由前端（libpq 处理器）执行 DEK 重加密后改写 SQL 完成，服务端兜底校验权限与参数（V4.0.1-20-3-18）。轮换支持对称 KEK（sm4）与非对称 KEK（sm2）两类，覆盖软加密（localkms）与硬加密（tzwykms/swxakms），满足等保与合规要求。

### 7.5.2  **功能**

- 对称 KEK 轮换：加载旧/新 KEK，用旧 KEK 解密关联传统 DEK（encrypted_value）再用新 KEK 重新加密；
- 非对称 KEK 轮换：使用新 KEK(sm2) 公钥重新对关联 HE DEK 的私钥做信封加密（he_ec_privkey/he_eg_privkey），新公钥由新私钥 DER 派生一次（硬加密从密码机导出公钥）；对称 DEK 的 encrypted_value 改用新公钥 SM2 信封；
- 一列多 DEK：轮换对该 KEK 关联的所有 DEK（含一列多 DEK 场景下绑定的对称 DEK 与各 HE 算法 DEK）分别重加密，DEK 明文不变、已加密数据无需重加密；
- 批量更新 hg_dek_args（同一事务），失败可回滚；
- 轮换完成后清除连接级缓存（tecc_cache 与 key_manager 的 DEK 明文缓存）并重载 KEK 元数据；
- 在线轮换：各连接独立缓存，轮换期间及完成后其它连接基于自身缓存继续加解密不受影响；
- 权限校验：仅 KEK 所有者或具有相应权限的用户可执行，过程对应用透明；
- 服务端 ALTER KEK 校验 ACL_UPDATE 权限与参数合法性（KEY_PATH 必填），并更新 KEK 的 KEY_PATH 元数据。

### 7.5.3  **性能**

在线轮换不中断业务；重加密在客户端完成（批量 UPDATE hg_dek_args 同一事务）。

### 7.5.4  **输入项**

| 输入项 | 说明 |
|---|---|
| ALTER KEK 语句 | ALTER KEK kek [WITH (KEY_PATH='...')] |
| 新 KEK | 软加密：tecc_ktool 生成的新密钥文件；硬加密：密码机新密钥索引 'hsm:id=<索引>' |
| 旧 KEK | 现有 KEK（软加密读密钥文件、硬加密按 HSM_KEY/SWXAKEY 标记复用）|

### 7.5.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 重加密 DEK 元数据 | hg_dek_args 更新（encrypted_value / he_ec_privkey / he_eg_privkey）|
| KEK 元数据 | hg_kek_args.KEY_PATH / PUBLIC_KEY 更新 |
| 改写后 SQL | 原 ALTER KEK + _tecc_processed 标记 + 批量 UPDATE 追加语句 |

### 7.5.6  **算法**

- 对称 KEK 轮换：加载旧/新 KEK（软加密读取密钥文件、硬加密按新 KEY_PATH='hsm:id=<索引>' 构造 16 字节 placeholder 并复用 HSM_KEY/SWXAKEY 标记），用旧 KEK 解密关联传统 DEK（encrypted_value）再用新 KEK 重新加密——软加密走本地 SM4-CBC+HMAC、硬加密由密码机内对称 KEK 加解密；
- 非对称 KEK 轮换：使用新 KEK(sm2) 公钥重新对关联 HE DEK 的私钥做信封加密（he_ec_privkey/he_eg_privkey），新公钥由新私钥 DER 派生一次（硬加密从密码机导出公钥）；轮换遵循 7.3 的加解密分工——旧 KEK 私钥解 HE 私钥信封（软加密本地 tecc_sm2_envelope_decrypt、硬加密由密码机内 SM2 私钥 sm2_decrypt 解密、私钥不出境）、新 KEK 公钥重信封（本地），对应用透明；
- 轮换在客户端完成旧 DEK 解密、新 KEK 重加密、批量更新 hg_dek_args（同一事务），失败可回滚；
- 轮换完成后前端清除连接级缓存（tecc_cache 与 key_manager 的 DEK 明文缓存）并重载 KEK 元数据，避免同连接继续使用旧 KEK 解密新 encrypted_value。

### 7.5.7  **流程逻辑**

```
ALTER KEK kek WITH (KEY_PATH='new') ─► 前端加载旧 KEK / 新 KEK ─► 查 KEK is_asym 与关联 DEK 列表
    ─► 逐 DEK 重加密（对称：旧 KEK 解密 + 新 KEK 重加密；非对称：旧 SM2 私钥解 HE 私钥信封 + 新公钥重信封）
    ─► 更新 hg_kek_args.PUBLIC_KEY ─► 改写 SQL（原语句 + _tecc_processed + 批量 UPDATE）─► 服务端校验并执行
    ─► 清除连接级缓存并重载
```

### 7.5.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 7 章对应（V5-AD-4-5）。

2）方法：前端 stmt_processor.c（tecc_stmt_processor_process_alter_kek，:5976）；服务端 createkek.c（AlterKekCmd，:762）。

3）接口说明：重加密在客户端 libpq 完成（密钥材料不出客户端），后端做权威校验与 KEY_PATH 更新。

4）接口参数：KEK 名称、新 KEY_PATH、关联 DEK 列表、重加密结果。

### 7.5.9  **存储分配**

重加密中间缓冲（DEK 明文/密文、信封密文）仅客户端内存，随事务管理；无新增持久化结构。

### 7.5.10  **注释设计**

对称/非对称轮换分支、HSM placeholder、HE 私钥重信封、缓存清理以 `/* ReqID:TECC4.0 */` 注释标注。

### 7.5.11  **限制条件**

- 轮换仅 KEK 所有者或具有相应权限的用户可执行；
- 软加密（localkms）下轮换后解密需使用新 KEK 私钥文件：KEK 所有者所在客户端更新本地新私钥文件（.priv）即可继续解密；其它持有私钥的客户端需手动同步新私钥文件（或接入对应密码机），未同步前仅可写不可读；
- 轮换失败可回滚（同一事务）；
- DEK 明文不变、已加密业务数据无需重加密。

### 7.5.12  **测试计划**

- 对称轮换：sm4 KEK 轮换后传统 DEK 可解、密文数据不变；
- 非对称轮换：sm2 KEK 轮换后 HE 私钥信封重做、同态数据可解密、PUBLIC_KEY 更新；
- 硬加密：密码机内密钥轮换（swxa_alter_kek.sql）、并发轮换（swxa_concurrent.sql）；
- 权限：非所有者轮换报错；
- 一列多 DEK：轮换后各 DEK 绑定与解密正常；
- 缓存：轮换后同连接新查询用新 KEK 解密成功。

### 7.5.13  **尚未解决的问题**

无。

## 7.6  **V5-DD-4-6**  **V4.0.0 兼容策略**

### 7.6.1  **程序描述**

## 7.7  **V5-DD-4-7**  **tecc_ktool 软加密密钥生成工具**

### 7.7.1  **程序描述**

tecc_ktool 是独立的离线 KEK 文件管理 CLI 工具，不依赖数据库连接，仅管理软加密（localkms）的本地密钥文件，不涉及硬加密（tzwykms/swxakms）密码机；支持 Linux 和 Windows 平台（V4.0.1-20-3-16）。

### 7.7.2  **功能**

| 命令 | 参数 | 功能 |
|---|---|---|
| generate | --key-name、--key-algo <sm4\|sm2>、--key-path <目录>、[--force] | 生成 KEK 密钥文件 |
| list | [--dir <path>] | 扫描目录，展示 .key/.priv 文件列表（Name 列为文件名去扩展名）|
| info | --key-path <path> | 查看密钥文件元信息（类型、大小、创建时间、格式版本、.pub 存在性）|
| delete | --key-path <path> | 安全销毁密钥文件（4 遍覆写后删除）|
| validate | --key-path <path> | 校验密钥文件完整性（格式 + HMAC）|

与 SQL 命令的分工：

| 工具/命令 | 职责 | 依赖 |
|---|---|---|
| tecc_ktool | 线下生成/管理 KEK 密钥文件（.key/.priv/.pub），不碰数据库 | 无（离线）|
| CREATE KEK | 将 KEK 元数据注册至数据库，引用 tecc_ktool 生成的文件路径 | 数据库 + 密钥文件 |
| ALTER KEK | 在线 DEK 重加密轮换 | 数据库 + 新旧密钥文件 |

### 7.7.3  **性能**

密钥文件生成/校验为离线本地操作，无性能指标要求。

### 7.7.4  **输入项**

| 输入项 | 说明 |
|---|---|
| generate | --key-name（纯文件名，不含路径分隔符、不以 . 开头）、--key-algo（sm4|sm2）、--key-path（目录）、--force |
| list / info / delete / validate | --dir / --key-path |

### 7.7.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 密钥文件 | sm4：<key-name>.key；sm2：<key-name>.priv + <key-name>.pub |
| 参考语句 | generate 成功后输出对应 CREATE KEK 参考语句 |
| 列表/元信息/校验结果 | list 文件列表、info 元信息、validate 完整性结论 |

### 7.7.6  **算法**

文件生成与命名：

| key_algo | 生成文件 | 内容 |
|---|---|---|
| sm4（对称）| `<key-name>.key` | 32 字节随机密钥，MEK 加密存储 |
| sm2（非对称）| `<key-name>.priv` + `<key-name>.pub` | SM2 私钥 DER（MEK 加密）+ 公钥 65 字节未压缩点（明文）|

设计要点：
- 文件命名：--key-name 决定文件名基名，--key-path 指定生成目录（不存在自动创建，权限 0700）；
- key-name 校验：必须是纯文件名（不含路径分隔符、不以 . 开头、非 . 或 ..），防止路径穿越；
- 覆盖保护：目标文件已存在时 generate 默认报错拒绝覆盖（防止误覆盖已注册 KEK 导致关联 DEK 无法解密），确认需重新生成时加 --force 显式覆盖；
- generate 成功后输出对应的 CREATE KEK 参考语句，引导用户完成数据库注册。

密钥文件格式（TECCKEK v1 自描述格式）：

```
magic(7) + ver(1) + reserved(8) + algo_id(4) + salt(16) + iv(16)
+ SM4-CBC 密文 + HMAC-SHA256(32)
```

- 文件以固定 MEK（32 字节主密钥）加密：tecc_ktool 生成路径与运行时解密路径（kms_adapter）使用同一固定密钥，保证工具生成的文件运行时可直接解密，同时避免"MEK 轮换导致旧文件不可读"问题；
- 与库内密钥材料的层级区分：.key/.priv 文件是 MEK 保护的密钥文件；hg_dek 的 encrypted_value 是 KEK 保护的 DEK 密文；hg_dek_args 的 HE 私钥信封是 KEK(sm2) 公钥 SM2 加密，三层各自独立、互不混用。

安全设计：
- delete 采用 4 遍覆写（全零 → 全一 → 随机 → 全零）并逐遍 fsync 落盘后 unlink，防止密钥材料被普通文件恢复工具找回；删除 .priv 时提示 .pub 未被销毁（公钥可公开）；
- validate 校验文件最小长度、magic 与 HMAC-SHA256，检测文件损坏或被篡改；
- 权限收敛：工具为本地 CLI，仅操作指定目录文件，不提供网络接口；
- 与 CREATE KEK 的公钥入库配合：非对称 KEK 注册时由前端从 .priv 同目录加载 .pub 文件（65 字节未压缩点）经 SQL 传递入库 hg_kek_args（详见 7.3 公钥入库路径设计）。

### 7.7.7  **流程逻辑**

```
generate：解析参数 → key-name/key-algo 校验 → 目标文件存在性检查（拒绝覆盖，--force 覆盖）
    → 生成密钥材料（sm4 随机 32B / sm2 密钥对）→ MEK 加密写盘 → 输出 CREATE KEK 参考语句
delete：4 遍覆写（全零→全一→随机→全零，逐遍 fsync）→ unlink
validate：最小长度 + magic + HMAC-SHA256 校验
```

### 7.7.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 7 章对应（V5-AD-4-7）。

2）方法：src/bin/tecc_ktool/（tecc_ktool.c main 分发、cmd_generate.c、cmd_list.c、cmd_info.c、cmd_delete.c、cmd_validate.c）。

3）接口说明：离线 CLI，与运行时 kms_adapter.c 共用固定 MEK 加密格式（TECCKEK v1）。

4）接口参数：命令名与选项（--key-name/--key-algo/--key-path/--force/--dir）。

### 7.7.9  **存储分配**

密钥文件（.key/.priv/.pub）按 key-path 目录落盘；工具运行期内存仅承载当前操作文件。

### 7.7.10  **注释设计**

MEK 加密格式、4 遍覆写、HMAC 校验、路径穿越防护以 `/* ReqID:TECC4.0 */` 注释标注；固定 MEK 一致性（与 kms_adapter MUST stay identical）加注释约定。

### 7.7.11  **限制条件**

- 仅管理软加密（localkms）本地密钥文件，不涉及硬加密密码机；

### 7.7.12  **测试计划**

# 8  **V5-DD-5**  **会话级加解密元命令模块**

`\enable hg_tecc.mode` / `\disable hg_tecc.mode` 会话级加解密控制用于满足调试、验收和运维场景（V4.0.1-20-3-11）：同一连接内，用户可临时关闭客户端结果解密，直接查看服务端返回的密文形态；恢复开启后业务查询继续透明返回明文。该能力仅改变当前 psql/libpq 会话的结果解密策略（客户端处理策略），不修改服务端数据、不影响其他连接。

## 8.1  **V5-DD-5-1**  **状态模型与处理流程**

### 8.1.1  **程序描述**

会话级开关控制当前连接的 TECC 客户端处理策略。状态保存在当前连接的 TECC 客户端状态对象 TeccState 中，由 TeccState.guc_params.tecc_mode 表示；hg_tecc.mode 本身不是服务端 GUC，不通过 SQL SET/SHOW/RESET 访问。关闭解密时仍保留 SQL 发送、密态列识别、常量加密、SQL 改写、错误处理等基础链路，避免绕过 TECC 元数据校验。

### 8.1.2  **功能**

- 状态模型：启用（默认，透明解密模式）/ 禁用（密文查看模式）；
- 关闭解密时保留 SQL 预处理链路（密态列识别、常量加密、SQL 改写）；
- 状态隔离在当前 PGconn 连接内，不持久化、不参与事务提交或回滚、不影响其他连接；
- 依赖连接已启用 TECC：未通过 enable_tecc=1 初始化时，元命令与 libpq 接口返回明确错误；
- psql 元命令与上层 libpq 接口共用同一套连接级状态与错误处理规则。

### 8.1.3  **性能**

开关切换无额外开销；禁用模式跳过结果解密，仅影响当前连接后续查询。

### 8.1.4  **输入项**

| 输入项 | 说明 |
|---|---|
| \enable hg_tecc.mode / \disable hg_tecc.mode | psql 元命令 |
| PQteccSetMode(conn, enabled) | libpq 接口调用 |
| 连接状态 | TeccState.guc_params.tecc_mode |

### 8.1.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 查询结果 | 启用：客户端解密后的明文；禁用：服务端返回的密文格式（十六进制表示）|

### 8.1.6  **算法**

状态模型：

| 状态 | 含义 | SQL 发送前处理 | 查询密态列结果 | 典型用途 |
|---|---|---|---|---|
| 启用 | 默认透明解密模式 | 执行密态列识别、常量加密和 SQL 改写 | 客户端解密后的明文 | 业务查询、回归测试明文断言 |
| 禁用 | 密文查看模式 | 仍执行密态列识别、常量加密和 SQL 改写（保留基础链路）| 服务端返回的密文格式（十六进制表示）| 排查密文段、验证导入导出、比较工具函数输出 |

状态保存在当前连接的 TeccState.guc_params.tecc_mode（沿用既有结构字段承载客户端状态，hg_tecc.mode 不是服务端 GUC，也不通过 SQL SET/SHOW/RESET 访问）。连接关闭后状态消失；新连接按连接参数、环境变量或 psql 启动选项重新初始化。该状态不写入数据库系统表，不参与事务提交和回滚。

连接参数 enable_tecc=1 负责在连接建立阶段启用并初始化 TECC 客户端能力；会话级开关只在已经初始化的 TECC 连接上动态控制当前 PGconn 后续查询是否执行结果解密。未启用 TECC 的普通连接不创建完整 TECC 状态，元命令和 libpq 接口应返回明确错误。

### 8.1.7  **流程逻辑**

```
用户输入 psql 会话元命令
    │
    ▼
psql 命令层识别 \enable/\disable hg_tecc.mode
    │
    ▼
调用 PQteccSetMode(conn, enabled)  ────── 上层应用也可直接调用该接口
    │
    ▼
libpq 更新当前 PGconn 的 TECC 会话加解密状态
    │
    ▼
后续查询进入 libpq TECC 处理链路
    │
    ├─ 模式启用：SQL 预处理阶段识别密态列、加密常量并改写 SQL；
    │          结果处理阶段按列元数据加载 DEK，客户端解密后返回明文
    │
    └─ 模式禁用：SQL 预处理阶段仍识别密态列、加密常量并改写 SQL（保留基础链路）；
               结果处理阶段跳过解密，应用侧接收服务端返回的密文格式（十六进制表示）
```

### 8.1.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 8 章对应（V5-AD-5-1）。

4）接口参数：PGconn、enabled（0/1）。

### 8.1.9  **存储分配**

### 8.1.10  **注释设计**

tecc_mode 语义、会话开关入口、结果解密跳过分支以 `/* ReqID:TECC4.0 */` 注释标注。

### 8.1.11  **限制条件**

## 11.1  **V5-DD-8-1**  **总体设计原则**

### 11.1.1  **程序描述**

三个维修性工具函数（tecc_enc_info、tecc_decrypt_raw、tecc_enc_ratio）的总体设计原则：权限收敛、类型收敛、输出可观察、不泄露密钥、与前端处理器配合。

### 11.1.2  **功能**

- 权限收敛：不额外限定超级用户；按 SQL 函数执行权限、源表/列 `SELECT` 权限、目标表整表 `SELECT` 权限和实际算法 DEK `USAGE` 权限分别控制；

## 11.3  **V5-DD-8-3**  **tecc_decrypt_raw 设计**

### 11.3.1  **程序描述**

tecc_decrypt_raw 是 libpq 前端伪函数，用于返回指定算法对应的原始明文字节 hex。第二个参数指定算法（rnd/det/ope/he_add/he_mul；search 不可逆并明确拒绝）。函数只接受“直接密态列引用 + 非空常量算法名”，要求当前会话 `hg_tecc_mode=on`，不做业务类型反规范化或文本格式化。

### 11.3.2  **功能**

| 输入算法名 | 目标段 | 未配置时行为 |
|---|---|---|
| rnd | 解密 RND 基础密文段 | 报错提示段不存在 |
| det | 解密 DET 确定性密文段 | 报错提示段不存在 |
| ope | 独立解密 OPE 段，返回归一化明文 hex | 报错提示段不存在 |
| search | 不支持恢复明文 | 直接报错 |
| he_add / he-add | 用对应 HE DEK 私钥解密 EC-ElGamal 段 | 报错提示段不存在 |
| he_mul / he-mul | 用对应 HE DEK 私钥解密有限域 ElGamal 段 | 报错提示段不存在 |

主要用于确认密态值能否使用指定算法的实际 DEK 恢复原始明文字节。查看各算法段是否存在、长度及密文内容时使用 `tecc_enc_info`。

### 11.3.3  **性能**

单值解析，无性能指标要求。

### 11.3.4  **输入项**

| 输入项 | 说明 |
|---|---|
| 密态值 | anyelement，仅接受直接密态列引用 |
| 算法名 | 非空 text 常量（rnd/det/ope/search/he_add/he_mul；兼容 he-add/he-mul）|

### 11.3.5  **输出项**

| 输出项 | 说明 |
|---|---|
| text | 指定算法对应的原始明文字节 hex；未配置载荷、无权限或不支持解密时报错 |

### 11.3.6  **算法**

libpq 预处理阶段校验会话模式、参数形态和源列密态元数据，将伪函数调用改写为源密态列投影；服务端按普通 `SELECT` 返回完整密文；客户端结果处理阶段抽取所需载荷，检查实际算法 DEK 的 `USAGE` 权限，加载密钥并解密为原始明文字节 hex。OPE 段独立解密，返回加密前归一化明文（非业务显示原文）；SEARCH 直接报不支持。

### 11.3.7  **流程逻辑**

```
检查 hg_tecc_mode → 校验“直接密态列 + 常量算法名” → 改写为源列投影
→ 服务端执行 SELECT → 客户端抽取载荷 → 检查实际 DEK USAGE
→ 客户端解密并返回明文 hex / 任一步失败则整条查询报错
```

### 11.3.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 11 章对应（V5-AD-8-3）。

2）方法：`stmt_processor.c` 负责识别和 SQL 改写，`tecc_processor.c` 负责结果载荷提取及 hex 替换，`tecc_crypto_scheduler.c` 负责权限检查与客户端解密；不在 `pg_proc.dat` 注册同名后端函数。

3）接口说明：返回解密后的原始明文字节 hex，不做业务类型格式化。

4）接口参数：密态值、算法名。

### 11.3.9  **存储分配**

查询预处理状态保存在连接级 `TeccState`；结果 hex 按解密后明文长度分配，无独立持久化。

### 11.3.10  **注释设计**

伪函数识别、改写、载荷抽取、DEK 权限检查和客户端解密以 `/* ReqID:TECC4.0 */` 注释标注。

### 11.3.11  **限制条件**

- `hg_tecc_mode=off` 时直接报错，不返回密文 hex；
- 普通列、常量、表达式或动态算法参数不接受；
- 未配置指定算法载荷、缺少源表/列 `SELECT` 权限或实际 DEK `USAGE` 权限时报错；
- SEARCH 不支持恢复原文；PREPARE ... AS 中不支持该伪函数；
- 返回原始明文字节 hex，不等同于普通 SELECT 的业务显示值。

### 11.3.12  **测试计划**

- RND、DET、OPE、HE_ADD、HE_MUL 返回明文 hex，OPE 返回归一化明文（与同值 RND 结果不同）；
- `hg_tecc_mode=off`、空算法名、SEARCH、未配置载荷和普通列入参均报错；
- 普通用户有源表 `SELECT` 但无实际 DEK `USAGE` 时拒绝，授权后可执行。

### 11.3.13  **尚未解决的问题**

## 11.4  **V5-DD-8-4**  **tecc_enc_ratio 设计**

### 11.4.1  **程序描述**

tecc_enc_ratio 按表定义和密态列元数据进行静态估算，不扫描真实表数据。函数输出密态列明细行和 TOTAL 汇总行，帮助用户在容量规划阶段评估密态算法组合带来的存储开销。

### 11.4.2  **功能**

- 输入：table_name（支持 schema.table 形式，解析为当前数据库普通表）、varlena_length（可选，默认 20 字节，必须大于 0）；
- 输出：密态列明细行（column_name、source_type/source_len、enc_type/algorithms、plain_size/enc_size/ratio）+ TOTAL 汇总行（total_plain_1m、total_enc_1m、overall_ratio）；
- 权限：调用者必须具有目标表的整表 `SELECT` 权限，仅有部分列权限时拒绝执行；不额外要求超级用户；
- 估算口径：定长类型用固定长度、变长类型优先 typmod 否则 varlena_length；密文按 CipherDataType 头部与已配置算法段估算；整表汇总考虑非密态列、tuple header、NULL bitmap、行指针和页面头；不纳入 TOAST、索引、FSM/VM、表膨胀、页碎片、压缩效果、真实数据分布。

### 11.4.3  **性能**

静态估算不扫描表数据，执行开销低。

### 11.4.4  **输入项**

| 参数 | 说明 | 默认值与约束 |
|---|---|---|
| table_name | 待估算表名，支持 schema.table 形式 | 必填，需解析为当前数据库普通表 |
| varlena_length | 变长类型估算长度 | 可选，默认 20 字节，必须大于 0 |

### 11.4.5  **输出项**

| 字段 | 说明 |
|---|---|
| column_name | 密态列名；汇总行为 TOTAL |
| source_type / source_len | 原始明文类型及估算长度 |
| enc_type / algorithms | 密态类型及算法组合 |
| plain_size / enc_size / ratio | 单值明文大小、密文大小和单列膨胀率 |
| total_plain_1m / total_enc_1m / overall_ratio | 100 万行规模下明文表、密态表估算大小和整表膨胀率 |

### 11.4.6  **算法**

估算口径：

| 项目 | 处理方式 |
|---|---|
| 定长类型 | 使用类型固定长度 |
| 变长类型 | 优先使用 typmod；无法确定时使用 varlena_length |
| 密文结构 | 按 CipherDataType 头部和已配置算法段估算 |
| 整表汇总 | 同时考虑非密态列、tuple header、NULL bitmap、行指针和页面头 |
| 不纳入范围 | TOAST、索引、FSM/VM、表膨胀、页碎片、压缩效果、真实数据分布 |

100 万行磁盘占用按 PostgreSQL heap page 结构估算；该函数的估算值用于方案设计和容量预估，不等同于实际磁盘文件大小。

### 11.4.7  **流程逻辑**

```
解析表名 → 检查目标表整表 SELECT 权限 → 查 hg_encrypted_columns 逐列估算明/密文大小 → 输出明细行 + TOTAL 汇总行
```

### 11.4.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 11 章对应（V5-AD-8-4）。

2）方法：`src/backend/utils/tecc/tecc_admin_funcs.c` 中的 `tecc_enc_ratio()`，由 `pg_proc.dat` 注册两个重载。

3）接口说明：静态估算，不扫描真实数据；要求目标表整表 `SELECT` 权限，不额外要求超级用户。

4）接口参数：table_name、varlena_length。

### 11.4.9  **存储分配**

setof record 按行返回，无独立持久化。

### 11.4.10  **注释设计**

估算口径与汇总逻辑以 `/* ReqID:TECC4.0 */` 注释标注。

### 11.4.11  **限制条件**

- 估算值用于方案设计和容量预估，不等同于实际磁盘文件大小；

### 11.5.5  **输出项**

|---|---|
| 处理结果 | 后端函数在服务端返回结构信息/估算结果；前端伪函数在客户端返回明文 hex |

### 11.5.6  **算法**

# 12  **V5-DD-9**  **内置函数适配模块**

对应需求 4.4.1.4"内置函数适配"（V4.0.1-20-3-6）。密态列上 PostgreSQL 内置函数的行为取决于列的加密算法能力：排序类函数依赖 OPE 密文保序比较，等值类函数依赖 DET/OPE 密文等值比较，算术类函数依赖同态加密（HE-ADD/HE-MUL）。本模块在 libpq 客户端查询预处理阶段对内置函数调用做算法能力校验，并对函数参数常量按函数语义加密，保证不支持的内置函数返回固定格式错误信息。

## 12.1  **V5-DD-9-1**  **总体设计与校验器**

### 12.1.1  **程序描述**

校验逻辑位于客户端 tecc_processor（stmt_processor.c / where_clause_processor.c），核心组件为聚合校验器、标量校验器与常量加密器，校验全部在查询预处理阶段完成，服务端零改动。

### 12.1.2  **功能**

- 客户端校验、服务端零改动：校验全部在 libpq tecc_processor 查询预处理阶段完成；
- 固定格式报错：不支持的内置函数统一返回含函数名与列名的 TECC 预处理错误，替代服务器端晦涩报错；
- 行为对齐需求矩阵：count/coalesce 无需算法；min/max/greatest/least 需 OPE；nullif/case 需 DET/OPE；sum 需 HE-ADD 且仅限整型；power 需 HE-MUL 且仅限整型；
- 零误报：校验失败必须阻断查询下发，且不得触发"SAFETY CHECK"类假阳性错误；元数据缺失时防御性放行。

### 12.1.3  **性能**

校验为查询预处理开销（函数分类 + 列元数据位掩码检查），无独立性能指标。

### 12.1.4  **输入项**

| 输入项 | 说明 |
|---|---|
| 查询语句 | SELECT 目标列 FuncCall、WHERE/HAVING 表达式 |
| 列元数据 | encryption_type 位掩码（DET 0x01 / OPE 0x02 / SEARCH 0x04 / HE-ADD 0x08 / HE-MUL 0x10）、original_type_oid |

### 12.1.5  **输出项**

| 输出项 | 说明 |
|---|---|
| 校验结果 | 放行（可改写下发）或固定格式错误（阻断下发）|

### 12.1.6  **算法**

核心组件：

| 组件 | 职责 |
|---|---|
| 聚合校验器 stmt_validate_aggregate_funcall | 按 TeccAggregateClass 六分类校验 count/min/max/sum/avg/string_agg/array_agg |
| 标量校验器 stmt_validate_scalar_funcall | 按分类校验 greatest/least/power（coalesce/nullif/case 走常量加密与操作符校验）|
| 常量加密 stmt_process_funcall_constants | 加密 coalesce/nullif/greatest/least 参数中的常量 |

校验器均返回 bool（失败时已设置错误信息），挂接于两处：SELECT 目标列 FuncCall 处理循环（聚合校验 → 标量校验 → 常量加密）、WHERE/HAVING 表达式 walker（校验失败以专用结果码 -10/-11 传递，防止特定错误被通用错误覆盖）。校验流程：提取函数名 → 分类（未跟踪函数放行）→ 遍历参数中加密列 → 解析列元数据 → 按分类检查算法位掩码（及整型范围）→ 不满足则报错终止。

### 12.1.7  **流程逻辑**

```
SELECT 目标列 FuncCall：聚合校验 → 标量校验 → 常量加密 → 改写下发
WHERE/HAVING walker：表达式遍历 → 校验失败以结果码 -10/-11 传递 → 阻断下发
```

### 12.1.8  **接口**

1）接口编号：与《瀚高全密态数据库V4.0.1 产品概要设计》第 12 章对应（V5-AD-9-1）。

2）方法：stmt_processor.c（stmt_validate_aggregate_funcall:772-929、stmt_validate_scalar_funcall:991、stmt_process_funcall_constants:304、TeccAggregateClass:700-708）；where_clause_processor.c:2439-2453。

3）接口说明：校验失败同步清零重写标志，避免"查询未改写"假阳性。

### 12.1.9  **存储分配**

无独立分配（校验为函数调用期逻辑）。

### 12.1.10  **注释设计**

校验器分类与位掩码检查以 `/* ReqID:TECC4.0 */` 注释标注。

### 12.1.11  **限制条件**

## 12.2  **V5-DD-9-2**  **函数支持矩阵**

### 12.2.1  **程序描述**

定义内置函数在密态列上的支持矩阵（对应需求 4.4.1.4 函数表），列算法能力以 encryption_type 位掩码表示，基类型以 original_type_oid 判定（同态运算仅 int2_enc/int4_enc/int8_enc）。

### 12.2.2  **功能**

| 函数 | 密态类型 | 依赖算法 | 客户端校验规则 |
|---|---|---|---|
| count（含 DISTINCT）| 全部密态类型 | 无需算法 | 无条件放行 |

| min / max | 全部密态类型 | OPE | OPE 位，否则报错 |
| coalesce | 全部密态类型 | 无需算法 | 放行；常量按列算法加密 |
| nullif | 全部密态类型 | DET/OPE | 常量加密阶段按列实际算法（DET 优先、OPE 兜底），两者皆无报错 |
| greatest / least | 全部密态类型 | OPE | OPE 位，否则报错（DET 列报错）|
| case | 全部密态类型 | DET/OPE | WHEN 条件按操作符校验（= 走 DET/OPE、>/< 走 OPE）；THEN/ELSE 分支支持密态列与普通常量混用，普通常量按密态列完整算法模式加密（RND + 列全部对称算法段，与写入路径一致），常量类型与密态列原始类型不兼容时报错 |
| power | int2_enc、int4_enc、int8_enc | HE-MUL | HE-MUL 位 + 整型基类型，否则报错 |

除上述函数外，其它内置函数在密态列上均不支持（avg/string_agg 属明确拒绝类，返回固定格式错误）。幂运算的 ^ 操作符形式走操作符处理路径，保持既有行为（指数须为正整数、上限 10000，he-add 列报错，均为服务端校验）。

## 12.3  **V5-DD-9-3**  **常量加密策略**

## 14.1  **V5-DD-11-1**  **pg_upgrade 升级设计**

### 14.1.1  **程序描述**

支持从 V4.0.0 升级到 V4.0.1，保证数据一致。pg_upgrade 采用"新库 initdb + 用户表 relfilenode 文件级拷贝 + pg_dump/pg_restore 重建 schema 与对象"的机制，TECC 密钥体系的升级保证 KEK/DEK 元数据与密文数据完整迁移。**当前 pg_upgrade 无 TECC 专门适配代码**（仅通用 PG 机制），升级可行性依赖 pg_dump 的 KEK/DEK 导出重建元数据，且 hg_encrypted_column_args 未导出（见 6.2.13），需补充（本子模块为设计，实施进度见 14.1.13）。

### 14.1.2  **功能**

- 总体要求：密文数据二进制兼容（用户表 relfilenode 文件级拷贝迁移，升级不重写密文，升级后客户端按既有解密链路继续解密 V4.0.0 数据）；
- 既有系统表保持结构稳定（KEK/DEK 元数据表、hg_encrypted_columns 为 V4.0.0 已有系统表，结构保持不变；系统表加字段需变更 bki 表结构且系统表 ALTER TABLE 受 PG 限制，元数据扩展一律采用新增 args 表）；
- 新增元数据表：V4.0.1 仅新增 hg_encrypted_column_args（一列多 DEK 绑定），由新库 initdb 建空表，无历史数据需要迁移；
- 系统目录注册（密态类型、pg_proc/pg_aggregate 等）由升级后的新版本二进制提供，不依赖数据目录迁移；
- pg_upgrade 修改点：适配 TECC 系统表与密态列元数据的检查与迁移逻辑，升级后校验密态数据与元数据一致性（密态查询与解密链路回归）。

升级各阶段对 TECC 数据的处理：

| 升级阶段 | 机制 | TECC 数据处理 |
|---|---|---|
| 新集群 initdb | V4.0.1 二进制创建新数据目录 | 系统表结构由 postgres.bki 提供（含 V4.0.0 既有 TECC 系统表与新增 hg_encrypted_column_args 空表），hg_metadata_views.sql 视图随 initdb 安装 |
| 全局对象导出 | pg_dumpall --globals-only --binary-upgrade | 角色/表空间，与 TECC 无直接关系 |
| 每库 schema 导出 | pg_dump --schema-only --binary-upgrade | 导出 KEK/DEK 的 DROP + CREATE 语句（见 14.1.3），含密态建表语句（ENCRYPTED WITH）|
| 用户表数据拷贝 | relfilenode 文件级拷贝（heap/matview/toast/index）| 密态表数据（密文）二进制拷贝，不重写 |
| pg_restore 还原 | 按 dump 文件重建 schema 与对象 | 重建 KEK/DEK 元数据、密态列定义与视图 |

系统表数据不随文件拷贝迁移：TECC 系统表属于 pg_catalog 命名空间，pg_upgrade 的 relfilenode 拷贝仅覆盖用户表（get_rel_infos 限定 nspname 非 pg_catalog 且 oid ≥ FirstNormalObjectId），因此 KEK/DEK 元数据（hg_kek、hg_dek、hg_kek_args、hg_dek_args 中的记录）必须通过 pg_dump/pg_restore 重建，不能依赖文件拷贝。

### 14.1.3  **功能（续）——KEK/DEK 元数据升级设计**

导出（pg_dump，已实现）：
- pg_dump 通过 getKekInfo/getDekInfo 读取 hg_kek、hg_dek 及 hg_kek_args、hg_dek_args 参数表，dumpKek/dumpDek 生成重建语句，放置于 PRE_DATA section（先 KEK 后 DEK，按依赖排序）：
  - KEK：CREATE KEK <name> (key_store, key_algo, key_path, public_key)；
  - 对称 DEK：CREATE DEK <name> WITH VALUES (KEK, key_algo='sm4', encrypted_value, key_length)；
  - 同态 DEK：CREATE DEK <name> WITH VALUES (KEK, key_algo='he-add'|'he-mul', he_ec_pubkey/he_ec_privkey 或 he_eg_pubkey/he_eg_privkey)，密钥对材料完整导出，还原后 DEK 保持可用；
- 语句均带 _tecc_processed = 'on' 标记，pg_restore 还原时前端处理器跳过重复加密/改写，直接将参数入库。

还原（pg_restore）：
- 按依赖顺序先重建 KEK、再重建 DEK（DEK 引用 KEK 名称，还原时按名解析）；
- 还原前需在目标机器放置密钥文件：对称 KEK 需 .key 文件、非对称 KEK 需 .priv 文件（CREATE KEK 还原时从 .priv 同目录加载 .pub 入库），路径经 key_path / TECC_KEK_PATH 定位（见 6.2.4 跨平台恢复）；
- 硬加密（tzwykms/swxakms）：密钥托管密码机，无文件迁移，KEK 元数据还原后按 KMS 索引关联密码机内密钥。

分布式身份标识保持：DEK 的 column_key_distributed_id = hash("schema.dek_name") 为确定性计算，重建后与旧值一致，密文段内嵌的 DEK 身份标识、列绑定元数据（hg_encrypted_columns.column_key_id）随之保持有效，密文数据无需重加密、解密链路不中断。

一列多 DEK 绑定（hg_encrypted_column_args）：当前 pg_dump 未导出该表（dumpDek 仅导出对称 DEK 引用与 HE 密钥对材料）。V4.0.1 需补充导出（在 pg_dump 中新增对 hg_encrypted_column_args 的读取与 CREATE 语句生成，按 column_id + key 输出 he_add_dek/he_mul_dek 的 DEK 分布式身份标识），或在升级脚本中依据 hg_encrypted_columns 与 hg_dek 重建绑定条目，保证升级后同态列的一列多 DEK 绑定不丢失。

密钥文件与运行环境：
- .key / .priv / .pub 密钥文件不随升级迁移，按部署环境自行保持；升级前后 TECC_KEK_PATH / key_path 指向不变，客户端升级后按既有路径加载密钥文件；
- 密钥文件格式（TECCKEK v1、固定 MEK 加密）在 V4.0.0/V4.0.1 间保持兼容，升级后旧密钥文件可直接使用；
- 硬加密（tzwykms/swxakms）：密钥托管密码机，无文件迁移；KEK/DEK 元数据重建后按 KMS 索引关联，升级后需验证密码机内密钥可用。

升级后校验：
- 元数据完整性：校验 hg_kek、hg_dek、hg_kek_args、hg_dek_args、hg_encrypted_column_args 记录数与升级前一致（KEK/DEK 数量、参数条目、一列多 DEK 绑定条目）；
- 解密链路回归：对含密态列的表执行 SELECT（等值/范围/模糊查询）与同态加/乘，确认 KEK/DEK 元数据完整、密文可解密、一列多 DEK 列解密正常；
- 等价性校验：pg_dump 还原的 CREATE KEK/DEK 与升级前元数据等价（key_path/key_algo/public_key/encrypted_value/HE 密钥对材料一致），密态查询结果与升级前一致。
