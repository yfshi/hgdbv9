# 1  **模块功能说明**

同态加密（Homomorphic Encryption, HE）模块是瀚高全密态数据库 V4.0.1 新增的核心能力模块，为整型密态类型（int2_enc / int4_enc / int8_enc）提供密文域直接计算能力，实现"数据不落明文、计算不落明文"的完整密态计算链路。

本模块的功能范围包括：

- **加法同态（he-add）**：基于椭圆曲线 ElGamal（EC-ElGamal）算法，支持密文加（+）、减（-）运算与 SUM 聚合，以及密态列与整型常量的标量加/减/乘运算；
- **乘法同态（he-mul）**：基于有限域 ElGamal（FF-ElGamal）算法，支持密文乘（*）运算、密态列与整型常量的标量乘法，以及幂运算（^、power 函数，指数为正整数且上限 10000）；
- **跨类型运算**：三种密态整数类型之间支持两两组合的加减乘运算，结果类型取较大者；
- **算法并存**：同态算法可通过 SUPPORT_ALGO 参数与 DET/OPE/SEARCH/RND 对称算法灵活组合，同一密态列可同时绑定对称 DEK 与多个同态 DEK（一列多 DEK）；
- **密钥体系依赖**：同态加密依赖两级密钥体系（KEK/DEK）与非对称密钥（SM2），密钥管理设计见第 7 章。

密态视图（V5-AD-2）模块在 V4.0.0 已有基础能力（视图/物化视图包含密态列投影、查询按元数据自动解密、加密元数据继承注册）之上，补齐**视图/物化视图定义中密态列过滤**能力，使视图查询行为与直接查询基表完全一致：

- **普通视图（VIEW）**：视图可包含全部或部分密态列、也可混合普通列，视图定义中密态列过滤常量由客户端自动加密，查询解密与直接查询基表一致；
- **物化视图（MATERIALIZED VIEW）**：数据以密文落盘，加密元数据自动继承基表列 DEK 与算法，REFRESH / WITH NO DATA 与 PG 原生语义一致。

工具增强（V5-AD-3）模块对应需求 4.4.2.1"工具增强"，扩展 psql 等客户端工具对密态数据的支持：

- **\copy 子查询导出与 BINARY 格式**：支持 \copy (SELECT ...) TO 'filename' 子查询导出，支持 WITH (FORMAT BINARY) 导出导入（覆盖全 9 种密态类型、边界值、NULL 场景，roundtrip 数据一致）；客户端 \copy 导出时加密列输出明文，服务端 COPY 导出时输出密文，两者相互独立（TEXT/CSV 格式在 V4.0.0 已交付）。

密钥管理（V5-AD-4）模块对应需求 4.5.1"安全性-密钥管理"，在 V4.0.0 两级密钥（KEK/DEK）体系上引入非对称密钥体系，支撑同态加密与密钥生命周期管理：

- **非对称密钥管理**：CREATE KEK 支持 key_algo='sm2'（非对称 SM2 KEK），CREATE DEK 支持 key_algo='he-add'/'he-mul'，同态 DEK 按算法独立生成密钥对；
- **KEK 密钥轮换**：ALTER KEK 更换 KEK，对关联 DEK（含 HE 私钥信封）重新加密，满足等保与合规要求；
- **一列多 DEK 绑定**：同一密态列可同时绑定对称 DEK 与 he-add/he-mul 同态 DEK，绑定关系独立存储、独立管理。

会话级加解密元命令（V5-AD-5）模块对应需求 4.4.2.2"会话控制"，提供 `\enable hg_tecc.mode` / `\disable hg_tecc.mode` 会话级加解密开关，并向上层应用开放 libpq 接口：

- psql 元命令内部调用 libpq 接口修改当前 `PGconn` 的 TECC 会话状态，不把 `hg_tecc.mode` 设计为 SQL 参数，也不提供 `SET/SHOW/RESET` 入口；
- 上层 C 应用可通过 `PQteccSetMode(PGconn *conn, int enabled)` 动态切换当前连接的 TECC 透明加解密，通过 `PQteccGetMode(PGconn *conn, int *enabled)` 查询当前状态；
- 同一连接内临时关闭客户端 SQL 加密/改写和结果解密，直接查看服务端返回的密文形态，用于调试、验收和运维场景；
- 仅影响当前会话的客户端处理策略，不修改服务端数据、不影响其他连接，无需断开重连即可切换明文/密文视图。

- **Tab 补全**：KEK/DEK 对象名、TECC DDL 关键字、ENCRYPTED WITH 子句参数与算法候选值、工具函数名的自动补全；
- **帮助信息**：psql 命令帮助、SQL 语法帮助、函数帮助三层体系，覆盖 TECC 连接参数、DDL 语法与工具函数。

- **DDL 显示元命令**：\sT 显示含密态列定义的 CREATE TABLE 语句、\sK 显示 CREATE KEK、\sk 显示 CREATE DEK，面向可重放与逻辑迁移；
- **信息查看元命令**：\dkek[+] 显示 KEK 信息、\ddek[+] 显示 DEK 信息（含扩展模式），面向管理对象巡检。

维修性工具函数（V5-AD-8）模块对应需求 4.6"维修性需求"，提供面向管理员和已授权用户的密文诊断工具函数：

# 2  **模块类型**

本模块是完全自研。算法实现基于公开密码学文献（ElGamal 公钥密码体制、椭圆曲线密码体制），不依赖第三方商用加密组件，符合国产化与国密合规要求。

# 4  **V5-AD-1**  **同态加密模块设计**

在传统全密态数据库中，加密列仅支持等值查询（确定性加密）、范围查询（保序加密）和模糊匹配（可搜索加密）等"查询型"能力，**无法对密文直接进行算术运算**。当业务需要对加密列执行求和、累加、乘积等计算时，必须先将密文返回客户端解密，再在明文上计算，这不仅破坏数据全生命周期加密的承诺，也会带来巨大的传输与计算开销。

同态加密允许直接在密文上进行运算，运算结果解密后与在明文上进行相同运算的结果一致。本模块为整型密态类型提供加法、减法、乘法、标量运算、幂运算及 SUM 聚合的密文域运算能力，并支持与对称加密算法并存，扩展密态数据库在统计分析场景中的应用能力。

## 4.1 算法能力与约束

### 4.1.1 能力矩阵

| 运算能力 | he-add（加法同态） | he-mul（乘法同态） |
|---|---|---|
| 加（+）/ 减（-） | 支持（列×列、列×常量） | 不支持 |
| SUM 聚合 | 支持（结果统一提升为 int8_enc） | 不支持 |
| 乘（*） | 支持列×整型常量的标量乘法 | 支持（列×列、列×常量） |
| 幂（^、power） | 不支持 | 支持（指数为正整数，上限 10000） |
| 跨类型运算 | 支持（int2/int4/int8 两两组合，结果取较大者） | 支持（规则同左） |
| 适用类型 | int2_enc / int4_enc / int8_enc | int2_enc / int4_enc / int8_enc |
| 底层算法 | EC-ElGamal（椭圆曲线点群） | FF-ElGamal（有限域模运算） |

### 4.1.2 约束

- 同态加密仅支持 int2_enc、int4_enc、int8_enc 三种密态整数类型，不支持 numeric_enc、float4_enc、float8_enc；
- 仅支持在 PG 兼容端口使用同态加密功能；
- 同态加密功能依赖于非对称密钥体系：同态 DEK（he-add / he-mul）必须绑定非对称 KEK（key_algo='sm2'），详见第 7 章密钥管理设计；
- 服务端同态运算不做溢出判断，运算结果在客户端解密后按结果类型（int2/int4/int8）进行范围校验，超范围报错；
- 跨类型运算要求参与列使用同一 DEK（按密文段内嵌 DEK 身份校验）。

## 4.2  V5-AD-1-1  EC-ElGamal（加法同态） 算法设计

### 4.2.1 算法原理

EC-ElGamal 将明文编码为椭圆曲线上的标量倍点，在点群上完成加密与同态运算。

|环节|数学表达|说明|
|---|---|---|
|系统参数|曲线 P-256，基点 G，阶 n|可切换 SM2 曲线以符合国密要求|
|密钥生成|私钥 x ← 随机(0,n)；公钥 Q = x·G||
|加密|E(m) = (C1, C2) = (r·G, m·G + r·Q)，r 为随机数|概率性加密，同一明文密文不同|
|解密|M = C2 − x·C1 = m·G，再求解离散对数得 m|需 BSGS 表加速|
|同态加法|E(a)+E(b) = (C1a+C1b, C2a+C2b) = E(a+b)|点群加法|
|同态减法|E(a)−E(b) = (C1a−C1b, C2a−C2b) = E(a−b)|点群减法|
|标量乘法|k·E(a) = (k·C1, k·C2) = E(k·a)|标量倍点|

### 4.2.2 CRT 拆分机制（核心优化）

由于 EC-ElGamal 解密需要解离散对数（DLP），明文值越大求解越困难。为此引入 CRT（中国剩余定理）拆分：

```
明文 m（≤2^96，覆盖 int8 全值域）
    │  按 8 个 12-bit 素数拆分为同余组
    ▼
m1 = m mod p1 ──► EC 加密 ──► (C1_1, C2_1)
m2 = m mod p2 ──► EC 加密 ──► (C1_2, C2_2)
...（共 8 个分量）
    │  同态运算逐分量进行
    ▼
解密时：每个分量在 12-bit 值域内解 DLP（BSGS 2^14 表一步命中）
    │  CRT 重组
    ▼
恢复明文 m
```

|参数|值|说明|
|---|---|---|
|素数个数|8|每分量值域 12-bit|
|单素数位宽|12 bit|值域 0~4095，BSGS 表 16384 全覆盖|
|总明文位宽|96 bit|2^96 ≈ 7.9×10^28，覆盖 int8 全范围|
|密文大小|1 + 8×(33+33) = 529 B|1 字节分区数 + 8×(C1+C2 压缩点)|

### 4.2.3 BSGS 离散对数求解

Baby-Step Giant-Step（大步小步）算法将 DLP 求解从 O(m) 降为 O(√m)：

- **Baby Step（预计算）**：预先计算 i·G（i=0..16383）并按键值排序建表，一次构建、多次复用；
- **Giant Step（在线求解）**：对目标点 M 逐次减去 m·G 并二分查表，命中即得明文值。

由于 CRT 将明文限制在 12-bit 值域内，BSGS 表（2^14 条目）在 0 步内即可覆盖全部取值，解密开销主要取决于 EC 点运算本身。

### 4.2.4 并行解密

解密 8 个 CRT 分量的 DLP 相互独立，采用多线程并行加速：

- 分区按线程数均匀分配（线程数上限 16）；
- 每个工作线程持有独立的运算上下文，避免 OpenSSL 上下文竞争；
- 主线程完成全部子分量后执行 CRT 重组；
- 跨平台线程封装（Windows / POSIX）。

### 4.2.5 负数处理

明文经 CRT 还原后取值在 [0, N) 区间，按符号约定：**当还原值 m > N/2 时，实际整数为 m − N**。加密侧对负数取模后加密，解密侧依据该约定还原符号，从而支持负数密文的同态运算。

### 4.2.6 溢出处理与范围校验

明文运算范围：8 分区 CRT 总模数 P ≈ 2^96（每分区约 12 位素数），按符号约定（还原值 m > P/2 视为负数）后有效明文范围约 ±2^95，远大于 int8 类型范围（2^63）。

服务端仅对密文执行同态运算，不感知明文数值与范围，不做溢出检查；溢出边界由客户端解密后的范围校验保证：

- 客户端解密得到明文后，按结果列的整数类型（int2/int4/int8）进行范围校验；
- 结果超出对应类型表示范围时报错（数值超出范围），不再静默返回错误值；
- 与原生整数类型加法/乘法超范围报错行为保持一致。

### 4.2.7 跨类型运算支持

int2_enc、int4_enc、int8_enc 的 EG_ADD/EG_MUL 密文段格式完全一致（均为 8 分区 CRT / 有限域 ElGamal 密文），服务端同态运算按 Datum 处理密文，仅校验段内 DEK 身份一致，不区分整数类型，因此底层天然支持跨类型运算。

- **操作符注册**：为三种密态整数类型两两组合注册跨类型操作符（加法、减法、乘法各 6 个方向组合：int2×int4、int4×int2、int2×int8、int8×int2、int4×int8、int8×int4）；
- **结果类型规则**：结果类型取参与运算类型的较大者（int2_enc + int4_enc → int4_enc、int2_enc + int8_enc → int8_enc、int4_enc + int8_enc → int8_enc），与原生整数类型提升惯例一致；
- **DEK 要求**：跨类型运算要求参与列使用同一 DEK（段内 DEK 身份校验，不一致报错）；
- **前端处理器**：跨类型 HE 运算为列间（密文×密文）运算，无常量参与，不做常量加密，密文直接发送至服务端运算；结果列类型按提升规则标记。跨类型场景中的整型常量按 4.5.2 规则由客户端加密后参与运算。

### 4.2.8 SUM 聚合设计

为支持密文统计分析场景，SUM 聚合在服务端密文上逐行同态累加，仅最终结果返回客户端解密一次。

**聚合状态类型提升规则：**

| 输入类型 | 聚合状态类型 | 说明 |
|---|---|---|
| int2_enc | int8_enc | 状态提升为 int8_enc，防小类型累加溢出 |
| int4_enc | int8_enc | 状态提升为 int8_enc |
| int8_enc | int8_enc | 状态类型与输入一致 |

聚合状态类型统一提升为 int8_enc，与原生 sum(int2)/sum(int4) → int8 的防溢出惯例保持一致；sum(int2_enc)、sum(int4_enc)、sum(int8_enc) 的结果类型均为 int8_enc。

**聚合行为设计：**

- 聚合过渡函数按输入类型区分（int2_enc / int4_enc 输入与 int8_enc 输入各有一套），逐行执行"状态 + 新值"的同态加法；
- 聚合为**非严格（non-strict）**：NULL 输入行跳过不累加；状态为空时用零值状态初始化，避免首行 NULL 导致聚合中断；
- 组合函数与过渡函数一致（均为同态加法），支持并行聚合（partial/combine 阶段同为密文域累加）；
- 聚合全程在密文上进行，服务端不感知明文数值；最终聚合结果返回客户端解密并做 int8 范围校验。

### 4.2.9 标量运算设计

同态加法既支持两个密态列（使用同一 DEK）之间的运算，也支持密态列与整型常量的标量运算，包括标量加（a+3）、标量减（a−3）与标量乘（a×3）。

**设计要点：**

- 标量常量由客户端持列的同态公钥加密为完整 intN_enc 密文（仅含对应同态段，段内携带 DEK 分布式身份），改写为 `enc + 'hex'::intN_enc` 发往后端参与运算，常量明文不出客户端、不进入网络报文与服务端；服务端以密文×密文通用同态操作符完成运算（he_add_generic / he_sub_generic / he_mul_generic）；
- 运算双向支持：a+3 与 3+a、a×3 与 3×a 均可用（常量在左侧的变体另行注册）；
- 负标量处理：负常量由客户端按负值加密（标量加转标量减、标量减转标量加由服务端逆运算语义保证），保证负数常量正确参与运算；
- 结果类型取被运算列的类型，结果密文仅含对应同态段；
- 标量乘法：列开启 he-mul 时客户端 FF-ElGamal 加密常量做全密文同态乘法；列仅 he-add（未开启 he-mul）时复用 EC-ElGamal 标量倍点能力（性能更优），但因 EC-ElGamal 仅支持加法同态、标量倍点必须知道明文 k，该例外路径常量以明文参与服务端运算（兼容路径）。

### 4.2.10 故障/异常处理

- **溢出**：服务端不做溢出判断，客户端解密后按结果类型范围校验，超范围报错，与原生整型运算行为一致；
- **DEK 不匹配**：参与同态运算的两个密文段内嵌 DEK 身份不一致时报错；
- **槽位缺失**：操作数缺少所需同态段（如对未开启 he-add 的列执行加法）时报错并提示正确配置；
- **私钥不可用**：客户端本地缺少 KEK(sm2) 私钥导致无法解开 HE 私钥信封时，不报错，直接返回密文。

## 4.3  V5-AD-1-2  有限域 ElGamal（乘法同态）

### 4.3.1 算法原理

|环节|数学表达|说明|
|---|---|---|
|系统参数|2048-bit 安全素数 p，生成元 g|采用 RFC 5114 IKE/2048 群参数|
|密钥生成|私钥 x ← 随机；公钥 h = g^x mod p||
|加密|E(m) = (c1, c2) = (g^r, m·h^r) mod p|概率性加密|
|解密|m = c2 · (c1^x)(−1) mod p|**直接模算术，无需解 DLP**|
|同态乘法|E(a)·E(b) = (c1a·c1b, c2a·c2b) = E(a·b mod p)|分量模乘|
|标量乘法|加密常量 k 得 E(k)，再做同态乘|客户端用公钥加密常量，发往后端|

> 关键区别：有限域 ElGamal 解密通过模逆直接恢复明文，不依赖 DLP 求解，因此 **无需 CRT 拆分也能处理大数**；其 CRT 双素数模式仅用于 **性能优化**（见下）。

### 4.3.2 CRT 双素数优化模式

|参数|值|说明|
|---|---|---|
|素数个数|2|各 1024-bit 安全素数（RFC 5114 / Oakley Group 2）|
|合模数 N|p1·p2 ≈ 2048 bit|与标准模式安全强度相当|
|加速比|约 4 倍|1024-bit 模幂约比 2048-bit 快 8 倍，双素数开销抵消后净加速约 4 倍|
|密文大小|2×2×128 = 512 B|与标准模式（256+256）相同|

CRT 模式将明文 m 分别在 p1、p2 两个子群中加密为 (c1_i, c2_i)，解密时先各自恢复 m_i 再按 CRT 公式重组：

```
m = m1 + p1 · ((m2 − m1) · p1⁻¹ mod p2)  (mod N)
```

### 4.3.3 幂运算设计

幂运算（a^n）在密文域内通过同态乘法叠加实现：将密文连续自乘 n−1 次（a^n = a×a×…×a），全程在服务端密文上进行，最终结果返回客户端解密一次。

**指数约束：**

- 指数 n 必须为正整数；
- 指数支持整型常量或非密态整数列，不支持密态列作为指数；
- 为防范指数过大导致服务端运算耗时失控（DoS 攻击），**指数上限为 10000**，超过上限报错；
- 负指数、零指数按语法错误处理。

**入口设计：**

| 入口 | 说明 |
|---|---|
| ^ 运算符 | `SELECT a ^ 3 FROM t;`，服务端重复同态相乘 n−1 次 |
| power 函数 | `SELECT power(a, 3) FROM t;`，与 ^ 运算符等价 |

**结果处理：**

- 运算结果仍为同态乘法密文，仅含 EG_MUL 段，解密得 a^n；
- 结果在客户端解密后按结果类型（int2/int4/int8）进行范围校验，超范围报错；
- 操作数缺少 EG_MUL 段（列未开启 he-mul）时报错。

### 4.3.4 标量乘法设计

密态列与整型常量的标量乘法（a×k）设计如下：

- 常量 k 由客户端持 he-mul 公钥加密为 E(k)（完整 intN_enc 密文，仅含 EG_MUL 段，段内携带 DEK 分布式身份），改写为 `a * 'hex'::intN_enc` 发往后端，再做同态乘法 E(a)·E(k) = E(a·k)；服务端以密文×密文通用操作符（he_mul_generic）完成运算，常量明文不出客户端；
- 运算双向支持：a×k 与 k×a 均可用（常量在左侧的变体另行注册）；
- 若列仅开启 he-add（未开启 he-mul），复用 EC-ElGamal 标量倍点能力（k·E(a) = E(k·a)），性能更优；该路径因 EC-ElGamal 仅加法同态、标量倍点必须知道明文 k，常量以明文参与服务端运算（兼容路径）；
- 负标量处理：负常量按符号约定取模后加密，解密侧依符号约定还原。

### 4.3.5 故障/异常处理

- **指数超限**：幂运算指数超过 10000 时报错，防止服务端运算耗时失控；
- **溢出**：结果解密后按类型范围校验，超范围报错；
- **DEK 不匹配**：参与乘法运算的两个密文段内嵌 DEK 身份不一致时报错；
- **槽位缺失**：操作数缺少 EG_MUL 段时报错并提示正确配置。

## 4.4  V5-AD-1-3  密文数据结构设计

### 4.4.1 CipherDataType v2.0 存储格式

同态加密要求单个加密值可同时携带多种算法的密文，因此将密文格式升级为 v2.0，新增两个同态槽位。EG_ADD/EG_MUL 槽位内嵌各自 DEK 的分布式身份标识（4 字节定长），使同一密态列可同时绑定对称 DEK 与多个同态 DEK：

```
┌──────────┬──────┬──────┬──────┬────────┬──────────────────┬──────────────────┐
│ Header   │ RND  │ DET  │ OPE  │ SEARCH │ EG_ADD           │ EG_MUL           │
│ (36 B)   │ ...  │ ...  │ ...  │ ...    │ [dek_id][HE加]   │ [dek_id][HE乘]   │
└──────────┴──────┴──────┴──────┴────────┴──────────────────┴──────────────────┘
```

|字段|位置|长度|说明|
|---|---|---|---|
|header|开头|36 B|版本号 + 各槽位长度（含 eg_add_length、eg_mul_length）+ DEK 分布式ID|
|eg_add_length|header|4 B|EG_ADD 段总长度（含内嵌的 4 字节 DEK 分布式ID）|
|eg_mul_length|header|4 B|EG_MUL 段总长度（含内嵌的 4 字节 DEK 分布式ID）|
|EG_ADD 段|槽位 5|动态|`[dek_id:4]` + EC-CRT 密文（1 + 66×n 字节）|
|EG_MUL 段|槽位 6|动态|`[dek_id:4]` + ElGamal 密文（512 字节）|

**DEK 身份标识（dek_id）规则：**
- 密文中所有 DEK 身份一律使用**分布式身份标识**（对 `schema.dek_name` 的确定性 hash，即 hg_dek 表的 column_key_distributed_id），不使用实例内 Oid——保证跨实例唯一性与密文可迁移性；
- header 中的全局 DEK 分布式ID 用于 RND/DET/OPE/SEARCH 对称槽位（对称 DEK）；
- EG_ADD 段内嵌 he-add DEK 的分布式ID；EG_MUL 段内嵌 he-mul DEK 的分布式ID；
- 各同态段独立携带 DEK 身份，服务端运算与客户端解密按段所属 DEK 解析密钥，互不干扰。

> 各槽位可独立为空（长度为 0），未启用对应算法的列不填充该槽位。同态操作符执行前会先校验所需槽位是否存在。

### 4.4.2 同态密文内部序列化格式

**EG_ADD（EC-CRT 密文）：**

```
┌──────────┬──────────────┬─────────────────────┬─────────────────────┐
│ dek_id   │ num(1 B)     │ C1_1(33B) C2_1(33B) │ ... C1_n C2_n       │
│ (4 B)    │              │                     │                     │
└──────────┴──────────────┴─────────────────────┴─────────────────────┘
```

- 段首 4 字节为 he-add DEK 的分布式身份标识（dek_id），随后为 EC-CRT 密文体；
- 密文体：1 字节记录分区数 n，随后每分区依次存放压缩形式的 C1、C2 椭圆曲线点（各 33 字节）；
- 8 分区时密文体为 529 字节，加上段首 dek_id 共 533 字节；分区数可配置，密文长度随 n 线性变化。

**EG_MUL（ElGamal 密文）：**

```
┌──────────┬──────────────┬──────────────┐
│ dek_id   │ c1 (256 B)   │ c2 (256 B)   │
│ (4 B)    │              │              │
└──────────┴──────────────┴──────────────┘
```

- 段首 4 字节为 he-mul DEK 的分布式身份标识（dek_id），随后为 ElGamal 密文体；
- 标准模式：c1、c2 各 256 字节（2048-bit 大数定长填充），共 512 字节，加上段首 dek_id 共 516 字节；
- CRT 模式：按 p1/p2 顺序存放 c1_1、c2_1、c1_2、c2_2，各 128 字节，总长同样为 512 字节。

### 4.4.3 槽位填充规则

不同算法配置下各槽位的填充行为如下：

| 列配置（SUPPORT_ALGO） | RND | DET/OPE/SEARCH | EG_ADD | EG_MUL |
|---|---|---|---|---|
| 仅 he-add | 不填充 | 不填充 | 填充 | 不填充 |
| 仅 he-mul | 不填充 | 不填充 | 不填充 | 填充 |
| 对称算法（默认含 RND） | 填充 | 按需填充 | 不填充 | 不填充 |
| he-add + he-mul | 不填充 | 不填充 | 填充 | 填充 |
| 对称 + he-add / he-mul（并存） | 填充 | 按需填充 | 按配置填充 | 按配置填充 |

规则要点：

- **纯 HE 列（仅配置 he-add/he-mul，不含任何对称算法）不生成 RND 密文**，RND 槽位为空；该规则保证 HE 解密路径不被对称槽位干扰，同时减少存储与解密开销；
- 混合列（对称与同态并存）保留对称槽位，同时填充对应同态槽位；
- **同态运算结果密文仅携带参与运算的同态段**（EG_ADD 或 EG_MUL），对称段不被携带——这是并存模式下赋值约束的根源（见 4.5.5）。

## 4.5  V5-AD-1-4 前端处理设计

### 4.5.1 建表语法解析与校验

前端建表语句处理器负责解析 ENCRYPTED WITH 子句中的加密选项，并执行第一层校验：

**解析选项：**

| 选项 | 含义 | 必选条件 |
|---|---|---|
| DEK | 对称 DEK（供 DET/OPE/SEARCH/RND）| 列启用任一对称算法时必选 |
| SUPPORT_ALGO | 列启用的算法列表（det/ope/search/he-add/he-mul）| 不配置或仅配置对称算法时默认同时启用 rnd |
| HE_ADD_DEK | he-add 算法使用的同态 DEK | 列启用 he-add 时必选 |
| HE_MUL_DEK | he-mul 算法使用的同态 DEK | 列启用 he-mul 时必选 |

DEK 名称均支持指定模式名（[模式名.DEK名]）。

**校验流程（前端→后端双层）：**

1. 前端语法校验：SUPPORT_ALGO 与 DEK 参数匹配（算法启用必须给出对应 DEK）、DEK 的 key_algo 与算法一致，语法错误立即报错、不访问数据库；
2. 后端权威校验：DEK 存在性、key_algo 与 SUPPORT_ALGO 匹配、USAGE 权限检查，防止绕过前端提交非法定义；
3. 校验通过后写入列 DEK 绑定元数据（hg_encrypted_column_args，详见 7.2）。

### 4.5.2 HE 表达式常量处理规则

前端表达式处理对 HE 运算符（+、-、*、^）按以下规则处理**整型常量**：

- **客户端常量加密（默认路径）**：`+`、`-`、`*` 的整型常量由客户端持列的同态公钥加密为完整 intN_enc 密文（+/- → EC-ElGamal 加密填充 EG_ADD 段；* → FF-ElGamal 加密填充 EG_MUL 段，段内携带 DEK 分布式身份），SQL 改写为 `enc + 'hex'::intN_enc` / `enc * 'hex'::intN_enc` 发送至服务端，服务端解析到密文×密文通用操作符（he_add_generic / he_sub_generic / he_mul_generic）执行同态运算，常量明文不出客户端、不进入网络报文与服务端；
- **透传（例外路径）**：以下场景常量保持明文透传，由服务端按现状处理——幂运算（^）的指数（服务端重复乘法循环次数，必须为明文）；he-add 列（未开启 he-mul）的标量乘（EC-ElGamal 标量倍点必须知道明文 k）；非整型常量（float/numeric 等，无对应标量操作符，服务端按操作符解析报错）；
- HE 运算不参与等值/范围/模糊查询的改写规则（与 DET/OPE/SEARCH 的查询改写互斥）；
- UPDATE SET 赋值场景（SET enc_col = enc_col + k 等）同样执行客户端常量加密，且保持 HE 结果只能赋给纯 HE 列的校验（见 4.5.5）。

### 4.5.3 结果列类型提升

HE 表达式的结果列类型按以下规则标记：

| 表达式 | 结果类型 |
|---|---|
| int2_enc + int4_enc / int4_enc + int2_enc | int4_enc |
| int2_enc + int8_enc / int8_enc + int2_enc | int8_enc |
| int4_enc + int8_enc / int8_enc + int4_enc | int8_enc |
| 同类型运算 | 原类型 |
| sum(int2_enc) / sum(int4_enc) / sum(int8_enc) | int8_enc |
| 幂运算 intX_enc ^ n | int8_enc（提升到最宽密态整型，与原生幂运算结果取更宽类型的惯例一致，避免解密明文超出原类型范围）|

结果列类型提升规则与原生整数类型提升惯例一致（取较大者）。

### 4.5.4 数据写入加密路径

INSERT/UPDATE 写入明文时，客户端按列的算法配置逐槽位加密：

- 对称算法（按需 DET/OPE/SEARCH，默认含 RND）→ 对称 DEK 加密，填充对应槽位；
- he-add → he-add DEK 公钥 EC-CRT 加密，填充 EG_ADD 槽位；
- he-mul → he-mul DEK 公钥 FF 加密，填充 EG_MUL 槽位；
- 纯 HE 列仅填充同态槽位（不生成 RND）；混合列同时填充对称槽位与同态槽位；
- 组装为 CipherDataType v2.0 密文后以 hex 传输服务端存储。

### 4.5.5 UPDATE 赋值校验

同态运算结果密文**仅携带参与运算的同态段**（见 4.4.3），赋值目标列必须与之兼容：

| 赋值场景 | 结果 |
|---|---|
| HE 结果 → 纯 he-add / he-mul 列 | 成功 |
| HE 结果 → 含对称算法配置的列（仅对称、或对称+同态并存）| 报错（结果密文缺少对称密文段）|
| 跨 DEK 赋值（结果 DEK 与目标列 DEK 不一致）| 报错（DEK 不匹配）|

校验由前端处理器在 UPDATE SET 赋值时执行（基于列缓存元数据），错误提示明确指明结果 DEK 与目标列 DEK 的差异。

### 4.5.6 查询语法增强设计

对应需求 4.4.1.6（V4.0.1-20-3-8）：增强密态列在复杂 SQL 语法中的支持能力。前端对查询语句统一走"子句遍历 → 加密列提取 → 列元数据获取 → 条件常量按列算法加密 → 密文比较"处理链路（stmt_processor + where_clause_processor），各语法场景的处理规则如下：

| 语法场景 | 前端处理 | 算法要求 |
|---|---|---|
| JOIN 等值（a.enc_col = b.enc_col）| 等值操作符两端为密态列时不做常量加密，直接比较密文（DET 段 memcmp 或 OPE 段等值比较）；递归遍历 JOIN 左右子树提取两侧加密列；跨表 JOIN 要求参与列配置 DET 或 OPE；不同 DEK 的 JOIN 严格拒绝 | DET 或 OPE |
| JOIN 范围（a.enc_col > b.enc_col）| 范围比较走 OPE 保序密文比较 | OPE |
| UNION ALL | 透传，仅追加结果，不涉及密文比较 | 无条件 |
| UNION / INTERSECT / EXCEPT | 透传；去重语义依赖服务端对密文的哈希与等值比较 | DET 或 OPE |
| WHERE enc_col IN (子查询)| 子查询（SubLink）递归提取列并处理，返回密文列可直接比较 | DET 或 OPE |
| WHERE enc_col = ANY / ALL (子查询)| ANY 依赖等值比较；ALL 依赖范围比较 | ANY：DET 或 OPE；ALL：OPE |
| EXISTS 子查询 | 透传，不涉及密文直接比较 | 无条件 |
| WITH / WITH RECURSIVE | 透传，不影响 CTE 执行 | 无条件 |
| GROUP BY enc_col | 透传；分组依赖密文哈希。DET-only 列需走 HashAggregate 路径（默认可能走 Sort 路径导致报错，可通过 SET enable_sort = off 切换）| DET 或 OPE |
| ORDER BY enc_col | 透传；排序依赖 OPE 保序密文 | OPE |
| DISTINCT enc_col | 透传；去重依赖密文等值比较 | DET 或 OPE |
| COUNT(DISTINCT enc_col)| 透传；去重计数依赖密文哈希 | DET 或 OPE |
| 精度/长度指定（varchar_enc(n)、bpchar_enc(n)、numeric_enc(p,s)）| 建表时通过 typenameTypeIdAndMod 解析类型修饰符（typmod）并存入列元数据 data_type_original_mod；解密输出按 typmod 格式化（numeric 按 scale、文本按声明长度）；text 原生类型不支持指定长度（text(n) 报错）| 无条件 |

**算法缺失处理：**where_clause_processor 对操作符与列算法不匹配的场景返回特定错误码（MISSING_DET / MISSING_OPE / MISSING_SEARCH / MISSING_DET_OPE / INCOMPATIBLE_TYPES），前端处理器转换为固定格式错误信息，提示所需算法与列实际配置差异。

**子查询与 CTE：**FROM 子句中的子查询（RangeSubselect）、WHERE 中的子链接（SubLink）均递归调用同一列提取与元数据处理链路；JOIN 嵌套递归遍历左右子树；WITH 语句透传不做改写。

**DET 等值 JOIN 规划期分流：**DET 加密列（算法为 det 或 det,search；det 与 ope 互斥，故 DET 列不含 OPE）的等值 JOIN 语义由 Hash Join 承载——等值比较 `cipherdata_eq` 用 DET 段 memcmp、哈希函数 `cipherdata_hash_func` 用 DET 段确定性哈希，两者语义均正确。但密态类型注册了 btree 操作符族（`btree/intN_enc_ops`），优化器静态判定密态列"可排序"，可能选 Merge Join；而排序比较 `cipherdata_cmp` 仅实现 OPE 段路径，DET 列无 OPE 段，运行期报错"no OPE or DET ciphertext available"。由于列级加密能力（det/ope 是列属性，记录于 `hg_encrypted_columns` 的 `encryption_type` 位掩码）无法通过类型级操作符族表达，优化器无法在规划期区分列能力，导致同一句 DET 等值 JOIN 随查询计划（是否选 Merge Join）时而可用、时而报错。

为此在 Merge Join 候选判定的唯一入口 `check_mergejoinable`（initsplan.c）处，对"引用无 OPE 加密列（DET-only/RND-only）的等值子句"不设置 mergeopfamilies，使其排除 Merge Join 候选、自动落到 Hash Join；Hash Join 判定走独立入口 `check_hashjoinable`，不受影响。设计要点：保持比较语义不变（排序比较 `cipherdata_cmp` 仍仅支持 OPE 段，DET 列的 ORDER BY / 范围查询 / 范围 JOIN 继续明确报错，不引入"密文序"静默乱序）；仅干预 JOIN 路径生成（不改动排序、索引、分区、聚合等既有行为）；一侧 DET、一侧 OPE 同样拦截（Merge Join 需两侧连接键均可排序，任一侧为 DET 列即拦截，落到 Hash Join 语义正确）。

## 4.6  V5-AD-1-5 操作符与聚合函数注册

同态加密在系统目录中注册以下操作符族与聚合函数：

| 类别 | 覆盖范围 | 说明 |
|---|---|---|
| 基础运算（+、-、*）| int2_enc、int4_enc、int8_enc 各类型内 | 同态加/减/乘 |
| 跨类型运算 | int2×int4、int4×int2、int2×int8、int8×int2、int4×int8、int8×int4 | 加减乘各 6 组，结果取较大者 |
| 标量运算 | 密态列 × 整型常量，双向 | 标量加/减/乘，常量在左或在右 |
| 幂运算 | int2_enc、int4_enc、int8_enc | ^ 运算符与 power 函数双入口，结果类型提升 int8_enc（见 4.5.3）|
| SUM 聚合 | sum(int2_enc)、sum(int4_enc)、sum(int8_enc) | 状态提升 int8_enc，结果类型 int8_enc |
| 聚合过渡函数 | int2_enc / int4_enc 输入各一组，int8_enc 输入一组 | 非严格，NULL 状态初始化 |

注册要点：

- 跨类型操作符复用同一通用同态运算实现，仅按类型组合注册包装入口；
- 标量运算为密态类型与原生整型的混合参数组合，常量侧为原生整型；TECC 客户端对标量整型常量做前端同态加密、改写为密文常量后走基础运算操作符（intN_enc × intN_enc 全密文路径），本类混合参数操作符保留作为兼容/例外路径（he-add 列标量乘的明文标量、非 TECC 客户端直连场景）；
- SUM 聚合的过渡函数与组合函数均为同态加法，支持并行聚合；
- 所有同态函数均为不可变（immutable）、并行安全属性，可被优化器用于并行计划。

### 4.7.3 性能优化方案汇总

V4.0.1 围绕同态加密与密态查询的性能瓶颈，从算法、客户端加解密、服务端聚合、服务端缓存与元数据、查询优化器五个层面实施了一系列优化，整体目标是在保证安全性的前提下，使密态查询与运算的性能尽量接近明文水平。各优化方案的收益与风险汇总如下表：

| 优化层次 | 优化方案 | 针对场景 | 大致收益 | 主要影响与风险 |
|---|---|---|---|---|
| 算法层 | 国密算法预计算表与循环展开 | SM3/SM4 加解密 | SM3 吞吐提升约 25%，SM4 反超 OpenSSL | 无，结果与 OpenSSL 逐字节一致，经一致性测试兜底 |
| 算法层 | EC 运算 BN_CTX 复用 | 单次 EC 运算（幂/加/减） | 减少每行 BN_CTX 创建与销毁开销 | 无，仅内存管理优化 |
| 算法层 | BSGS 表并行构建 | HE 客户端冷启动 | 建表约 1s 降至约 0.1s | 8 个表相互独立并行构建，无共享写，风险低 |
| 算法层 | BSGS 表静态数据化 | HE 客户端冷启动（短命进程每次重建表） | 建表 0.5s 完全消除，HE 查询启动 0.6s → 0.22s | 表数据约 3MB 编译进 libpq（页缓存跨进程共享，物理内存增量小）；生成程序与核心算法同源，参数指纹不匹配自动回退运行时构建 |
| 算法层 | 双向 BSGS 求解 | 负值解密 | 负值解密与正数对称，回归由超时降至 13s | 正数聚合解密慢约 2~3 倍，但聚合场景客户端解密占比小，影响有限 |
| 算法层 | 离散对数求解上限提升 | 同态加法聚合 | 聚合明文上限由 2.68 亿提升至 42.9 亿 | 无（正确性提升，见需求 20-3-1） |
| 算法层 | PBKDF2 HMAC_CTX 复用 | KEK 加载（每次进程冷缓存，两次 PBKDF2×10000 迭代） | PBKDF2 单次 49ms → 6ms，HE 查询启动 0.22s → 约 0.18s，对称查询同步受益 | HMAC_CTX 为 OpenSSL 3.0 废弃 API（仅编译警告，1.0/1.1/3.0 均支持）；派生输出逐字节一致，无安全影响 |
| 客户端加解密层 | 算法内部并行 | 单次 HE 加解密 | 约 1.4~1.5 倍 | 固定小线程数，避免超订阅 |
| 客户端加解密层 | HEX 编解码查找表 | 文本协议返回密文 | 扫描类场景约 2.86 倍 | 仅文本协议有效，二进制协议无此开销 |
| 客户端加解密层 | 字段级并行 | 批量 INSERT | 约 5.7 倍 | worker 线程需独立的元数据缓存与运算上下文 |
| 客户端加解密层 | 批量解密并行 | 批量 SELECT 解密 | 约 3.7~5.7 倍 | 线程数由环境变量控制，行数较少时自动退化为串行 |
| 服务端聚合层 | SUM 并行聚合 | 同态加法 SUM | 约 4.6 倍 | 依赖 PG 原生并行；带 LIMIT 的查询无并行收益 |
| 服务端缓存与元数据层 | HE 公钥多键缓存 | 多 DEK 同态运算 | 消除多 DEK 交替访问的缓存抖动 | relcache 失效仍整表失效，粒度安全 |
| 服务端缓存与元数据层 | 建表元数据检测走索引 | 建表 / DEK 检测 | 消除 hg_encrypted_columns 全表扫描 | 无，复用现有索引 |
| 查询优化器层 | DET 等值 JOIN 分流 Hash Join | DET 等值连接 | 稳定走 Hash Join，避免误选 Merge Join 运行期报错 | 仅干预 JOIN 路径生成，排序比较语义不变 |

各层次优化的要点说明：

**算法层**：针对国密算法和 EC-ElGamal 解密的计算热点，通过预计算表、循环展开、BN_CTX 复用、并行建表与双向求解等手段降低单次运算成本。其中双向 BSGS 使负值解密不再反复扫描，代价是正数聚合解密的常数因子略增，实测对聚合查询整体影响小于 10%。针对短命客户端进程（如 psql 每次连接即退出）的启动耗时：BSGS 表由每次进程运行时重建改为静态数据（由生成程序直接复用核心算法生成，编译进 libpq，参数指纹校验兜底），消除建表 0.5s；KEK 文件解密中的 PBKDF2（10000 次迭代）改用 HMAC 上下文复用，避免 OpenSSL 3.0 下每次迭代重新获取 provider 与分配上下文的开销，两次 PBKDF2 合计约 98ms 降至约 12ms。两项合计使 HE 客户端查询启动由约 0.6s 降至约 0.18s，且对称加密查询的 KEK 加载同步受益。

**客户端加解密层**：单次 HE 加解密内部天然存在相互独立的计算单元（he-add 的 8 个分块、he-mul 的 2 次模幂），并行化后单次运算提速约 1.4~1.5 倍；文本协议下的 HEX 编解码改用查找表后，密文输出不再成为扫描类查询的瓶颈。批量 INSERT 与批量 SELECT 是收益最大的场景：INSERT 侧按 HE 字段分片并行，SELECT 侧按行分片并行解密，均以环境变量控制并发度，行数较少时自动退化为串行以规避线程开销。

**服务端聚合层**：同态加法 SUM 的瓶颈在服务端逐行 EC 点加，通过 PG 原生并行聚合（Gather + Partial Aggregate）将累加分摊到多个 worker，实测约 4.6 倍加速，无需改动聚合逻辑。

**服务端缓存与元数据层**：公钥缓存由单键扩展为多键哈希表，多 DEK 列交替访问时不再反复失效重载；建表元数据检测由全表扫描改为复用现有索引扫描。

**查询优化器层**：DET 加密列仅支持等值比较（不可排序），优化器在规划期将 DET 等值 JOIN 分流到 Hash Join，避免误选 Merge Join 导致运行期报错，保证 JOIN 查询稳定高效。

> 上述优化的共同原则：仅在计算单元相互独立、可安全并行时启用并发；所有并行路径均保证共享资源只读或线程隔离，避免数据竞争；算法类优化均通过与 OpenSSL 结果的一致性测试兜底，确保密文语义不变。

## 5.3 定义改写设计

### 5.3.1 复用 SELECT 处理链路

视图/物化视图的定义查询按 SELECT 语句处理，完整复用现有 SELECT 处理链路：

由此保证视图定义与直接查询基表在过滤、表达式、排序等行为上完全对齐，无需为视图单独实现加密语义。

### 5.3.2 密态常量加密与原位改写机制

常量加密后通过"原位替换"完成语句改写：解析器记录常量在完整 SQL 中的字节偏移，加密后直接替换原文中的明文常量，其余语法元素（OR REPLACE、TEMP、视图名、列名列表、WITH 选项等）原样保留，改写结果即完整的 CREATE VIEW / CREATE MATERIALIZED VIEW 语句，发送服务端执行：

```
CREATE VIEW v AS SELECT ... WHERE name = 'Alice'
        │  识别密态列 → 常量加密（DET）
        ▼
CREATE VIEW v AS SELECT ... WHERE name = E'\\x<DET密文>'   ← 原位替换，其余不变
        │
        ▼
服务端存储（普通视图规则系统 / 物化视图密文落盘）
```

## 5.4 加密元数据设计

### 5.4.1 元数据注册路径

普通视图与物化视图的加密列元数据均由服务端在视图/物化视图建表（CTAS 路径）处理时自动注册到 hg_encrypted_columns：

- 普通视图：CREATE VIEW 经服务端视图定义处理，加密列元数据随定义注册；
- 物化视图：创建时执行定义查询将密文落盘，同时注册加密列元数据。

### 5.4.2 元数据继承与关联规则

- 视图/物化视图列继承基表列的 DEK 与算法配置，无需在视图中重复声明；
- 元数据按视图/物化视图自身的 OID + 列序号关联，与基表解密路径完全一致；
- 数据获取器按"表 OID + 列序号"查询加密列元数据（含 DEK、算法、USAGE 权限），视图查询解密与直接查询基表共用同一链路，无需额外逻辑。

## 5.5 查询解密设计

- SELECT FROM 视图/物化视图时，前端按视图返回列的加密元数据自动解密：开启密态功能且有权限时返回明文，否则返回密文；
- 视图查询时追加的过滤条件（WHERE 密态列）由客户端改写加密（需 DET/OPE），与直接查询基表一致；
- 视图/物化视图支持密态列与普通列混合、全部或部分密态列投影。

## 5.6 物化视图生命周期设计

### 5.6.1 REFRESH 机制

- REFRESH MATERIALIZED VIEW 语句不含定义，前端透传；
- 服务端按已存储的定义重新填充数据：定义中密态列过滤常量为创建时加密的密文常量，刷新时复用，保证刷新前后过滤语义一致；
- 元数据按物化视图 OID 关联，刷新重填不改变加密列元数据。

### 5.6.2 WITH NO DATA / WITH DATA

- WITH NO DATA：仅创建物化视图结构、不填充数据，加密列元数据同样注册（结构与元数据一致）；
- WITH DATA（默认）：创建即填充数据；
- 行为与 PostgreSQL 原生语义一致。

## 5.7 约束与限制

| 场景 | 行为 |
|---|---|
| 定义中 WHERE/ON 密态列过滤（=、<>、<、>、<=、>=） | 支持（需 DET/OPE，未配置报错）|
| 定义中表达式（如字符串拼接） | 报错（密文不可运算，与直接查询一致）|
| 定义中 ORDER BY / DISTINCT 密态列 | 报错（需 OPE/DET，与直接查询一致）|
| 定义中非解密聚合（count 等） | 支持 |
| DEK 轮换后 | 定义中固化的密文常量失效，需重建视图 / 刷新物化视图 |
| 无加密列的视图定义 | 透传，行为不变 |

## 5.8 故障/异常处理

- 密态列过滤未配置 DET/OPE：报错"操作符需要DET或OPE算法"，与直接查询基表一致；
- 定义中表达式/排序/去重非法：报错信息与直接查询基表一致；
- 视图/物化视图元数据获取失败（如基表已删除）：查询时报错，与 PG 原生行为一致。

# 6  **V5-AD-3**  **工具增强设计**

对应需求 4.4.2.1"工具增强"：扩展 psql 等客户端工具对密态数据的支持。本节覆盖 **\copy 元命令的子查询导出与 BINARY 格式**；pg_dump 导出 KEK/DEK 创建语句（V4.0.1-20-3-10）等能力在后续版本补充。

## 6.1 \copy 子查询导出与 BINARY 格式

### 6.1.1 能力概述

\copy 是 psql 客户端元命令，数据在客户端本地处理：导出时密态列输出明文，导入时明文经客户端加密后发送服务端。V4.0.0 已交付 \copy 的 TEXT、CSV 格式，本模块在既有能力之上新增 **BINARY 格式**与**子查询导出**两项能力：

| 能力 | V4.0.0（已交付） | V4.0.1（本模块） |
|---|---|---|
| \copy 表导出/导入（TEXT 格式） | 支持（加密列明文输出） | 保持 |
| \copy 表导出/导入（CSV 格式） | 支持 | 保持 |
| \copy 表导出/导入（BINARY 格式） | 不支持 | 新增 |
| \copy (SELECT ...) TO 子查询导出 | 不支持 | 新增 |

### 6.1.2 行为模型（客户端 \copy 与服务端 COPY 相互独立）

| 维度 | 客户端 \copy（psql 元命令） | 服务端 COPY（SQL 命令） |
|---|---|---|
| 数据处理位置 | 客户端（libpq） | 服务端 |
| 加密列导出 | 输出明文（解密后） | 输出密文 |
| 加密列导入 | 明文加密后发送服务端 | 直接写入密文 |
| 子查询支持 | 支持 \copy (SELECT ...) TO | 支持 COPY (SELECT ...) TO |
| 行为关系 | 相互独立，互不影响 | 相互独立，互不影响 |

### 6.1.3 BINARY 格式设计

**协议遵循：**

\copy 的 BINARY 格式遵循 PostgreSQL 原生二进制 COPY 协议（PGCOPY 签名 + 标志区 + 扩展区 + 字段长度头 + NULL 标记），与 TEXT/CSV 的按行文本解析不同，BINARY 模式按字段长度头定位边界，密态列密文以二进制形态随流传输，客户端按列元数据完成解密/加密。

**覆盖范围：**

| 场景 | 说明 |
|---|---|
| 类型覆盖 | 全 9 种密态类型（int2/int4/int8/float4/float8/numeric/varchar/bpchar/text 的 _enc 变体）|
| 混合列 | 加密列与非加密列混合的表 |
| 边界值 | INT2/INT4/INT8 上下限、浮点精度边界、Numeric 精度、特殊字符 |
| NULL 值 | 全 NULL、部分 NULL、首列 NULL、末列 NULL 等组合 |
| 数据一致性 | BINARY 导出后再导入（roundtrip）数据保持一致 |

**处理要点：**

- 导出（TO）：密态列密文解析为明文后按目标类型序列化为二进制字段；
- 导入（FROM）：明文按源列类型解析、加密后编码为二进制字段；
- NULL 值按二进制协议 NULL 标记处理，不参与加解密；
- 密文在二进制流内部以明文长度头界定，客户端按列映射定位密态列槽位。

### 6.1.4 子查询导出设计

\copy (SELECT ...) TO 'filename' 复用前端 SELECT 处理链路识别加密列，导出时对查询结果按列解密：

| 子查询场景 | 行为 |
|---|---|
| 单表 SELECT \* | 全部加密列解密导出 |
| 单表显式列 / 单列 | 对应加密列解密导出 |
| 单表非加密列 | 原样导出 |
| 多表 JOIN | 结果集内加密列全部解密导出 |
| 聚合函数（COUNT(\*) 等） | 聚合结果为非密文值，原样导出 |
| GROUP BY 加密列 | 分组键加密列解密导出，聚合值原样导出 |

### 6.1.5 约束与限制

- 子查询中加密列仅支持解密输出，不支持在子查询内对密文做运算（与直接查询行为一致）；
- 多表 JOIN 场景结果集内加密列全部解密导出（与需求约定一致）；
- BINARY 模式按列类型严格解析，类型不匹配时报错；
- 客户端 \copy 与服务端 COPY 行为相互独立，互不影响。

### 6.1.6 故障/异常处理

- BINARY 流解析失败（签名错误、字段长度越界）：报错并终止本次 COPY；
- 密态列解密失败（密钥缺失、密文损坏）：按行报错，事务内可回滚；
- 子查询中引用未知加密列/表：报错提示元数据无法获取。

## 6.2  pg_dump 导出与跨平台恢复设计

对应需求 4.4.2.1（V4.0.1-20-3-10）与 4.8.1（V4.0.1-20-3-21）：pg_dump 将 KEK/DEK 创建语句导出到备份文件，pg_restore 还原时可重建密钥元数据，并支持跨平台恢复。

### 6.2.1 导出范围

- **KEK**：导出 key_store、key_algo、key_path、public_key（非对称 KEK 公钥，入库明文值）；
- **对称 DEK**：导出 kek 引用、key_algo、encrypted_value（已加密的 DEK 密文 hex 串）、key_length；
- **同态 DEK**（key_algo = he-add / he-mul）：导出 kek 引用、key_algo 及 HE 密钥对材料（he_ec_pubkey / he_ec_privkey / he_eg_pubkey / he_eg_privkey）；
- **密钥文件**（.key / .priv / .pub）不在备份范围内，仅导出元数据，密钥文件需单独备份。

### 6.2.2 导出语句结构

每个 KEK/DEK 对象导出 DROP + CREATE 语句对，pg_restore 按对象依赖顺序执行重建：

- CREATE KEK：输出 key_store / key_algo / key_path / public_key 参数，还原时前端解析后重新校验并入库；
- CREATE DEK WITH VALUES：输出 kek / key_algo / key_length / encrypted_value（对称）/ HE 密钥对材料（同态），还原时生成/重建元数据记录。

### 6.2.3 还原流程

- pg_restore 按依赖顺序重建 DEK/KEK 元数据；
- 还原前需在目标机器放置对应的 .key 文件（对称 KEK）或 .priv 文件（非对称 KEK，且需同时存在同名 .pub 公钥文件——CREATE KEK 还原时从 .priv 同目录加载 .pub 入库）；
- 密钥文件缺失或校验失败时还原报错，事务内可回滚。

### 6.2.4 跨平台恢复

- 导出的 key_path 仅用于运行时定位密钥文件名；
- 跨平台还原时在目标机器设置 TECC_KEK_PATH 环境变量指向密钥文件所在目录，由 TECC_KEK_PATH 替代 key_path 中的目录部分定位密钥文件，屏蔽不同平台路径格式差异（如 Windows 盘符与 Linux 挂载点）；
- 未设置 TECC_KEK_PATH 时按 key_path 原始路径查找，失败报错。

### 6.2.5 限制

- 密文数据随普通 pg_dump 数据导出（密态列在库内为密文存储，导出/导入不改变其形态）；
- 明文导出（客户端解密后导出明文）不在本设计范围，与 \copy 子查询导出的行为相互独立。

# 7  **V5-AD-4**  **密钥管理设计**

对应需求 4.5.1"安全性-密钥管理"：在 V4.0.0 两级密钥（KEK/DEK）体系上引入非对称密钥体系，覆盖密钥算法参数、一列多 DEK 绑定、HE 密钥对生成与存储、分布式身份标识、KEK 密钥轮换等设计，支撑同态加密与密钥生命周期管理。

## 7.1 密钥算法参数（key_algo）设计

KEK 与 DEK 统一使用 key_algo 参数指定密钥算法，以"对称/非对称、用途"为语义划分，便于后续扩展新算法（如 rsa、aes、paillier 等）。

**KEK（密钥加密密钥，仅用于信封加密保护 DEK）：**

| key_algo | 算法 | 密钥材料 | 保护对象 |
|---|---|---|---|
| sm4（默认）| SM4 对称 | 32B 随机密钥（MEK 加密存 .key 文件）| 传统 DEK 密文（encrypted_value）|
| sm2 | SM2 非对称密钥对 | SM2 密钥对（localkms：私钥 MEK 加密存 .priv、公钥入库；swxakms/tzwykms：密钥对托管密码机、公钥导出后入库）| HE DEK 私钥（SM2 公钥信封加密）|

**DEK（数据加密密钥）：**

| key_algo | 算法 | 密钥材料 | 服务算法 |
|---|---|---|---|
| sm4（默认）| SM4 对称 | 32B 随机密钥（KEK 加密存 encrypted_value）| DET/OPE/SEARCH/RND |
| he-add | EC-ElGamal | EC-ElGamal 密钥对（P-256）| he-add（加减法、SUM、标量）|
| he-mul | ElGamal | 有限域 ElGamal 密钥对（RFC 5114 2048-bit）| he-mul（乘法、幂）|

**设计要点：**
- 同态 DEK 按算法独立生成密钥对，he-add 与 he-mul 各是各的、互不混用；
- 传统 DEK（sm4）绑定对称 KEK（sm4），同态 DEK（he-add/he-mul）绑定非对称 KEK（sm2，信封加密需要公钥），创建时校验；

## 7.2 一列多 DEK 绑定

同一密态列可同时绑定对称 DEK 与同态 DEK：

```sql
CREATE TABLE t (
    c int4_enc ENCRYPTED WITH (
        DEK = dek_sym,               -- 对称DEK（sm4）：DET/OPE/SEARCH/RND
        HE_ADD_DEK = dek_he_add,     -- he-add DEK（可选，he-add/he-sub/SUM）
        HE_MUL_DEK = dek_he_mul,     -- he-mul DEK（可选，he-mul）
        SUPPORT_ALGO = 'det,he-add,he-mul'
    )
);
```

- 对称槽位（RND/DET/OPE/SEARCH）使用对称 DEK；
- EG_ADD 槽位使用 he-add DEK；EG_MUL 槽位使用 he-mul DEK；
- 各槽位密文独立携带所属 DEK 的分布式身份标识（见 4.4.1），服务端运算与客户端解密按段解析密钥，互不干扰；
- 未指定某同态 DEK 但列开启对应算法时，报错提示。

**多 DEK 校验（双层执行）：**

1. **前端（libpq 建表语句处理器）**：
   - 解析 ENCRYPTED WITH 子句时校验 SUPPORT_ALGO 与 DEK 参数匹配（如开启 he-add 必须给出 HE_ADD_DEK），语法错误立即报错、不访问数据库；
   - 校验 DEK 的 key_algo 与对应算法一致（通过 DEK 缓存元数据）；
   - 校验层次与现有 DET/OPE 互斥校验（前端执行）保持一致。

2. **后端（服务端 CREATE TABLE 处理）**：
   - 权威兜底校验：DEK 存在性、key_algo 与 SUPPORT_ALGO 匹配、USAGE 权限检查；
   - 防止绕过前端（如直接 SQL、第三方客户端）提交非法定义；
   - 校验通过后将多 DEK 引用写入列 DEK 绑定元数据表 hg_encrypted_column_args（见下）。

**建表校验规则汇总（对应需求 V4.0.1-20-3-3）：**

| SUPPORT_ALGO 配置 | 必选 DEK 参数 | key_algo 要求 |
|---|---|---|
| 含 DET/OPE/SEARCH/RND 任一对称算法 | DEK | 'sm4' |
| 含 he-add | HE_ADD_DEK | 'he-add' |
| 含 he-mul | HE_MUL_DEK | 'he-mul' |
| 未配置的算法 | 对应 DEK 参数可省略 | — |

- 所有指定的 DEK 必须存在，且当前用户对其具有 USAGE 权限，否则报错；
- 同态 DEK（he-add/he-mul）必须绑定非对称 KEK（key_algo='sm2'），对称 DEK 绑定对称 KEK 或非对称 KEK 均可。

**多 DEK 绑定元数据存储（hg_encrypted_column_args）：**

列与 DEK 的多对多绑定关系采用与 hg_dek_args/hg_kek_args 一致的 args 扩展表模式存储，新增系统表 hg_encrypted_column_args：

| 字段 | 说明 |
|---|---|
| oid | 记录 OID |
| column_id | 引用 hg_encrypted_columns.oid |
| function_name | 算法类型标识 |
| key | 'he_add_dek' / 'he_mul_dek' |
| value | DEK 分布式身份标识（4B int4） |

唯一索引：column_id + key；辅助索引：oid；同时挂 toast 与依赖清理机制。

采用 args 扩展表而非直接给 hg_encrypted_columns 加字段，原因：

- hg_encrypted_columns 为系统表，加字段需变更 bki 表结构，影响 V4.0.0→V4.0.1 的 pg_upgrade（文件级拷贝系统表时新旧结构不匹配，且系统表 ALTER TABLE 受 PG 限制），升级复杂；
- 新增 args 表在新库初始化时建空表，pg_upgrade 无历史数据与结构冲突，升级友好；
- 未来扩展（如新增其它算法的 DEK 绑定）只需新增 key 条目，不动表结构。

关联与取值规则：

- column_id 引用 hg_encrypted_columns.oid，与 hg_dek_args.dek_id 引用 hg_dek.oid 的关联模式一致；
- value 存储 DEK 的 column_key_distributed_id（跨实例确定性一致，与密文段内嵌 DEK 身份标识同一体系，见 7.4），不使用实例内 hg_dek.oid，保证迁移/跨库后绑定关系不失效；
- 单 DEK 模式（V4.0.0 兼容）：列仅配置一个 DEK 时，不写 args，DEK 由 hg_encrypted_columns.column_key_id 承载；多 DEK 模式：写入 he_add_dek、he_mul_dek 条目，对称 DEK 仍由 column_key_id 承载。

生命周期管理：

- 建列：后端 CREATE TABLE 处理时，与 hg_encrypted_columns 记录在同一事务写入 args；
- 删列/删表/删 DEK：通过依赖（dependency）机制级联清理对应 args 记录；
- 元数据视图 hg_encrypted_columns_info 扩展 he_add_dek、he_mul_dek 列（关联 args → hg_dek 解析 DEK 名称与分布式 ID），客户端列缓存查询一次获取，无需额外表访问；
- 客户端按列缓存的 he_add_dek/he_mul_dek 分布式 ID 反查 DEK 名称，加载对应 HE 公钥/私钥；服务端运算按密文段内嵌 DEK ID 反查本表获取对应 DEK，做 DEK 匹配与密钥加载。

## 7.3 密钥存储与保护

**HE 密钥对存储（hg_dek_args）：**

| 键 | 内容 | 保护 |
|---|---|---|
| he_ec_pubkey / he_eg_pubkey | HE 公钥（明文 hex）| 可公开 |
| he_ec_privkey / he_eg_privkey | HE 私钥（信封加密 hex）| KEK(sm2) 公钥 SM2 信封加密 |

- 服务端仅存储 HE 公钥明文与信封密文，不接触任何私钥明文，符合"服务端零信任"模型；
- 客户端查询时使用 KEK(sm2) 私钥解密信封获取 HE 私钥，仅在前端内存中使用。

**KEK(sm2) 公钥的入库路径（前端传递，后端不读文件）：**

HE DEK 创建（信封加密）与查询解密（信封解密）分别依赖 KEK(sm2) 公钥与私钥，公钥在 CREATE KEK 时入库 hg_kek_args.PUBLIC_KEY。key_path 是**客户端**密钥文件路径，服务端无法读取（客户端与服务端分离部署时更是如此），故公钥由**前端 libpq 处理器**在 CREATE KEK 时获取并经 SQL 改写传递，服务端不读文件：

- 软加密（localkms）：前端从 key_path 同目录的 .pub 文件读取 65 字节未压缩点（04‖x‖y）；
- 硬加密（tzwykms/swxakms）：前端调用密码机导出公钥接口，返回原始点（bits‖x‖y），剥离长度前缀并补 04 前缀，统一为 65 字节未压缩点；
- 前端将公钥 hex 注入 CREATE KEK 语句的 public_key 参数（与 _tecc_processed 标记一并注入），服务端解析 public_key 参数后以 65 字节二进制存入 PUBLIC_KEY；后端不再读 key_path 文件，消除"客户端服务端同机"的隐含依赖。

**公钥入库的收益（跨客户端创建 HE DEK）：** 信封加密只需公钥、无需私钥，公钥保存于服务端后，任何持有该 KEK USAGE 权限的客户端均可从服务端读取 PUBLIC_KEY 创建 HE DEK（CREATE DEK 时前端从 hg_kek_args 加载公钥做 SM2 信封加密），无需在本地持有 KEK 私钥文件或访问密码机——这是多客户端协同创建 HE DEK 的基础，也避免了各客户端各自保存公钥副本导致的不一致。

**HE 私钥信封的加解密路径设计：**

HE 私钥信封采用 SM2 非对称加密，加解密遵循"公钥加密、私钥解密"的既定分工：

| 操作 | 使用的密钥 | 执行位置 |
|---|---|---|
| 信封加密（CREATE DEK / ALTER KEK 重信封）| SM2 公钥 | 客户端本地（公钥已入库，公开无害）|
| 信封解密（查询时解 HE 私钥）| SM2 私钥 | localkms：本地 .priv 文件；swxakms/tzwykms：密码机内（私钥永不出设备）|

- "公钥本地加密、私钥设备内解密"是非对称密码学在硬加密（HSM）场景下的标准通行做法——国密 SDF 接口的 `SDF_ExternalEncrypt_ECC`（外部公钥加密）与 `SDF_InternalDecrypt_ECC`（内部私钥解密）、PKCS#11 的 `C_Encrypt`/`C_Decrypt` 均按此分工设计，TLS、云 KMS 信封加密等业界实践与之同构；
- 公钥本身设计为公开材料，导出到客户端加密不引入安全损失；私钥始终不出密码机（硬加密的核心安全模型），故解密必须由密码机完成；
- 该分工使 HE 加密侧摆脱设备在线依赖（CREATE DEK 无需设备即可信封加密），仅解密侧依赖密码机，与对称 KEK 场景（加解密均需设备内密钥）形成对照。

## 7.4 分布式身份标识（dek_dist_oid）

- 所有 DEK 在 hg_dek 表生成 `column_key_distributed_id` = hash("schema.dek_name")，跨实例确定性一致；
- 密文中任何位置的 DEK 身份（header 全局字段、EG_ADD/EG_MUL 段内嵌）一律使用该分布式身份标识，不使用实例内 hg_dek.oid；
- 列与 DEK 的绑定元数据（hg_encrypted_column_args 的 value，见 7.2）同样使用该分布式身份标识，保证绑定关系随 DEK 迁移保持一致；
- 服务端按分布式身份反查实例内 hg_dek.oid，客户端按分布式身份反查 DEK 名称，两路解析链路统一；
- 保证同一 DEK 的密文可在多库/跨实例间迁移、交换、解密。

## 7.5 密钥轮换（ALTER KEK）

ALTER KEK 由前端（libpq 处理器）执行 DEK 重加密后改写 SQL 完成，服务端兜底校验权限与参数：

- 对称 KEK 轮换：加载旧/新 KEK（软加密读取密钥文件、硬加密按新 KEY_PATH='hsm:id=<索引>' 构造 16 字节 placeholder 并复用 HSM_KEY/SWXAKEY 标记），用旧 KEK 解密关联传统 DEK（encrypted_value）再用新 KEK 重新加密——软加密走本地 SM4-CBC+HMAC、硬加密由密码机内对称 KEK 加解密；
- 非对称 KEK 轮换：使用新 KEK(sm2) 公钥重新对关联 HE DEK 的私钥做信封加密（he_ec_privkey/he_eg_privkey），新公钥由新私钥 DER 派生一次（硬加密从密码机导出公钥）；轮换遵循 7.3 的加解密分工——旧 KEK 私钥解 HE 私钥信封（软加密本地 tecc_sm2_envelope_decrypt、硬加密由密码机内 SM2 私钥 sm2_decrypt 解密、私钥不出境）、新 KEK 公钥重信封（本地），对应用透明；
- 一列多 DEK：轮换对该 KEK 关联的所有 DEK（含一列多 DEK 场景下绑定的对称 DEK 与各 HE 算法 DEK）分别重加密，DEK 明文不变、已加密数据无需重加密；
- 轮换在客户端完成旧 DEK 解密、新 KEK 重加密、批量更新 hg_dek_args（同一事务），失败可回滚；
- 轮换完成后前端清除连接级缓存（tecc_cache 与 key_manager 的 DEK 明文缓存）并重载 KEK 元数据，避免同连接继续使用旧 KEK 解密新 encrypted_value；
- 在线轮换：各连接独立缓存，轮换期间及完成后其它连接基于自身缓存继续加解密不受影响，无需中断业务；
- 服务端 ALTER KEK 校验 ACL_UPDATE 权限与参数合法性（KEY_PATH 必填），并更新 KEK 的 KEY_PATH 元数据；
- 轮换仅 KEK 所有者或具有相应权限的用户可执行，过程对应用透明。

## 7.6 V4.0.0 兼容策略

为保障 V4.0.0 存量密文与建表语句的平滑过渡，本模块保留 V4.0.0 的单 DEK 风格兼容：

| 场景 | V4.0.0（旧） | V4.0.1（新） |
|---|---|---|
| 同态 DEK | 不支持同态，无 HE DEK（仅对称算法 DET/OPE/SEARCH/RND）| 新增 he-add / he-mul 同态 DEK，按算法独立密钥对 |
| 列绑定 | 一列一个对称 DEK | 一列可多 DEK（对称 + he-add + he-mul）|
| 建表风格 | `DEK = dek_name, SUPPORT_ALGO='det,ope,search'` | 对称部分沿用 `DEK = ...`；同态显式 `HE_ADD_DEK/HE_MUL_DEK` 参数进入多 DEK 体系 |

兼容规则：

- 建表时若**未显式提供 HE_ADD_DEK/HE_MUL_DEK**，保持 V4.0.0 单 DEK 建表风格：列启用同态算法时，`DEK` 参数直接指定同态 DEK（key_algo='he-add' 或 'he-mul'），该 DEK 可同时服务 he-add 与 he-mul——这是 V4.0.1 多 DEK 体系落地前的**过渡形态**（P0-2），V4.0.0 本身不支持同态，不存在"一个 HE DEK 同时含 EC+FF 两套密钥对"的形态；
- 显式提供任一 HE_ADD_DEK/HE_MUL_DEK 即进入多 DEK 体系，按 7.2 的规则校验与存储；
- 旧密文（V4.0.0 格式，对称算法加密）可继续解密，无需重加密。

## 7.7 tecc_ktool 软加密密钥生成工具（对应需求 V4.0.1-20-3-16）

### 7.7.1 定位与边界

tecc_ktool 是独立的离线 KEK 文件管理 CLI 工具，**不依赖数据库连接**，仅管理软加密（localkms）的本地密钥文件，不涉及硬加密（tzwykms/swxakms）密码机；支持 Linux 和 Windows 平台。

与 SQL 命令的分工：

| 工具/命令 | 职责 | 依赖 |
|---|---|---|
| tecc_ktool | 线下生成/管理 KEK 密钥文件（.key/.priv/.pub），不碰数据库 | 无（离线）|
| CREATE KEK | 将 KEK 元数据注册至数据库，引用 tecc_ktool 生成的文件路径 | 数据库 + 密钥文件 |
| ALTER KEK | 在线 DEK 重加密轮换 | 数据库 + 新旧密钥文件 |

### 7.7.2 命令集

| 命令 | 参数 | 功能 |
|---|---|---|
| generate | --key-name、--key-algo <sm4\|sm2>、--key-path <目录>、[--force] | 生成 KEK 密钥文件 |
| list | [--dir <path>] | 扫描目录，展示 .key/.priv 文件列表（Name 列为文件名去扩展名）|
| info | --key-path <path> | 查看密钥文件元信息（类型、大小、创建时间、格式版本、.pub 存在性）|
| delete | --key-path <path> | 安全销毁密钥文件（4 遍覆写后删除）|
| validate | --key-path <path> | 校验密钥文件完整性（格式 + HMAC）|

### 7.7.3 文件生成与命名

| key_algo | 生成文件 | 内容 |
|---|---|---|
| sm4（对称）| `<key-name>.key` | 32 字节随机密钥，MEK 加密存储 |
| sm2（非对称）| `<key-name>.priv` + `<key-name>.pub` | SM2 私钥 DER（MEK 加密）+ 公钥 65 字节未压缩点（明文）|

设计要点：

- 文件命名：`--key-name` 决定文件名基名，`--key-path` 指定生成目录（不存在自动创建，权限 0700）；
- key-name 校验：必须是纯文件名（不含路径分隔符、不以 . 开头、非 . 或 ..），防止路径穿越；
- **覆盖保护**：目标文件已存在时 generate 默认报错拒绝覆盖（防止误覆盖已注册 KEK 导致关联 DEK 无法解密），确认需重新生成时加 `--force` 显式覆盖；
- generate 成功后输出对应的 CREATE KEK 参考语句，引导用户完成数据库注册。

### 7.7.4 密钥文件格式

TECCKEK v1 自描述格式：

```
magic(7) + ver(1) + reserved(8) + algo_id(4) + salt(16) + iv(16)
+ SM4-CBC 密文 + HMAC-SHA256(32)
```

- 文件以固定 MEK（32 字节主密钥）加密：tecc_ktool 生成路径与运行时解密路径（kms_adapter）使用**同一固定密钥**，保证工具生成的文件运行时可直接解密，同时避免"MEK 轮换导致旧文件不可读"问题；
- 与库内密钥材料的层级区分：.key/.priv 文件是 MEK 保护的密钥文件；hg_dek 的 encrypted_value 是 KEK 保护的 DEK 密文；hg_dek_args 的 HE 私钥信封是 KEK(sm2) 公钥 SM2 加密，三层各自独立、互不混用。

### 7.7.5 安全设计

- delete 采用 **4 遍覆写**（全零 → 全一 → 随机 → 全零）并逐遍 fsync 落盘后 unlink，防止密钥材料被普通文件恢复工具找回；删除 .priv 时提示 .pub 未被销毁（公钥可公开）；
- validate 校验文件最小长度、magic 与 HMAC-SHA256，检测文件损坏或被篡改；
- 权限收敛：工具为本地 CLI，仅操作指定目录文件，不提供网络接口；
- 与 CREATE KEK 的公钥入库配合：非对称 KEK 注册时由前端从 .priv 同目录加载 .pub 文件（65 字节未压缩点）经 SQL 传递入库 hg_kek_args（详见 7.3 公钥入库路径设计）。

# 8  **V5-AD-5**  **会话级加解密元命令设计**

`\enable hg_tecc.mode` / `\disable hg_tecc.mode`

会话级加解密控制用于满足调试、验收和运维场景：同一连接内，用户可临时关闭客户端结果解密，直接查看服务端返回的密文形态（十六进制表示）；恢复开启后，业务查询继续透明返回明文。该能力仅改变当前 psql/libpq 会话的结果解密策略（客户端处理策略），不修改服务端数据、不影响其他连接。

## 8.1 设计目标

- 提供比连接参数更轻量的会话内开关，用户不需要断开重连即可切换明文/密文视图；
- 与 TECC 客户端透明解密链路复用同一连接状态，不新增服务端 GUC，也不提供 `SET/SHOW/RESET` 入口；
- psql 提供面向交互用户的元命令入口，上层应用提供面向程序调用的 libpq 函数接口；
- 关闭解密时仍保留 SQL 发送、密态列识别、常量加密、SQL 改写、错误处理等基础链路，避免绕过 TECC 元数据校验；
- 状态隔离在当前 `PGconn` 连接内，不持久化、不参与事务提交或回滚、不影响其他连接。

## 8.2 状态模型

|状态|含义|SQL 发送前处理|查询密态列结果|典型用途|
|---|---|---|---|---|
|启用|默认透明解密模式|执行密态列识别、常量加密和 SQL 改写|客户端解密后的明文|业务查询、回归测试明文断言|
|禁用|密文查看模式|仍执行密态列识别、常量加密和 SQL 改写（保留基础链路）|服务端返回的密文格式（十六进制表示）|排查密文段、验证导入导出、比较工具函数输出|

状态保存在当前连接的 TECC 客户端状态对象 `TeccState` 中，由 `TeccState.guc_params.tecc_mode` 表示当前连接是否启用结果解密。这里沿用既有结构字段承载客户端状态，但 `hg_tecc.mode` 本身不是服务端 GUC，也不通过 SQL `SET/SHOW/RESET` 访问。连接关闭后状态消失；新连接按连接参数、环境变量或 psql 启动选项重新初始化。该状态不写入数据库系统表，不参与事务提交和回滚。

连接参数 `enable_tecc=1` 负责在连接建立阶段启用并初始化 TECC 客户端能力；会话级开关只在已经初始化的 TECC 连接上动态控制当前 `PGconn` 后续查询是否执行结果解密。未启用 TECC 的普通连接不创建完整 TECC 状态，元命令和 libpq 接口应返回明确错误。

## 8.3 libpq 接口设计

会话级开关对上层 C 应用提供两个公开 libpq 接口，声明位于 `libpq-fe.h`：

```c
int PQteccSetMode(PGconn *conn, int enabled); 使用示例： PQteccSetMode(conn, 0/1);
int PQteccGetMode(PGconn *conn, int *enabled); 使用示例：PQteccGetMode(conn, &mode)；需手动获取mode的值得到加解密状态。
```

接口语义如下：

|接口|输入|输出/返回值|说明|
|---|---|---|---|
|`PQteccSetMode`|`conn` 为当前连接；`enabled` 为 0 表示关闭，非 0 表示开启|成功返回 0，失败返回 -1|修改当前 `PGconn` 的 TECC 会话模式；不向服务端发送 `SET` 命令，不影响其他连接|
|`PQteccGetMode`|`conn` 为当前连接；`enabled` 为输出参数|成功返回 0 并写入 0/1，失败返回 -1|读取当前 `PGconn` 的 TECC 会话模式；输出值 1 表示开启，0 表示关闭|

失败场景包括连接指针为空、输出参数为空、当前连接未启用 TECC 或 TECC 客户端状态未初始化。接口只改变 libpq 客户端状态，不提交事务、不回滚事务、不修改服务端配置。

psql 元命令层复用上述接口：`\enable hg_tecc.mode` 等价于对当前 `pset.db` 调用 `PQteccSetMode(pset.db, 1)`；`\disable hg_tecc.mode` 等价于调用 `PQteccSetMode(pset.db, 0)`。因此交互式用户和上层应用共享同一套连接级状态与错误处理规则。

## 8.4 处理流程

```
用户输入 psql 会话元命令
    │
    ▼
psql 命令层识别 \enable/\disable hg_tecc.mode
    │
    ▼
调用 PQteccSetMode(conn, enabled)  ────── 上层应用也可直接调用该接口
    │
    ▼
libpq 更新当前 PGconn 的 TECC 会话加解密状态
    │
    ▼
后续查询进入 libpq TECC 处理链路
    │
    ├─ 模式启用：SQL 预处理阶段识别密态列、加密常量并改写 SQL；
    │          结果处理阶段按列元数据加载 DEK，客户端解密后返回明文
    │
    └─ 模式禁用：SQL 预处理阶段仍识别密态列、加密常量并改写 SQL（保留基础链路）；
               结果处理阶段跳过解密，应用侧接收服务端返回的密文格式（十六进制表示）
```

禁用模式下，客户端跳过结果解密，直接查看服务端返回的密文形态（十六进制表示），便于排查密文段、验证导入导出；由于 SQL 预处理链路保留，密态列识别、常量加密与错误处理等基础链路照常生效，不绕过 TECC 元数据校验。

## 8.5 边界与异常处理

|场景|处理策略|
|---|---|
|会话中重复启用或禁用|保持幂等，返回当前状态或提示状态已切换|
|当前连接未启用 TECC|元命令和 libpq 接口返回明确错误，不影响普通 PostgreSQL 查询|
|事务中切换|只影响后续结果处理，不参与事务语义，ROLLBACK 不回滚该客户端状态|
|密文格式损坏|模式启用时按解密错误返回；模式禁用时尽量输出原始密文形态，便于排查|
|并发会话|状态隔离到连接级，不共享、不互相影响|

# 9  **V5-AD-6**  **命令行交互与帮助设计**

## 9.1 Tab 补全

Tab 补全复用 psql 既有补全框架，按输入上下文返回静态关键字或数据库对象候选。TECC 新增对象通过系统表查询生成候选，避免用户手工记忆 KEK/DEK 名称和密态列参数。

|输入场景|补全内容|数据来源|
|---|---|---|
|DROP KEK、`\dkek`、`\sK`|KEK 名称|hg_kek|
|DROP DEK、CREATE DEK 中 KEK 绑定、`\ddek`、`\sk`|DEK 或 KEK 名称|hg_dek / hg_kek|
|CREATE / DROP 后续关键字|KEK、DEK 等 TECC DDL 关键字|psql 静态关键字表|
|ENCRYPTED WITH 子句|DEK、SUPPORT_ALGO、算法候选值|静态关键字 + hg_dek|
|TECC 工具函数|函数名候选|pg_proc|

算法候选值覆盖传统查询算法和同态算法，包括 DET、OPE、SEARCH、DET/SEARCH 组合、OPE/SEARCH 组合、he-add、he-mul 及 he-add/he-mul 组合。补全仅辅助输入，不替代后端语义校验。

## 9.2 帮助信息

帮助信息分为三层：

|帮助入口|展示内容|设计要点|
|---|---|---|

# 11  **V5-AD-8**  **维修性工具函数设计**

## 11.1  **总体设计原则**

- 权限收敛：不额外限定超级用户；`tecc_enc_info` 遵循函数及源表/列权限，`tecc_enc_ratio` 要求目标表整表 `SELECT` 权限，`tecc_decrypt_raw` 还要求实际算法 DEK 的 `USAGE` 权限；
- 类型收敛：仅接受 TECC 密态类型作为密文入参，非密态类型明确报错；
- 输出可观察：返回结构化字段，便于 psql 查看、回归测试断言和问题定位；
- 不泄露密钥：函数不输出 KEK/DEK 明文；服务端不读取本地 KEK 私钥文件，`tecc_decrypt_raw` 仅在客户端加载所需密钥；
- 前后端分工：`tecc_enc_info`、`tecc_enc_ratio` 是后端 SQL 函数；`tecc_decrypt_raw` 是 libpq 前端伪函数，查询预处理阶段改写为源密态列投影，结果处理阶段在客户端解密。

## 11.3  **tecc_enc_info 设计**

tecc_enc_info 面向单个密态值解析 CipherDataType。函数不做业务解密，只读取密文头部和各算法段边界，并将段内容以十六进制文本输出。

|字段类别|字段|说明|
|---|---|---|
|基础信息|version、dek_dist_oid、total_len|密文格式版本、DEK 分布式身份标识、总长度|
|传统算法段|rnd_len/rnd_hex、det_len/det_hex、ope_len/ope_hex、search_len/search_hex|RND、DET、OPE、SEARCH 段长度和内容|
|同态算法段|he_add_len/he_add_hex、he_mul_len/he_mul_hex|HE-ADD、HE-MUL 段长度和内容|

处理流程如下：

```
函数及源对象权限检查
 ·-> 入参 NULL 判断
 ·-> 密态类型校验
 ·-> CipherDataType 结构校验
 ·-> 读取头部与各算法段
 ·-> 组装 record 返回
```

当密文结构损坏、长度字段越界或入参不是密态类型时，函数返回明确错误，避免输出误导性内容。

## 11.4  **tecc_decrypt_raw 设计**

tecc_decrypt_raw 是 libpq 前端伪函数，用于返回指定算法对应的原始明文字节 hex。它只接受“直接密态列引用 + 非空常量算法名”，要求 `hg_tecc_mode=on`；普通列、常量、表达式或空算法名入参均报错。函数不做业务类型反规范化或文本格式化，因此返回值用于诊断，不等同于普通 SELECT 的业务显示值。

|输入算法名|目标段|未配置时行为|
|---|---|---|
|rnd|解密 RND 基础密文段|报错提示段不存在|
|det|解密 DET 确定性密文段|报错提示段不存在|
|ope|独立解密 OPE 段，返回归一化明文 hex（调试用，非业务显示原文）|报错提示段不存在|
|search|不支持恢复明文|直接报错|
|he_add / he-add|用对应 HE DEK 私钥解密 EC-ElGamal 段|报错提示段不存在|
|he_mul / he-mul|用对应 HE DEK 私钥解密有限域 ElGamal 段|报错提示段不存在|

libpq 在预处理阶段将伪函数调用改写为源密态列投影，服务端按普通 SELECT 执行并返回完整密文；libpq 结果处理阶段抽取所需载荷，检查实际算法 DEK 的 `USAGE` 权限并在客户端解密。`hg_tecc_mode=off`、普通列入参、无 DEK 权限、算法不支持或载荷缺失时均失败关闭，不返回密文或明文 hex。若需查看完整密文结构，应使用 tecc_enc_info。

## 11.5  **tecc_enc_ratio 设计**

tecc_enc_ratio 按表定义和密态列元数据进行静态估算，不扫描真实表数据。函数输出密态列明细行和 TOTAL 汇总行，帮助用户在容量规划阶段评估密态算法组合带来的存储开销。

调用者必须具有目标表的整表 `SELECT` 权限，仅有部分列权限时拒绝执行。函数不要求调用者必须为超级用户。

### 11.5.1 输入参数

|参数|说明|默认值与约束|
|---|---|---|
|table_name|待估算表名，支持 schema.table 形式|必填，需解析为当前数据库普通表|
|varlena_length|变长类型估算长度|可选，默认 20 字节，必须大于 0|

### 11.5.2 输出字段

|字段|说明|
|---|---|
|column_name|密态列名；汇总行为 TOTAL|
|source_type / source_len|原始明文类型及估算长度|
|enc_type / algorithms|密态类型及算法组合|
|plain_size / enc_size / ratio|单值明文大小、密文大小和单列膨胀率|
|total_plain_1m / total_enc_1m / overall_ratio|100 万行规模下明文表、密态表估算大小和整表膨胀率|

### 11.5.3 估算口径

|项目|处理方式|
|---|---|
|定长类型|使用类型固定长度|
|变长类型|优先使用 typmod；无法确定时使用 varlena_length|
|密文结构|按 CipherDataType 头部和已配置算法段估算|
|整表汇总|同时考虑非密态列、tuple header、NULL bitmap、行指针和页面头|
|不纳入范围|TOAST、索引、FSM/VM、表膨胀、页碎片、压缩效果、真实数据分布|

该函数的估算值用于方案设计和容量预估，不等同于实际磁盘文件大小；实际占用仍以部署环境、数据分布和索引设计为准。

## 11.6  **前后端调用链配合**

普通 SQL 函数默认不允许直接作用于密态列，以避免在服务端对不可解密数据执行无意义或不安全的明文语义函数。`tecc_enc_info` 作为已注册后端诊断函数接收密态值；`tecc_enc_ratio` 以表名为参数；`tecc_decrypt_raw` 由 SELECT 目标列表处理器识别并改写，不发送同名函数调用到服务端。

|函数类别|密态列入参处理|说明|
|---|---|---|
|普通函数|默认拦截|如字符串、数学、JSON 等明文语义函数|
|受支持聚合/比较函数|按既有规则处理|如 count、min/max 等有限场景|
|后端 TECC 工具函数|放行至服务端执行|tecc_enc_info、tecc_enc_ratio|
|前端 TECC 伪函数|改写为源密态列，客户端处理结果|tecc_decrypt_raw|

该设计保证诊断工具可用，同时不扩大普通函数对密态列的可操作面。

# 12  **V5-AD-9**  **内置函数适配设计**

对应需求 4.4.1.4"内置函数适配"（V4.0.1-20-3-6）。密态列上 PostgreSQL 内置函数的行为取决于列的加密算法能力：排序类函数依赖 OPE 密文保序比较，等值类函数依赖 DET/OPE 密文等值比较，算术类函数依赖同态加密（HE-ADD/HE-MUL）。若查询绕过客户端直接下发，非法组合会在服务端产生晦涩报错（如 "cannot compare encrypted values for ordering"）。本模块在 libpq 客户端查询预处理阶段对内置函数调用做算法能力校验，并对函数参数常量按函数语义加密，保证不支持的内置函数返回固定格式错误信息。

## 12.1 设计目标

- 客户端校验、服务端零改动：校验全部在 libpq tecc_processor 查询预处理阶段完成；
- 固定格式报错：不支持的内置函数统一返回含函数名与列名的 TECC 预处理错误，替代服务器端晦涩报错；
- 行为对齐需求矩阵：count/coalesce 无需算法；min/max/greatest/least 需 OPE；nullif/case 需 DET/OPE；sum 需 HE-ADD 且仅限整型；power 需 HE-MUL 且仅限整型；
- 零误报：校验失败必须阻断查询下发，且不得触发"SAFETY CHECK"类假阳性错误；元数据缺失时防御性放行。

## 12.2 总体设计

校验逻辑位于客户端 tecc_processor（stmt_processor.c / where_clause_processor.c），核心组件：

| 组件 | 职责 |
|---|---|
| 聚合校验器 stmt_validate_aggregate_funcall | 按 TeccAggregateClass 六分类校验 count/min/max/sum/avg/string_agg/array_agg |
| 标量校验器 stmt_validate_scalar_funcall | 按分类校验 greatest/least/power（coalesce/nullif/case 走常量加密与操作符校验） |
| 常量加密 stmt_process_funcall_constants | 加密 coalesce/nullif/greatest/least 参数中的常量 |

校验器均返回 bool（失败时已设置错误信息），挂接于两处：SELECT 目标列 FuncCall 处理循环（聚合校验 → 标量校验 → 常量加密）、WHERE/HAVING 表达式 walker（校验失败以专用结果码 -10/-11 传递，防止特定错误被通用错误覆盖）。校验流程：提取函数名 → 分类（未跟踪函数放行）→ 遍历参数中加密列 → 解析列元数据 → 按分类检查算法位掩码（及整型范围）→ 不满足则报错终止。

## 12.3 算法能力判定

列算法能力以 encryption_type 位掩码表示（DET 0x01 / OPE 0x02 / SEARCH 0x04 / HE-ADD 0x08 / HE-MUL 0x10），经元数据缓存解析 TeccColumnCacheItem 获得；基类型以 original_type_oid 判定（同态运算仅 int2_enc/int4_enc/int8_enc）。

## 12.4 函数支持矩阵

| 函数 | 密态类型 | 依赖算法 | 客户端校验规则 |
|---|---|---|---|
| count（含 DISTINCT） | 全部密态类型 | 无需算法 | 无条件放行 |
| sum | int2_enc、int4_enc、int8_enc | HE-ADD | HE-ADD 位 + 整型基类型，否则报错 |
| min / max | 全部密态类型 | OPE | OPE 位，否则报错 |
| coalesce | 全部密态类型 | 无需算法 | 放行；常量按列算法加密 |
| nullif | 全部密态类型 | DET/OPE | 常量加密阶段按列实际算法（DET 优先、OPE 兜底），两者皆无报错 |
| greatest / least | 全部密态类型 | OPE | OPE 位，否则报错（DET 列报错） |
| case | 全部密态类型 | DET/OPE | WHEN 条件按操作符校验（= 走 DET/OPE、>/< 走 OPE）；THEN/ELSE 分支支持密态列与普通常量混用，普通常量按密态列完整算法模式加密（RND + 列全部对称算法段，与写入路径一致），常量类型与密态列原始类型不兼容时报错 |
| power | int2_enc、int4_enc、int8_enc | HE-MUL | HE-MUL 位 + 整型基类型，否则报错 |

除上述函数外，其它内置函数在密态列上均不支持（avg/string_agg 属明确拒绝类，返回固定格式错误）。幂运算的 `^` 操作符形式走操作符处理路径，保持既有行为（指数须为正整数、上限 10000，he-add 列报错，均为服务端校验）。

## 12.5 常量加密策略

- 白名单：coalesce / nullif / greatest / least，其余函数（如 power）的常量参数不做客户端加密（幂指数须保持明文整数供服务端同态运算）；
- 返回值语义：coalesce/greatest/least 的常量可能被函数返回给外层表达式（may_return_const），按全算法加密；nullif 的常量仅做等值比较、绝不返回，按列实际算法加密；
- 类别过滤：常量与密态列的类型类别（char/non-char）不一致时跳过加密、保持明文；
- CASE 分支常量：THEN/ELSE 分支混用密态列与普通常量时，常量按密态列完整算法模式（RND + 列全部对称算法段，与写入路径一致）加密，使分支密文与列存储格式一致、客户端统一解密；常量类型与密态列原始类型不兼容时报错（见 12.4 case 行与 12.7）；
- 多列一致性：函数参数含多个加密列时校验 DEK 一致性，算法能力取并集。

## 12.6 错误处理设计

不支持的内置函数统一返回固定格式错误，经 psql 输出为 `TECC query preprocessing failed: <消息>`，消息模板五类：聚合需 OPE（`聚合函数 "%s" 需要OPE加密算法，但列 "%s" 未配置OPE`）、聚合不支持（`聚合函数 "%s" 不支持加密列运算，列 "%s" 已加密`）、标量需 OPE、标量需 DET/OPE、标量不支持（同构格式）。校验失败时同步清零重写标志，避免"查询未改写"假阳性。

## 12.7 约束与限制

| 限制 | 说明 |
|---|---|
| CASE switch 形式 | `CASE col WHEN 常量` 形式常量未加密，报 `operator does not exist`；`CASE WHEN 条件` 形式正常 |
| CASE 分支混用类型不兼容 | 密态列与普通常量混用时，常量类型与密态列原始类型不兼容（如 int2_enc 列配字符串常量）报错，前端提示改为与列原始类型匹配的常量或密态列 |
| CASE 跨类型密态列分支 | THEN/ELSE 分支为不同密态类型（如 int2_enc 与 int4_enc）时暂不支持，需同一类型 |
| COALESCE 结果参与 HE 运算 | COALESCE 返回值参与 HE 加/乘时，列需具备对应同态算法，否则报服务器端错误 |
| COUNT(DISTINCT) on 纯 HE 列 | 客户端放行，服务端密文去重语义依赖服务端实现 |

## 14.1 pg_upgrade 升级设计（V4.0.1-20-3-20）

支持从 V4.0.0 升级到 V4.0.1，保证数据一致。pg_upgrade 采用"新库 initdb + 用户表 relfilenode 文件级拷贝 + pg_dump/pg_restore 重建 schema 与对象"的机制，TECC 密钥体系的升级按 14.1.2~14.1.4 设计保证 KEK/DEK 元数据与密文数据完整迁移。总体要求：

- 密文数据二进制兼容：用户表（含密态列）的 relfilenode 文件级拷贝迁移，升级过程不重写密文，升级后客户端按既有解密链路继续解密 V4.0.0 数据；
- 既有系统表保持结构稳定：KEK/DEK 元数据表（hg_kek、hg_dek、hg_kek_args、hg_dek_args）、hg_encrypted_columns 为 V4.0.0 已有系统表，结构保持不变（pg_upgrade 要求新旧版本系统表结构一致）；系统表加字段需变更 bki 表结构、且系统表 ALTER TABLE 受 PG 限制，因此元数据扩展一律采用新增 args 表（新库初始化时建空表，无历史数据与结构冲突，升级友好），各功能模块开发时遵循该约束；
- 新增元数据表：V4.0.1 仅新增 hg_encrypted_column_args（一列多 DEK 绑定），由新库 initdb 建空表，无历史数据需要迁移；V4.0.0 无此表数据；
- 系统目录注册（密态类型、pg_proc/pg_aggregate 等）由升级后的新版本二进制提供，不依赖数据目录迁移；
- pg_upgrade 修改点：适配 TECC 系统表与密态列元数据的检查与迁移逻辑，升级后校验密态数据与元数据一致性（密态查询与解密链路回归）。

### 14.1.1 升级机制与 TECC 系统表数据迁移范围

pg_upgrade 各阶段对 TECC 数据的处理：

| 升级阶段 | 机制 | TECC 数据处理 |
|---|---|---|
| 新集群 initdb | V4.0.1 二进制创建新数据目录 | 系统表结构由 postgres.bki 提供（含 V4.0.0 既有 TECC 系统表与新增 hg_encrypted_column_args 空表），hg_metadata_views.sql 视图随 initdb 安装 |
| 全局对象导出 | pg_dumpall --globals-only --binary-upgrade | 角色/表空间，与 TECC 无直接关系 |
| 每库 schema 导出 | pg_dump --schema-only --binary-upgrade | 导出 KEK/DEK 的 DROP + CREATE 语句（见 14.1.2），含密态建表语句（ENCRYPTED WITH）|
| 用户表数据拷贝 | relfilenode 文件级拷贝（heap/matview/toast/index）| 密态表数据（密文）二进制拷贝，不重写 |
| pg_restore 还原 | 按 dump 文件重建 schema 与对象 | 重建 KEK/DEK 元数据、密态列定义与视图 |

**系统表数据不随文件拷贝迁移**：TECC 系统表属于 pg_catalog 命名空间，pg_upgrade 的 relfilenode 拷贝仅覆盖用户表（get_rel_infos 限定 nspname 非 pg_catalog 且 oid ≥ FirstNormalObjectId），因此 KEK/DEK 元数据（hg_kek、hg_dek、hg_kek_args、hg_dek_args 中的记录）必须通过 pg_dump/pg_restore 重建，不能依赖文件拷贝。

### 14.1.2 KEK/DEK 元数据升级设计

**导出（pg_dump，已实现）**：

- pg_dump 通过 getKekInfo/getDekInfo 读取 hg_kek、hg_dek 及 hg_kek_args、hg_dek_args 参数表，dumpKek/dumpDek 生成重建语句，放置于 PRE_DATA section（先 KEK 后 DEK，按依赖排序）：
  - KEK：`CREATE KEK <name> (key_store, key_algo, key_path, public_key)`；
  - 对称 DEK：`CREATE DEK <name> WITH VALUES (KEK, key_algo='sm4', encrypted_value, key_length)`；
  - 同态 DEK：`CREATE DEK <name> WITH VALUES (KEK, key_algo='he-add'|'he-mul', he_ec_pubkey/he_ec_privkey 或 he_eg_pubkey/he_eg_privkey)`，密钥对材料完整导出，还原后 DEK 保持可用；
- 语句均带 `_tecc_processed = 'on'` 标记，pg_restore 还原时前端处理器跳过重复加密/改写，直接将参数入库。

**还原（pg_restore）**：

- 按依赖顺序先重建 KEK、再重建 DEK（DEK 引用 KEK 名称，还原时按名解析）；
- 还原前需在目标机器放置密钥文件：对称 KEK 需 `.key` 文件、非对称 KEK 需 `.priv` 文件（CREATE KEK 还原时从 .priv 同目录加载 .pub 入库），路径经 key_path / TECC_KEK_PATH 定位（见 6.2.4 跨平台恢复）；
- 硬加密（tzwykms/swxakms）：密钥托管密码机，无文件迁移，KEK 元数据还原后按 KMS 索引关联密码机内密钥。

**分布式身份标识保持**：DEK 的 column_key_distributed_id = hash("schema.dek_name") 为确定性计算，重建后与旧值一致，密文段内嵌的 DEK 身份标识、列绑定元数据（hg_encrypted_columns.column_key_id）随之保持有效，密文数据无需重加密、解密链路不中断。

**一列多 DEK 绑定（hg_encrypted_column_args）**：当前 pg_dump 未导出该表（dumpDek 仅导出对称 DEK 引用与 HE 密钥对材料）。V4.0.1 需补充导出（在 pg_dump 中新增对 hg_encrypted_column_args 的读取与 CREATE 语句生成，按 column_id + key 输出 he_add_dek/he_mul_dek 的 DEK 分布式身份标识），或在升级脚本中依据 hg_encrypted_columns 与 hg_dek 重建绑定条目，保证升级后同态列的一列多 DEK 绑定不丢失。

### 14.1.3 密钥文件与运行环境

- `.key` / `.priv` / `.pub` 密钥文件不随升级迁移，按部署环境自行保持（同 14.2）；升级前后 TECC_KEK_PATH / key_path 指向不变，客户端升级后按既有路径加载密钥文件；
- 密钥文件格式（TECCKEK v1、固定 MEK 加密）在 V4.0.0/V4.0.1 间保持兼容，升级后旧密钥文件可直接使用；
- 硬加密（tzwykms/swxakms）：密钥托管密码机，无文件迁移；KEK/DEK 元数据重建后按 KMS 索引关联，升级后需验证密码机内密钥可用。

### 14.1.4 升级后校验

- 元数据完整性：校验 hg_kek、hg_dek、hg_kek_args、hg_dek_args、hg_encrypted_column_args 记录数与升级前一致（KEK/DEK 数量、参数条目、一列多 DEK 绑定条目）；
- 解密链路回归：对含密态列的表执行 SELECT（等值/范围/模糊查询）与同态加/乘，确认 KEK/DEK 元数据完整、密文可解密、一列多 DEK 列解密正常；
- 等价性校验：pg_dump 还原的 CREATE KEK/DEK 与升级前元数据等价（key_path/key_algo/public_key/encrypted_value/HE 密钥对材料一致），密态查询结果与升级前一致。

| 限制 | 说明 |

# 17  **安全性分析**

本章节说明同态加密设计对产品安全功能的影响。

| 安全维度 | 设计 | 说明 |
|---|---|---|
| 密文安全强度 | EC-ElGamal 基于 P-256 曲线 DLP 困难问题，安全强度约 128 bit；FF-ElGamal 基于 RFC 5114 2048-bit 安全素数群 DLP 困难问题 | 满足等保测评与合规要求 |
| 概率性加密 | 两算法加密均引入随机数 r，同一明文多次加密产生不同密文 | 防止密文模式泄露明文分布 |
| 服务端零信任 | 服务端仅存储 HE 公钥明文与私钥信封密文，不接触私钥明文；标量常量加密使用服务端公钥现场进行 | 私钥不出客户端 |
| 私钥保护 | HE 私钥以 KEK(sm2) 公钥做 SM2 信封加密后落库，客户端用 KEK 私钥解封（软加密 localkms 本地 .priv 文件、硬加密 tzwykms/swxakms 密码机内 SM2 私钥，私钥永不出设备）| 密钥材料全链路加密存储 |
| DoS 防护 | 幂运算指数上限 10000，防止指数过大导致服务端运算耗时失控 | 可用性保障 |
| 溢出防护 | 服务端不判溢出，客户端解密后按类型范围校验，超范围报错 | 数据正确性保障 |
| 密文可迁移性 | DEK 身份一律使用分布式标识（hash(schema.dek_name)），跨实例一致 | 迁移/灾备场景安全 |
| 权限控制 | DEK 使用需 USAGE 权限；KEK 轮换需所有者权限；工具函数按函数、表/列及 DEK 对象权限控制 | 密钥操作审计 |
